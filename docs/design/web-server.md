# Web server

This is one of PayOnce's design notes. [CLAUDE.md](../../CLAUDE.md) has the commands, the file map, the rules that hold everywhere and the index of these notes. Where the two differ, this file is right.

- It binds to loopback and has no login. `guard` checks the Host header and, for writes, the Origin header and a JSON content type. It refuses an `/api/` GET with 403 when `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`, or when an `Origin` header names another origin (`crossSite`). Static files stay open. `X-Content-Type-Options: nosniff` is set once before routing, so every response has it, CSV downloads and errors included.
- Routes: the reconciliation routes under `/api/reconcile` (see Reconciliation), `GET /api/metrics` (see Metrics), `GET /api/options`, `GET /api/alerts` (see below), `GET /api/cash`, `GET /api/cash/cached` (the same panel from the cache as it is, never starting an Airwallex read, for the MCP server), `GET /api/board` (see Incident board), `GET /api/suppliers` and `GET /api/suppliers/:key` (see Supplier view), `GET /api/incidents`, `GET /api/incidents/:id`, `GET /api/incidents/:id/audit` (JSON, or CSV with `?format=csv`), `POST /api/incidents` (takes `bankOutcome`, `emails`, `scenario`, `startedBy`, an optional `invoiceId`, refused with 409 when it is already in the ledger or on a pay row of the waiting run, and an optional `dueDate` string, refused with 400 when it is not a string or `dueDateProblem` finds a problem; 202 `{ invoiceId }`), `POST /api/incidents/:id/approve` (needs `approver` and `approvalId`), `POST /api/incidents/:id/close` (needs `closedBy` and `finding`, and `covered`, the transfer ids of the close card's mismatched transfers, while any is on file), `POST /api/incidents/:id/resume`, `POST /api/incidents/:id/why` (see Ask why), `POST /api/incidents/:id/pay-again`, `GET /api/incidents/:id/bank-details`, `POST /api/incidents/:id/bank-change` (takes `calledBy`, `numberCalled`, `calledAt`, `spokeTo`, `confirmed` and `details`), `GET /api/runs`, `POST /api/runs` (takes `fileName`, `csv` and `uploadedBy`; 201 `{ runId }`, 400 with `problems` for a file it cannot read, 409 with `runId` while a run waits or for the same file, 422 with `rows` when every row is skipped, 408 when the body takes more than 30 seconds to arrive, 413 "The file is too large. A pay run file can be at most 40,000 characters" for a body over 256 KB (`MAX_RUN_BODY_BYTES`), 502 when Airwallex could not be read), `GET /api/runs/:id`, `GET /api/runs/:id/audit` (JSON, or CSV with `?format=csv`), `POST /api/runs/:id/approve` (needs `approver` and `approvalId`), `POST /api/runs/:id/check` and `POST /api/runs/:id/cancel` (needs `cancelledBy` and `note`), `GET /api/outages` (`outagesReport`: `rule`, `enders`, `endRefused`, `active` oldest first and `recent` ended newest first, at most 20, each an `OutageView` with PayOnce's own `text`; ledger only; the page reads `enders` from it for both end forms, and the board's slot takes its outages from `GET /api/board`) and `POST /api/outages/:id/end` (needs `endedBy` and `note`; 400, 403 for a name not in `APPROVERS`, 404, or 409 with `endedBy` and `endedAt`; 200 `{ ok, invoices, runs }`). Every JSON route but `POST /api/runs` and `POST /api/inbox` takes a body of up to 64 KB. `HttpError` takes an `extra` object merged into the error JSON, and `headers` for the response, such as `Retry-After`. An incident's detail carries `outage`, the active outage on its rail as an `OutageView`, or null, and `GET /api/options` carries `outageEnders` (null when any named person may end one).
- The page shows an "Outages" card above the cash panel for each active outage and each ended in the last day (on the board, the active ones move to the board's slot): the rail, its sentence, the codes, the payouts counted and what it holds, with links (for an active one the board's list, for an ended one the hold rows), and for an active one the end form (an approver picker, or a name field with no approver list, and a note) with "End outage on USD LOCAL". The approval card says when an outage on its rail is active: on an open request, that an approval waits until a person ends it and when it stops counting; on an expired request, only that an approval of the next request waits too. The cash panel has a "Waiting on an outage" row. A time to the minute on the page (`minuteText`) carries its day when it is not today. Text nodes only.
- Inbox routes: `POST /api/inbox` (takes `uploadedBy`, `source` `file` or `paste`, `fileName` and `eml`, the bytes in strict base64; `readJson` is given a 3 MB limit for this route only; 201 `{ id, candidates, suggested }`, 400 an email PayOnce cannot read, 413 over 2 MB, with the parser's words also for a body over the route's 3 MB limit, 503 while four uploads wait to be parsed, 408 when the body takes more than 30 seconds to arrive, 409 `{ id, state, invoiceId }` for one already uploaded), `GET /api/inbox` (waiting uploads, then the latest 50 others, with no matching), `GET /api/inbox/:id` (the upload, notes in words, candidates, `sameMessageId`), `POST /api/inbox/:id/deliver` (`invoiceId`, `deliveredBy`; in the invoice's turn, then a wake for an open or escalated invoice) and `POST /api/inbox/:id/dismiss` (`dismissedBy`, `note`). An incident's emails carry `uploadId`, `uploadedBy`, `replyTo`, `styleText`, `attachments`, `notes` in words and `partial`. `GET /api/options` adds `maxEmailBytes`, `reader` and `readerIsModel`. Static files are served with a Content-Security-Policy and every response with `nosniff`.
- Outbox routes: `POST /api/incidents/:id/outbox` takes `template` and `createdBy`: 201 `{ draftId }`, 400 for a template PayOnce does not offer or no name, 409 with `draftId` while a draft of that template is open, 422 when the template does not fit the invoice now. `POST /api/incidents/:id/outbox/:draftId/copied` (optional `copiedBy`), `.../sent` (needs `sentBy`) and `.../dismiss` (needs `dismissedBy`, optional `note` up to 200 characters) answer 404 for a draft of another invoice and 409 for one already sent or dismissed. All run in the invoice's turn. Any other error in these steps answers 500. An incident's detail carries `outbox: { drafts, offers, notOffered, withheld }`, and the list's `headline` never takes an outbox line.
- The page has a "Supplier email" card (file or paste, a name, the free-tier notice), an "Inbox" list and `#inbox/N`, which shows the upload, a match card (candidates, another invoice, a name) and a dismiss card. Email text only ever reaches text nodes.
- The CSV travels as a string inside JSON, so the guard covers an upload and nothing parses multipart. The upload waits for the checks, a few Airwallex GETs. A run's id is `^[1-9][0-9]{0,9}$`. Every step on a run (approve, check, cancel, release) runs in `runKey(id)`'s turn. An approval that completes the request starts the release in that key's turn without awaiting it.
- A run's detail has the run, `status` (`waiting-approval`, `approved`, `expired`, `needs-check`, `released`, `cancelled`), `counts`, the rows with each released row's invoice (state, attempts, `busy`, `watching`) and, for a pay row, `feeSeen` from `feeSeenText` and `arrivalAdvice`, the last check's cash, the approval in an incident's shape plus `largest`, `domains` (each row's domain check, from `domainChecks`) and `arrivalAdvice` (line, invoice and advice for each row whose terms carry an estimate), `outage`, the first active outage on a pay row's rail while the run waits (an `OutageView`, or null), which the run approval card names because the run is released whole, the events, `busy` (the run's key or any of its invoices) and `watching`. An incident's detail has `run: { id, line }` or null, and its approval has `arrivalAdvice` when the terms carry an estimate. The list carries `runId`. `GET /api/options` adds `runColumns`, `sandboxOutcomes`, `maxRunRows` and `maxRunFileChars`.
- The page routes `#run/7` to a run. The sidebar has a "Pay run" form (file input, read with `file.text()`, and the stored name, kept in step with the incident form's name) and a "Pay runs" list. The run view has a rows card, the run's timeline with its audit line and downloads, the approval card (the approver picker checks limits against the largest total, and a "Cannot approve" row names everyone barred, the uploader included when not on the approver list), the cash card from the last check, a cancel card while it waits and "Check again" in the header. An incident from a run links back to it. The "New payee" and callback tags show only on a row that pays.
- `GET /api/incidents` reads the ledger a few times in all, never once per closed invoice: `Ledger.headlines()`, `runIdsByInvoice()`, `attemptsMaybeWithBank()` tested with `withBank`, `invoicesWithPayoutInFlight()` (a payout in any state that is not final, the test an incident's `watching` makes), and one `boardGroups`, which reads each open invoice a few times, as the board does. An invoice's `headline` is the board's fixed `why` while the invoice is on the board, and otherwise its latest decision, closed or standing line (a topic other than `outbox:N`), never an error, email or outbox line.
- An incident's detail carries `audit`: the number of lines, and `problem`, the first break in the chain or a running hash that is missing or does not match, null when there is none. It reads the invoice's chain with `Ledger.chainedEvents(invoiceId)` and the running hash with `Ledger.runningHashCheck()`. The page shows it under the timeline with links to the export. It carries `review` when a person can close it, and the page shows the close card from that. `busy` is true while the agent or the sandbox bank is working on it, and `watching` while a payment is with the bank, including an outside payout tied to it. The page polls every 1.5 seconds while either is true.
- Approve and close wait for any step already running on the invoice, then run. Resume queues a look.
- `GET /api/cash` answers at once from `BalanceCache` and the ledger. It starts one balance read when the last try, good or failed, is 30 seconds old, so a page that stays open reads the balance at most twice a minute and a closed one reads nothing, unless alerts are on (see Alerts). The server reads once at start. After each good read it runs `recordMissingFees`, so while failed transfers have no fee one refresh makes up to six reads: the balance and five transfers. Because it answers before the read it starts, the first answer after nobody asked for a while carries a read older than 30 seconds, with `refreshing` true. `refreshing` covers only the balance read, not the `recordMissingFees` run after it, though no new read starts before that run ends. The page says it is reading the balances again and polls every 1.5 seconds until the balance read lands. A failed read keeps the last good one, and the answer carries the error, the read's age and `statesCheckedAt` from the watcher. Headroom is null when the balance was never read, Airwallex has no balance in that currency, or `RESERVE_FLOORS` is unreadable. `payRuns` is `{ built: true }`, and a `pay-run` line carries its `runId`; the page links a row not released yet to its run.
- A currency is listed when it has a floor set, a line in the ledger, an invoice floor or a balance that is not zero. The page shows the cash panel, one row per currency, with the Outages card above it. Both sit above the board, reconciliation and metrics, and below an incident, a pay run, an email or a supplier record, so that view's header is on the first screen (`placePanels`). Under 900px wide the sidebar follows the main view (`.sidebar` `order: 1`) and both panels follow every view, so a phone opens on what was picked. A currency is open by default when money in it is promised or waiting on a person, or a headroom is below 0. A person's click is kept in `localStorage` under `payonce.cashOpen`. The panel is redrawn only when the figures change, and the ages are set on their own nodes on every poll.
- The page scrolls to keep the newest timeline line on screen when that line was already visible, and for 15 seconds after an action. Picking another view, from the top bar, a list, a board entry or a link, scrolls to the top first (`select`), and a top-bar button does so even when its view is already open. Picking an incident also scrolls the sidebar to it in the list once the list shows it, except after a start from the form, which leaves the sidebar where it is so the form stays on screen.
- While the latest request is requested or approved, an expired one included since the next look opens a new one, the approval card sits right after the why card, above the close and callback cards (`placeApproval`, which moves only the approval card's node, so focus elsewhere is kept). When it is void or used, the card follows the callback card, as with no request. At 1180px and narrower the three share `order: -1` above the timeline, in the same order.
- `parseDate` in `web/app.js` gives null for anything that is not a non-empty string, because `new Date(null)` is 1970. A time from another day shows its day: under the time in the timeline, and as "Oct 28, 09:34:12" elsewhere (`stampText`). A timeline line is redrawn only when `eventSignature` changes, and whether its time is today is part of that, so after midnight the next poll gives yesterday's lines their day.
- On start it wakes every invoice not closed with a payment the ledger has with the bank (`withBank`, a transfer the ledger keeps failed while the bank has it live included), or a payout sent outside PayOnce that is not paid or failed. The sandbox bank goes back to paying any replacement still in flight, an original in flight that was paid on an approval after a hold, and a pay run row's original in flight, which gets the row's `sandbox_outcome`. It reads that from the approval the attempt was opened on (`approvalOf`), not from the invoice's latest request.
- The watcher sweeps every 30 seconds. A paid, failed, cancelled or overdue webhook for a transfer the ledger does not know, or for an attempt marked failed with no transfer, asks for a sweep on the next check. One for an outside payout already tied to an invoice wakes that invoice.
- `GET /api/options` lists the default email thread first, so the form opens on the incident that is replaced without a person. It also lists the approvers and the approval policy, and an incident's approval carries its signoffs, `needed`, `expiresAt` and who is barred, so the page can offer only the names that may approve. Both approval cards list everyone barred, with why, in a "Cannot approve" row, so a barred person who is not on the approver list is named too. It carries `alerts` (`on`, `format`, `host`, `test`, `problem`, `stopped`), never the address. `GET /api/alerts` adds `recent`, the last 50 alerts with their key, kind, title, state, tries and last error.
- When `terms.fx` is set, the approval card adds what the payment takes from the source wallet, an "Exchange rate" row (the rate as Airwallex quotes the pair, the markup over mid-market, the quote id and when it runs out) and a "Transfer fee" row, and the page compares limits with `fx.sellAmountMinor`. The header says "Paid from USD" when `obligation.sourceCurrency` differs from `currency`.
- The start form has an optional "Due date" date input. The header shows the due date and flags one that has passed by the browser's date. When `terms.arrival` is set, the approval card has an "Arrival" row: the route, its usual days and the latest day, the due date in amber when the payment is at risk, and the public holidays note. The run rows card shows each pay row's estimate and the fee last seen, and the run approval card lists the estimate of every row whose terms carry one. When an estimate counts from a day before today, the cards and the rows card add when it usually arrives if sent today: the cards only for a request that is requested or approved and has not expired, and the rows card only while the run waits (`adviceFor` in `server.ts`, and `adviceOf` in `mcp-views.ts` by the same rule). The page shows the server's `arrivalAdvice` and keeps no copy of the rules or the wording.

Checked on 2026-11-02 on a copy of a reviewer ledger seeded with 5,000 settled invoices and 60,000 chained lines, server on port 4344 with webhooks off: `GET /api/incidents` went from a median of 1,153 ms to 83 ms, and an incident detail from 100 ms to 16 ms (median of 10 each).

Checked on 2026-11-03 in headless Chrome, server on port 4388 with Airwallex at `sandbox.invalid`, on a ledger copy with legacy names holding U+202E and U+200B (who started two incidents, an approval and its signoffs, a callback, two uploads, two drafts, a cancelled run, an ended outage and an explained break): no header or card held a format character, where before the incident, outbox, inbox, run and outage cards did. With 400 ms added to every request, going from reconciliation, an email or a run to an incident, or from reconciliation to an email or a run, left the main area empty for about 270 ms before and never after. Before, an upload refused with no email id read "falsefalse" after its message, and now nothing follows it.

Checked again in review on 2026-11-03 in headless Chrome, server on port 4392 with Airwallex at `sandbox.invalid`: with 400 ms added to every request, each of the 30 moves between the board, an incident, a pay run, an email, a supplier record and reconciliation showed exactly one view in every 10 ms sample, never a blank main area, and ended on the view picked. Picking a third view 100 ms after a second never showed the second, whichever of their answers was slower. Typed notes and an email's display name held U+202E or U+200B on the outbox, run, inbox, outage and reconciliation cards before the fix and none after.
