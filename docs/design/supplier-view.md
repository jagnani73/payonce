# Supplier view

This is one of PayOnce's design notes. [CLAUDE.md](../../CLAUDE.md) has the commands, the file map, the rules that hold everywhere and the index of these notes. Where the two differ, this file is right.

- A supplier is one Airwallex beneficiary record: `obligations.beneficiary_id`, and `run_rows.beneficiary_id` for a pay row of the waiting run that no invoice holds yet. A skip row never makes a record, since its id may be one Airwallex does not have. The key in every route, link and command is the id, checked against `SUPPLIER_KEY_PATTERN` (`BENEFICIARY_ID_PATTERN` from `run-file.ts`). Every control keys on the record (`lastPaidTransfer`, `verifiedBankChange`, `payeeRule`, the run check), so the page shows what the next payment is checked against. Records are never merged. Records that share a name (`sameSupplier`, through `supplierNameKey`) or an account (an account key on file under both, or a `rail_failures.payee` both failed to) are linked, for display only. An empty name, and `UNNAMED_PAYEE`, the name the sweep gives a found payout with no account name, never link records. A stored id outside the pattern is listed with `key: null` and no link.
- `supplierList` and `supplierDetail` each read the ledger once, inside `Ledger.readSnapshot`. The list reads every record with `Ledger.supplierListRead`: only the columns its cautions, counts and names use from invoices (`SupplierObligation`), attempts (`SupplierAttempt`) and payouts sent outside PayOnce, no drafts or outage holds, and approvals with only the account their terms name, so each terms JSON is parsed once. It builds the links between records from that same read (`linksOf`). The detail reads its record with `Ledger.supplierRead(key)` (the invoices in full, what the page shows of each payment as `SupplierPayment`, with the route advisory's JSON parsed only for what paid a listed invoice, its drafts and holds) and the other records' names and accounts with `Ledger.supplierLinks(key)`, which leaves out that record's own approvals, read already. It reads an approval's account only inside `CASE WHEN json_valid(terms)`, as `metricsRead` reads `duplicate_of`, because SQLite promises no order for the two sides of an AND and `json_type` throws on text that is not JSON. Neither puts in its answer an email's or an upload's subject, body or display name, a draft's subject, body, facts or dismiss note, a callback's `spoke_to`, `confirmed` or `new_details`, a timeline line, an escalation reason or a skip reason. Both still read some of them. The list's read takes `escalation_reason` and the detail's takes whole invoice rows, and the reason is only tested with `startsWith` against exported constants. The detail's inbox and `boardEntriesFor` read waiting uploads in full, but only for `candidatesFor`. The board also reads each open invoice's first timeline line, only for its time, and the waiting run's rows in full. Both work on a read-only ledger. `Ledger.supplierNamed` says whether an invoice or a waiting pay row names a record, for `resolveSupplier`.
- Money and groups are the board's own, built by `boardEntriesFor` for the invoices that need them, each entry as the whole board has it: the list for every invoice that is not closed (`Ledger.openObligations`) and every pay row of the waiting run, summed per record, and the detail for its own invoices and pay rows, with their totals. Neither builds entries when its records have no open invoice and no waiting run row. The detail's waiting uploads and the board's use one invoice index.
- Accounts are named by where the money goes: each key `attempts.account_key`, approval terms and `run_rows.account_key` carry is read as its routeKey where the ledger keeps one (`Ledger.accountRoutes`, applied in the supplier reads), else as it is, and labelled A, B, C in the order first seen, so a bank name Airwallex rewrote makes no new account. Sources: decided for (`account_key`, `opened_at`), sent to (`sent_key`), asked to approve (the terms' `accountKey`), pay run (a pay row's `account_key`, `checked_at`), verified by a callback (the routeKey of `applied_key`), on the record before a callback (`routeKeyOf` the callback's `old_details`) and paid outside PayOnce (a payout's `sent_key`). The page and the CLI never print the key; the JSON carries it as `accountKey`. An ending comes only from `sent_ending` and the callback JSON, as 1 to 4 letters and digits. A payment's account is its `sent_key`, else its `account_key` when it has a transfer and is not misdirected. Its check is `checked`, `misdirected`, `not-kept` (no `account_key`), `not-sent` (no transfer) or `outside`.
- The account PayOnce last paid is `ledger.lastPaidTransfer`'s, never a copy of the rule. What PayOnce last stored is the newest key among decided, asked to approve, pay run and callback, and the header says the record is read again before every payment, naming the invoice it was stored on, or a pay run row as "row N of pay run M" (`runLine`), since the row's number may not be an invoice yet. The latest applied callback is the one `verifiedBankChange` reads, the newest applied whatever it kept. `verifiedBy` is that callback when its key is this account's. Each account reads only its own payments, payouts, callbacks and failures, grouped once per record. `barred` is `bankChangeRecorders` for each applied callback with this key, through `knownName`, as `barredFrom` reads it.
- Cautions are `{ code, level, text, invoices, accounts, keys, runs, since }`. `text` is fixed words that may hold account labels, counts, failure codes' words (`wordsFor`: only a code in `FAILURE_CODE`'s form that is the table's own entry, so `constructor` gets none) or a rail in its own form, and in `callback-verified` the account's ending (1 to 4 letters and digits) and when the callback was recorded, to the minute in UTC. Invoice numbers (25 at most), account labels and other record ids (`keys`) go in the arrays. No caution carries a name, a domain or a reference, and none fills `runs`. In order, cautions before infos:
  - `account-changed` follows the engine's tests. It shows, with that account's label, when `lastPaidTransfer` gives an account, the account PayOnce last stored is not that one, and the latest applied callback did not verify it (the `verifiedBankChange` test). It also shows, with those invoices and whatever the callbacks, whenever an open invoice's reason starts with `CHANGED_BANK_DETAILS_REASON`, `LAST_PAID_CHANGED_REASON`, `ACCOUNT_CHANGED_REASON` or `RUN_ACCOUNT_CHANGED_REASON` (a pay run row whose record changed after the run was approved). Its text has a part for each case. The first speaks only of first payments and pay run rows: PayOnce sends no first payment to those details, and skips a pay run row to them, before a callback. That rule does not hold a replacement whose original went to them, such as the replacement of a payout sent outside PayOnce.
  - `callback-verified`: the latest applied callback verified the account PayOnce last stored, and it is not the account `lastPaidTransfer` gives. It says when the callback was recorded and which account (label and ending), that paying a held invoice or a pay run row to it needs two approvers (`payeeRule`, `runRule`), and that nobody who recorded a callback for it may approve. It says nothing about automatic payments, and reads with `new-payee`, which says the same about two approvers.
  - Then `new-payee` (never paid, or paid only by itself and never on a person's approval), `unconfirmed-account`, `misdirected`, `shared-account`, `account-failure` (90701, 90101 or 90802 on the last paid or last stored account in the last 30 days), `domain-changed`, `asks-not-to-pay` and `asks-new-details` (open invoices only), `paid-twice` (`LATE_TRANSFER_REASON`), `no-phone` (escalated invoices with no phone on file, since a callback is recorded on the escalated invoice from its own phone), `recent-failures` (by `bank_created_at`, else `opened_at`; a failed attempt the bank still has live is not one), `non-receipt`, `flagged-senders`, `no-domain`, `outside-payout`, `held-duplicate` and `outage` (an active outage on an open invoice's rail).
  - "Recent" is a 30-day constant. The list carries the codes of level `caution`.
- The detail lists every open invoice, then the 25 newest closed, with counts per state. Per invoice: the board's group, label, `why` and `also`, money at risk, what paid it (with the route advisory's latest usual day; a payout sent outside PayOnce counts only if `payoutPays` says it pays the invoice), each attempt and outside payout (reference only as `^[A-Z0-9-]{1,30}$`, status only as `^[A-Z_]{1,30}$`, a failure code and its words, a rate mismatch only as true or false), and the emails as counts with `summarise` of the three findings and `readBy`, never the stored summary. Also callbacks (who called, the number's last four digits, from and to account), likely duplicates across this record and same-name records (bucketed on `numberOf(...).base`, "same bill" when amount and currency match too), outage holds (a run's hold on the record of each row the run released, by the invoice it became, and while the run waits on its pay rows' records; never on a skip row or a dropped row), rail failures and active outages, pay run rows (skip reasons only as a count), waiting uploads that name its invoices (one `invoiceIndex`), and drafts by template label, audience, state and who moved them.
- The list puts a record with an entry waiting on a person first, then one with a must-tier caution, then the most money at risk, then the name and the key.
- `GET /api/suppliers` and `GET /api/suppliers/:key` are GETs behind `guard`, write nothing and so skip the Dispatcher. An unknown key, or one outside the pattern, answers 404 "No invoice or pay run row in the ledger names supplier record X", X cut to 20 characters.
- The page: a Suppliers list in the sidebar and `#supplier/<key>` (`supplierKeyOf`), shown first in the main area, above the Outages card and the cash panel, with cards in this order: cautions, money at risk now, accounts, invoices, bank details callbacks, supplier emails, messages, likely duplicates, outages, pay runs. A card with nothing to show is hidden, except money at risk and accounts, which say there is none. The incident header's supplier, the approval card's beneficiary id, a paying run row's payee and each board entry's supplier link to the record; the board entry's supplier sits below the entry's own link, since one link cannot hold another. The list is fetched only while the sidebar's Suppliers section is on screen (an `IntersectionObserver`), on every refresh as the incident list is, and at once when the section comes into view. The record is fetched at most once every idle poll (5 seconds), only while it is on screen. Each is drawn again only when its JSON changes. A time in a sentence reads "at 17:31 GMT+5:30" today and "on Oct 28, 21:33 GMT+5:30" on another day (`whenNode`), and "Since" takes the time alone. A payment with no transfer says it was not sent, with no account or send time. A supplier record, and any view after one, stays on screen until the next view or its placeholder can be shown. So do reconciliation, an email, a pay run and an incident: `renderOtherSelected` renders the view picked first and hides the others only once it or its placeholder is shown. Outside text goes through `whyText` into text nodes.
- Everywhere on the page, Airwallex names and PayOnce lines that quote them go through `whyText` before they reach a text node, as on the ask-why card: format characters and the tag block dropped, controls as spaces. That covers the incident list's supplier and headline, every timeline line, the approval card's pay-to line, a pay run row's payee and its skip reasons and notes, an inbox candidate's supplier, and the values "On file now" on the callback form. Names a person types are refused at input (see Names), and a name stored before that rule can still hold format characters, so every stored person name the page shows goes through `whyText` too, and so do the notes people type and the sender names in emails: who started an incident, approvers and signoffs, who called on a callback and who they spoke to, draft creators and movers, uploaders, who delivered or dismissed an email, who cancelled a run, who ended an outage (and the outage sentence that names them) and who explained a break. The notes are a draft's dismiss note, a run's cancel note, an upload's dismiss note, an outage's end note, a break's explanation note and what a callback confirmed. For an email, that is the display name, on the incident's email card and in the inbox view, and the From line as written, in the inbox view. Email subjects and bodies are shown as stored. `api` cleans a server refusal the same way, since one can quote a stored name, such as the duplicate upload error naming who delivered the email. `h` drops a `false` or `null` child, but `replaceChildren`, `append` and the other DOM child methods write it as text, so a part that is not shown goes to them as an empty spread list.
- `pnpm supplier` prints the list, or one record's sections in nearly the page's order, with the inbox and messages last and the emails under each invoice (a word is a record id first, then an invoice number, which prints "INV pays supplier record X" first). Names, domains, typed names and references go through `printable`, the phone as `…` and its last four digits, and times in UTC. An account's line gives its facts, then "PayOnce:" and "outside PayOnce:" counts, separated by semicolons; a payment gives its state, then "bank status", and one with no transfer says "not sent" with no account or send time; a draft names who created, copied, marked sent or dismissed it; a pay run row says "pays" or "skipped for N reasons", then "row" and its state.
- MCP: `suppliers` and `supplier` (`{ key }`, a record id or an invoice number) through `answer`. Plain paths: `cautions[].text`, `invoices[].board.(label|why|also[])` and `invoices[].emails.findings.summary`. `name`, `names[]`, `suppliers[].name`, `related[].name` and `domains[].domain` wrap as `supplier`, an `ending` wraps as `airwallex` unless it is 1 to 4 letters and digits, `failureWords` and `codeWords` wrap unless they are exactly PayOnce's words for a code, and `barred[]` wraps as `person`.

Checked on 2026-11-03, with no Airwallex call and no transfer:

- On a fresh ledger seeded with one record per case (a callback verified and its recorder barred, a record changed with no callback, two records sharing an account key and two sharing only a failing payee, two with one name, a new payee, a payment from before accounts were kept, a misdirected transfer, a 90701 failure 2 days old and one 40 days old, two domains, the asks on an open invoice and on a settled one, a late transfer, a waiting run row with no invoice and a skip row, an outage hold, INV-0042 with INV-42A and RENT-2026-OCT with RENT-2026-NOV, a live outside payout and a found payout, 30 closed invoices) and hostile text in every source field: each of the 23 records gave exactly its expected cautions, `lastPaid` matched `lastPaidTransfer`, money summed over the records equalled the board's totals, and each open invoice had the board's group. No answer held an email, draft, upload, run cell, callback note, payTo, escalation reason, skip reason, timeline line or the phone or account digits beyond their last four. The builders ran on a read-only ledger.
- `pnpm supplier` printed every record's cautions and invoices with no control or format character and left the file byte for byte the same. The MCP tools, over stdio with only JSON-RPC on stdout, equalled the routes on the same file for all 25 answers, with every seeded string wrapped and the caution text plain. In headless Chrome, a name holding `<img src=x onerror=alert(1)>`, U+202E and U+200B showed as text with neither control, the view held no `img` or `script`, every link landed on the right record, an unknown key showed the 404's words, moving between the board, an incident, an upload and a supplier never left the main area blank, the list was fetched 3 times in 21 seconds while an incident polled every 1.5, and the page had no horizontal scroll at 390 px.
- On a copy of the 5,000-invoice seed, median of 10, built directly: the list took 51 ms with one record holding all 5,000 and 56 ms spread over 50 records, the detail 20 ms for a 2-invoice record and 64 ms for the 5,000-invoice one, against 66 to 70 ms for the incident list's work. Through the server, with its watcher retrying the escalated invoices against an unreachable Airwallex: `GET /api/incidents` 92 to 94 ms, `GET /api/suppliers` 68 to 73 ms, a 2-invoice record 38 to 39 ms and the 5,000-invoice record 86 to 99 ms.
- The default demo through `runScenario`, with Airwallex stubbed, gave the same timeline, decisions and posts as 09de207, and kept each attempt's `sent_key` equal to its `account_key`. `pnpm dev` printed the same 7 decision lines, and the one open approval on a copy of the main ledger bound the same under both.
