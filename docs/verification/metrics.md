# Metrics: dated checks

How the rules in [design/metrics.md](../design/metrics.md) were checked, as written at the time. Only paths have been updated to the current layout, so a note may describe behaviour that has changed since.

## 2026-11-03: the figures, the triggers and the page on ledger copies

Checked on 2026-11-03 on ledger copies in the session scratchpad, with no Airwallex call:

- A copy of the real-run ledger seeded with 22 cases (an automatic replacement, a replacement approved after a deadline, duplicates stopped and paid, a request renewed three times, two approvers, an approval voided after signing, paid twice, SWIFT fees kept and not read, a refused create, a never-created attempt, six outages, explained, cleared, pending and unknown breaks, a reopened close, payments exactly at the 7-day edge and a millisecond before it, missing times, a pay run, a payment from another wallet, an unreadable currency, an old reason, a kept transfer and a paid mismatched one): hand-written SQL gave the same figures as `metricsOf` in all three periods at a fixed now.
- On copies of the main ledger and the 5,000-invoice seed, fees lost since the start equalled the cash panel's `fee-lost` lines, started invoices added up to the invoice count, closed ones to settled plus rejected, and every escalation reason had a code (10 and 19 reasons, none `other`).
- The triggers, through the Ledger's own methods inside `BEGIN IMMEDIATE` while a second process held read transactions: 33 checks of `escalate`, `rewordEscalation`, `escalateIfOpen`, `holdBeforePaying`, `escalateUnlessSettled`, `reject`, `openAttempt`, `record` (failed, failed again, revived, paid, and the retry that keeps a state to hold the duplicate lock), `failAttempt`, a late transfer, `adoptPayout` and `settle`. Each time was set once, at the change, and never moved, and no statement failed. Main's code on a file this code had upgraded ran the default demo the same and the triggers stamped its attempts. Two processes opening a copy of the main ledger at once added the columns and the five triggers once.
- The default demo through `runScenario` with Airwallex stubbed wrote the same rows as main's code, apart from the new columns. A look on the main ledger's one open approval (INV-362408) under main's code and this code opened the same request with the same binding.
- `metricsReport` on the 5,000-invoice seed took 45 ms warm in one process (42.6 ms of it the read). Through the server, an answer built after another connection's commit took a median of 67.5 ms (at most 140 ms), and a cached one about 15 ms, the same as any small route on this machine.
- With hostile text in every text column the metrics read or sit next to, on a copy of `verify/db/evil`, no seeded string reached the route, `pnpm metrics` text or JSON, the MCP answer or the metrics view's DOM, and the MCP answer held no `outsideText`. The route, the CLI's JSON and the MCP tool gave the same answer. `pnpm metrics` and the MCP tool left the file's hash unchanged. Its `duplicate_of` held valid JSON, so it missed the throw on one that is not JSON (see below). Amounts, fees, counts and the signoffs needed are read as SQLite returns them, and PayOnce writes only integers there.
- The page in headless Chrome over the DevTools protocol: no console error or CSP report on the seeded copy, no horizontal scroll at 360 px with `APPROVERS` set, period buttons switch with no reload, and `#%6Detrics` opens the invoice called metrics.

## 2026-11-03: after a cold review and a verifier

Checked again on 2026-11-03 after a cold review and a verifier, on ledger copies in the session scratchpad, with no Airwallex call:

- A `duplicate_of` that is not JSON made every period throw "malformed JSON" before. All three answer now.
- Paid more than once on a seeded copy with a paid late transfer, outside payouts with and without an amount (EUR and GBP), a paid mismatched EUR transfer on a USD invoice, and two EUR invoices paid from USD, one whose approval names the extra payment's quote and one whose does not. Before: 1,400,000 EUR over 3 invoices and 160,000 USD over 2. Now: 4 invoices, extra 1,500.00 GBP in 1 payment and 5,377.00 USD in 2, 2 not known, and the mismatched 640.00 EUR on its own line. Hand-written SQL gave the same.
- On a copy of the main ledger, whose 8 closed invoices predate the time columns, the incidents note said 12 before and 8 now, as hand-written SQL does.
- With `/api/metrics` failing, the page asked 26 times in 40 seconds before and twice now, at 0 and 31 seconds. A 30d error arriving after the person switched to all showed against all before, and is dropped now.
- A stubbed 400 with no code on the first send counted as never created before and as refused now. The timeline lines are the same.
- A held duplicate released and paying counted as still held before, and as approved and paying now. An invoice paid the first time whose original was marked failed and then found late had a time from the first failure (200 s) before, and none now.
- At 360px the top bar was 129px and stuck to the top. It is static now and scrolls away. With no `APPROVERS`, the approval card's caution pushed the page to 372px. Every view at 360, 400, 480, 560, 561, 600, 760 and 1280px now has no sideways scroll and no console error.
- 17 stored JSON columns on the board, outage and incident list paths, each made not JSON on its own on a seeded copy: before, 15 of them made all three views throw, approval terms only on an open request, and the run's cash and run approval terms none. Now none does. Through the server, outage codes that are not JSON answered 500 on the three routes before and 200 now. What PayOnce writes reads as before: the three views were byte-identical to main's on copies of the main ledger and a seeded one.
- The verifier's hand-written SQL matched every figure on the seeded, main, 5,000-invoice and real-run copies. `pnpm dev` printed the same 7 decisions as main, and the default demo against a stub wrote the same rows as main apart from the new columns.
