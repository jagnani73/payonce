# PayOnce

Payment incident agent for the Airwallex Agentic Banking Hackathon 2026, built on starter kit 3. TypeScript, pnpm, Node 24. Sandbox only.

## Commands

```bash
pnpm install
pnpm typecheck                                      # tsc --noEmit
pnpm dev                                            # policy on seven sample incidents, no credentials
pnpm ui                                             # web page and JSON API at http://127.0.0.1:4310, webhook receiver on 4311
pnpm recover [OUTCOME] [INVOICE] [EMAILS] [SCENARIO] [NAME] # one incident against the sandbox, or continue an existing invoice (status checks, no webhooks)
pnpm approve <INVOICE> [REQUEST NAME]               # show the waiting approval (a replacement, or paying a held invoice), its request number and the policy; with both, record that person's approval of that request
pnpm close <INVOICE> [NAME] [NOTE] [--covers=REF,...] # show a paid incident or a held invoice waiting on a person; with NAME and NOTE, close it (a held invoice without paying); --covers names every mismatched transfer the close covers
pnpm run audit [INVOICE] [json|csv]                 # check every invoice and pay run timeline, reconciliation's chain and their three running hashes, or one invoice's; with a format, print its audit trail
pnpm run audit run <RUN> [json|csv]                 # the same for one pay run's timeline
pnpm cash                                           # read balances once and print each currency down to the headroom above its floor; exit 1 if Airwallex is unreadable, a floor is unreadable or a headroom is below 0
pnpm board [FILTER...]                              # the incident board from the ledger alone, active outages first; filters in any order: a group (person, deadline, bank, open), a currency, an origin (payonce, outside, pay-run)
pnpm payrun upload <FILE> <NAME>                    # check a pay run CSV (Airwallex GETs only) and store it as a run waiting for approval; NAME is required
pnpm payrun show <RUN>                              # rows, cash, the waiting request, its number and who is barred
pnpm payrun approve <RUN> [REQUEST NAME]            # show the terms; with both, record that approval. pnpm ui releases the run
pnpm payrun check <RUN>                             # run every check again (GETs only) and open a new request if the old one expired or the terms changed
pnpm payrun cancel <RUN> <NAME> <NOTE>              # cancel a run that is waiting
pnpm outbox <INVOICE>                               # message drafts on file and the messages that fit now, suggested first
pnpm outbox <INVOICE> draft <TEMPLATE> <NAME>       # draft a message for a person to send and print it; PayOnce never sends it
pnpm outbox <INVOICE> show <DRAFT>                  # print a draft, whether its text still matches its hash, and what changed since
pnpm outbox <INVOICE> sent <DRAFT> <NAME>           # record that you sent it yourself
pnpm outbox <INVOICE> dismiss <DRAFT> <NAME> [NOTE]
pnpm outage                                         # the active rail outages and the last five ended, ledger only
pnpm outage end <ID> <NAME> <NOTE>                  # end an outage as a name in APPROVERS (any name when APPROVERS is unset; nobody while an approval setting cannot be read)
pnpm supplier [RECORD|INVOICE]                      # every supplier record, or one Airwallex beneficiary record (an invoice number gives the record it pays), ledger only
pnpm reconcile [offline]                            # one reconciliation check against Airwallex (GETs only), or the stored record matched again with no call, then the report; exit 1 when it failed, a wallet does not add up, does not end at Airwallex's balance or has a movement PayOnce cannot read, or a break waits on a person
pnpm reconcile show [CURRENCY]                      # the last report, ledger only, read-only
pnpm reconcile explain <ID[,ID...]> [NAME NOTE --facts=FP,...] # the breaks and their facts; with NAME, NOTE and the printed facts, explain open breaks of one kind
pnpm mcp                                            # the read-only MCP server over stdio, by hand; Claude Code and Claude Desktop start it with node (see README)
pnpm ask <INVOICE> [facts]                          # ask the model reader's models why PayOnce did what it did on the invoice; with facts, print exactly what would be sent and ask nothing
pnpm metrics [7d|30d|all] [json]                    # the ops metrics for the last 7 or 30 days or since the ledger started, ledger only, read-only; json prints the route's answer
pnpm reset                                          # move payonce.db aside so the next run starts an empty ledger
```

Defaults: OUTCOME `CHANNEL_TIMEOUT`, EMAILS `nothing-arrived`, SCENARIO `usd-local`, NAME the OS login name (who started the incident). OUTCOME is a simulator failure type, `PAID`, or `STAYS_IN_FLIGHT`, which leaves the original in `SENT`. `pnpm audit` is pnpm's own dependency audit, so the audit command needs `run`. Asking an invoice why is `pnpm ask` because pnpm runs its own `why` command, a dependency check, in place of a script named `why`. `pnpm reconcile` runs the script: pnpm 12.5.1's `pnpm help` lists no `reconcile` or `recon` command. `pnpm metrics` runs the script too: `pnpm help` lists no `metrics` command and `pnpm help metrics` answers "unrecognized subcommand". There is no lint script and there are no tests.

## Structure

- `src/decide.ts`: pure decision policy (wait / replace / escalate / close). Rules stay in code; the model never decides amounts or moves money. `floorReason` is its cash check, which the engine also runs before it spends an approval. The reasons alerts compare with are exported constants (`ORIGINAL_DEADLINE_REASON`, the three bank-details reasons, `LAST_PAID_CHANGED_REASON` among them, `OUTSIDE_PAYOUT_REASON`, `BELOW_FLOOR_REASON`, `UNREADABLE_CASH_REASON`, `NO_FLOOR_CLAUSE` and `NOT_TO_PAY_CLAUSE`), and `engine.ts` exports `REPLACEMENT_DEADLINE_REASON` and `LATE_TRANSFER_REASON`. `OUTAGE_REASON` and `NO_FLOOR_REASON` are exported too. The two reasons supplier emails escalate for, `NOT_TO_PAY_REASON` and `PARTLY_UNREAD_REASON`, are constants too. `NOT_TO_PAY_CLAUSE` is how the ask not to pay reads when it is added to another reason, and `namingNotToPay` adds it. `LAST_PAID_CHANGED_REASON` and `UNCONFIRMED_ACCOUNT_REASON` are why a first payment waits for a person because of where PayOnce last paid the supplier. Every other reason `decide` gives is an exported constant too (`UNVERIFIED_SENDER_REASON`, `REPLACE_REASON` and the rest), apart from the one that names the source currency, and the explanation's reason grammar is built from them. The strings are the ones stored before, so no binding changed.
- `src/incident.ts`: `Incident` and `Decision` types. Amounts are minor units.
- `src/money.ts`: `toMinor`, `readMinor`, `toMajor` and `formatMoney`, for two-decimal currencies only.
- `src/engine.ts`: the agent, shared by the CLI and the server. `resumeIncident` looks at an invoice: it syncs the payments, reads new emails, decides and acts. `deliver` puts a fixture thread's emails on an invoice (uploads go through `src/intake.ts`), and `noteSenders` writes the sender and Reply-To check. `startPayment` sends a new invoice's original or holds the invoice for a person; given the account key a pay run approved, it also holds the row when the record changed or the floor would be breached (`CASH_HOLD_REASON`). `startFirst` sends an open invoice's first payment from a look: a pay run row's only when the look has the run's turn (`sendRunRow`), and any other invoice's after its first send failed. `replaceUnderLock` is the automatic replacement. `AccountChangedError` is what `requireAccount` throws. `approvePayment` records an approval of a replacement or of paying a held invoice, `closeIncident` records a person closing a paid incident, or closing without paying an invoice with nothing live at the bank, such as a held duplicate or one closed before that a payment reopened, `payAgain` puts a person's second payment to the lock, `note` writes the timeline. `Bank` is the hook told about each payment sent. `linkOutsidePayout` ties a payout sent outside PayOnce to the invoice its reference names or nearly matches. `rateFor` takes a new exchange rate quote for a cross-currency payment or reuses one, and `checkRate` compares a transfer with the quote its approval named. `noteMismatchedTransfer` keeps a transfer under a failed attempt's request id that does not match the invoice beside that attempt, and `MISMATCHED_TRANSFER_REASON` is why the invoice then waits for a person, with `MISMATCHED_FAILED_REASON` in its place once the bank has failed every such transfer. The engine never simulates a bank outcome.
- `src/dispatcher.ts`: `Dispatcher` runs steps one invoice at a time. `wake` queues a look at an invoice, and a wake that arrives before a queued look has started is dropped. `wake(invoiceId, true)` gives the look the run's turn, so it may send a pay run row's first payment. A wake with the turn that finds a look already queued hands the turn to that look.
- `src/watcher.ts`: the fallback for webhooks. `Watcher` reads every transfer the ledger shows in flight, PayOnce's own and outside payouts tied to its invoices, and wakes the invoice when the bank has paid or failed one. It reads an outside payout in any state that is not final, `unknown` included, so one a look read in a status PayOnce does not know, such as OVERDUE, is read again, and an incident's `watching` counts it the same way. PayOnce's own include a transfer the ledger keeps failed while the bank has it in flight, and a transfer kept beside an attempt because it does not match the invoice. It also wakes an invoice whose next look is due and one with an approval nobody has acted on. Given an interval, it runs the sweep. `lastCheckedAt` is when the last check that read every payment with the bank without an error started. A read failure prints the first time, then at most once a minute while the same message repeats, with how many reads failed meanwhile. A check with a failed read leaves it as it was, so the panel's "payment states checked" age grows while Airwallex cannot be reached. Given `release` (only `server.ts` passes it), it releases a waiting run whose request is approved, at most once a minute per run, and wakes a released row that has not sent, with the run's turn, one per run per check, only while the run's key is not busy: the first due row of the run in file order whose invoice has no step running (`unsentRunInvoices` reads them by run and line). Without it, as in `pnpm recover`, it never touches an unsent run row.
- `src/deadlines.ts`: how long the bank has to pay or fail a transfer, by transfer method, counted from the transfer's `created_at`. `isOverdue` treats a time it cannot read as overdue.
- `src/arrival.ts`: the route advisory. `CORRIDORS` holds the usual arrival in business days by destination country, currency, method and, for a US local payment, clearing system, from Airwallex's payout network pages for the US and Germany. `arrivalFor` builds `ArrivalTerms` (method, country, route, days, the day it counts from, the earliest and latest usual day, and the due date) in one key order, `arrivalBlock` copies one, and `ifSentOn` counts one from another day. `arrivalRisk` compares it with the due date. `dueDateProblem` checks a due date, `today` is this machine's date, and `addBusinessDays` skips Saturdays and Sundays only. `arrivalText`, `sentArrivalText` and `replacementArrivalText` write it for people. `routeText` names a route with its method when the two differ, such as "LOCAL (ACH), usually 0 to 2 business days", so the advice reads the same as the fee beside it; the terms keep `route` as it was. `arrivalAdvice` is what the page and the CLI show for one, never part of the terms. `feeSeenText` gives the fee PayOnce last recorded for a currency and method. `ROUTES` lists the route names an estimate can carry.
- `src/sweep.ts`: `sweep` lists the transfers created since the ledger started and deals with the ones PayOnce did not send. It also records a transfer listed under the request id of an attempt marked failed with none (`recordLateTransfer`), and wakes the invoice of a pending attempt whose transfer it lists, so that invoice's look records it. A transfer under the request id of an attempt marked failed that does not carry the invoice's number, amount and currency goes to `noteMismatchedTransfer` in the invoice's turn, and the invoice is woken only when the transfer is first kept or its status changes. Every listed transfer then goes to `railFailureSeen`.
- `src/outages.ts`: rail outages. `RAIL_FAILURE_CODES` (91401, 91402, 99901, 99902, with PayOnce's labels), `outageRuleFromEnv` (`OUTAGE_FAILURES` 2 to 100, default 3; `OUTAGE_WINDOW_MINUTES` 1 to 1440, default 30; a value outside falls back with a `problem`), `describeOutageRule` (the start-up line), `payeeOf` (the payee key, a hash of the account fields; see Rail outages), `railFailureSeen` (records a failure and may declare, never throws), the timeline lines (`holdLine`, `waitingLine`, `runHoldLine`, `runWaitingLine`, and the declared and end lines), `outageEnders`, `endOutage` with `EndRefusedError` (`why` is `input`, `approver`, `unknown` or `ended`), and the views `outageView` and `outagesReport`. `OutageHolding` is what an active outage holds now as the board lists it (invoices with what it holds of each, runs, and `sends`, the `OutageSend`s per currency), and `HoldingOf` works one out; `incident-board.ts` gives it as `outageHolding`, so this file has no board code. `outagesReport` and `endOutage` take a `HoldingOf`, and `outageView` takes an `OutageHolding`. `sendsText` writes the sends for the CLIs. The Outages card and `pnpm outage` read `outagesReport`, and the board builds its outages from `outageView`.
- `src/duplicates.ts`: `sameSupplier` (two supplier names, compared in NFKC with format characters dropped, case and spacing aside; people's names go through `sameName`), `sameInvoiceNumber`, `sameNumberExactly` (the same number with no letters added), `likelyDuplicates` (the other invoices a new one may be a second bill for), `sameNumberForSupplier` (the other invoices to the same supplier whose number `sameInvoiceNumber` matches, for any amount or currency), `sameBillAndNumber` (the same test for two bills not in the ledger, such as two rows of a file), and `nearlyPays` and `invoiceForPayout` (the invoice a payout sent outside PayOnce is for).
- `src/sandbox-bank.ts`: `SandboxBank` plays the bank in the sandbox. It sends a new transfer to `SENT`, pays or fails it when the scenario says so, and pays every replacement. The scripted run sends its original inside `scripting`, and the bank leaves that one to the script. Any other original gets the outcome `expectOriginal` recorded in this process, else what `outcomeOf` reads from the ledger (a pay run row's `sandbox_outcome`), else is paid. It reads each sent transfer first, trying up to four times in all on a server error or a lost connection, as the simulation calls do. A transfer that converts is left alone, because the simulator refuses to move it. Before its deadline the bank reports it once: one error line on the timeline, and the error with its stack trace on the console, as `noteError` prints every error: an `AirwallexError` or `AirwallexUnreachableError` as one line, since its message says all there is and it repeats on every look while Airwallex is down, and any other error with its stack trace. `PAID_OUTCOME`, `STAYS_IN_FLIGHT` and `SANDBOX_OUTCOMES` (the page's bank outcomes and a run file's `sandbox_outcome` values) live here.
- `src/scenario.ts`: the demo payments (`SCENARIOS`), `openScenario`, `runScenario` (the scripted incident) and `untilAtRest`. A held invoice stops the script before anything is sent, and no supplier emails arrive for it. When the script's first send fails, it records the scenario's outcome with `expectOriginal`, so the bank gives it to the original that the next look sends. `eur-from-usd` is the one scenario with a `sourceCurrency`.
- `src/webhooks.ts`: `WebhookReceiver` and `verifySignature`, and a private `RefusalLog`, which prints refused requests at most once a minute.
- `src/tunnel.ts`: `openTunnel` starts a cloudflared quick tunnel and reads its address from cloudflared's output.
- `src/assess.ts`: maps an Airwallex transfer to `originalStateOf` and `resendCanFix`, compares bank details (`routeKeyOf`, `NOT_ROUTING_FIELDS`, `ROUTE_SCHEME` and `knownRoute`; see Accounts), and reads the fee the payer paid (`feeOf`) and what a transfer took from the wallet before the fee (`debitOf`). `record`, the sweep, `payoutMoney`, `rateMismatch` and `conversionText` all read the debit through `debitOf`. `RESENDABLE_FAILURE_CODES` is exported for the metrics.
- `src/ledger.ts`: SQLite tables for obligations, attempts, approvals, emails, findings and events. `isExpired` and `expiryOf` say when an approval request stops covering a payment. `readSnapshot(fn)` runs reads in one deferred `BEGIN`, on a read-only ledger too, and `approvalsFor` and `callbackRecorders` (names only) give one invoice's approvals and callback recorders. `liveAtBank` says whether the bank has an attempt's payment live, whatever state the ledger gives the attempt, and `LIVE_ATTEMPT` is the same test in SQL. `withBank` is an attempt's own payment that the bank has live and has not paid, and `mismatchedLive` is a transfer under its request id that does not match the invoice and that the bank has not failed. `lateBesideLive` is the test `paidTwice` makes, and `settle` makes it too. `schemaGaps` lists the tables in `SCHEMA` and the columns in `ADDED_COLUMNS` a file lacks, read-only, and `close` closes the connection. `recon()` gives reconciliation's store on the same connection (see Reconciliation). Its tables are not in `SCHEMA`, so `schemaGaps` and the MCP server do not ask for them. `metricsRead` and `changeStamp` serve the metrics, and `ownLive`, `liveAtBank`'s test of an attempt's own payment, is exported for them. `readingSoft(fn)` runs a view's reads with stored JSON read soft. `storedStrings`, `storedList` and `storedObject` are how the row mappers, the stored findings and the cash panel's line amount read stored JSON (see Ledger).
- `src/payments.ts`: idempotent send and status sync between Airwallex and the ledger. `recordMissingFees` reads the fee of up to five failed transfers the ledger has none for, those never tried or tried longest ago first. A transfer whose fee it could not record is read again only after 10 minutes.
- `src/reserve.ts`: the reserve floors. `reserveFromEnv` reads `RESERVE_FLOORS` (currency:amount pairs, major units), `currencyFloor` gives one currency's floor and where it comes from, `floorFor` gives the floor one invoice's replacement is held to, and `describeFloors` is the start-up line. `debitCurrency` is the wallet a payment leaves: `obligation.sourceCurrency`.
- `src/cash-position.ts`: the cash panel. `cashLines` lists every amount the ledger knows about by kind, `committedMinor(ledger, currency, { invoiceId?, runId? })` adds up the promised ones the policy, the run checks and the panel all take off, leaving out the invoice or run being paid, `payRunLines` gives one `pay-run` line per row of an approved waiting run and per released row not sent yet (from `Ledger.payRunRows`), and `cashReport` works each currency down to its headroom. `lineAmount` is what a line takes from its wallet. `waitingRunLines` gives the pay rows of a waiting run that `payRunLines` leaves out (its request not approved, or expired), built the same way, `awaiting-approval` while the request is open and `awaiting-person` otherwise. `cashReport` never takes them; only the incident board does. `FIRM_KINDS` (what headroom takes off) and `WAITING_KINDS` are exported for the board's totals. `attemptLostFee` and `payoutLostFee` are the `fee-lost` test, which the metrics use too. `cashLines(ledger, now, { openOnly: true })` skips settled and rejected invoices, whose only lines are fees kept; the board reads it that way. Given `obligations`, it reads only those invoices' lines. `committedMinor` builds its sending and approved lines from `Ledger.committedRead`, which reads only the columns those lines use (see Ledger).
- `src/run-file.ts`: the pay run file. `parseRunFile` reads the CSV (RFC 4180 quotes, CRLF or LF, a BOM, blank lines skipped), refuses a file it cannot read with `FileProblem`s, and reads each row with `rowFromCells`, which a check also uses on the cells the ledger stored. `RUN_COLUMNS`, `MAX_RUN_ROWS` (50) and `MAX_RUN_FILE_CHARS` (40,000) live here. `due_date` is an optional column.
- `src/runs.ts`: pay runs. `checkRows` (GETs only), `uploadRun`, `recheckRun`, `settleRunRequest` (keeps or opens the run's request inside the transaction that wrote the check), `approveRun`, `releaseRun`, `cancelRun`, `pendingRunApproval`, `runRule`, `runBarred`, `largestTotal`, `runNote` (the run's timeline) and `runKey` (the Dispatcher key `run:N`).
- `src/currency-lock.ts`: `withCurrencyLock` holds a lease on a currency in `currency_locks` around a payment and hands the step its `Lease`. `withCurrencyLocks` takes several in code order. Waiters queue in `currency_lock_waiters` and get the lock in the order they asked. `CurrencyBusyError` means 45 seconds passed behind the payments ahead.
- `src/fx.ts`: `quoteValidity` reads `FX_QUOTE_VALIDITY` when a quote is taken, as the bank deadlines are read, and throws on a value it does not take. `describeQuotes` is the start-up line.
- `src/approval.ts`: `ApprovalTerms` is `ReplacementTerms` (action `replace`, built by `termsFor`) or `HeldPaymentTerms` (action `pay`, built by `heldTermsFor`). `RunTerms` (action `run`, built by `runTermsFor`) is a run's. `bindingOf` is SHA-256 of the terms JSON. `payTo` is the pay-to line. `FxTerms` is the quote in the terms of a payment from another currency's wallet, built by `fxTermsOf` (and `withFeeEstimate`) in one key order. `paymentAmount` and `runAmount` are the only ways to make the `PaymentAmount` the approval policy takes. `describeRate`, `markupOf`, `paidWith` and `conversionText` write rates for people, and `rateMismatch` compares a transfer with its approved quote. `terms.arrival` is the `ArrivalTerms` of an invoice with a due date, and a run row's `arrival` is there only when the file gives the row a due date. `withArrival` swaps in another estimate and keeps the key order.
- `src/bank-change.ts`: `bankChangeForm` says what a person needs to record a callback about new bank details, or why one cannot be recorded now. `recordBankChange` checks the callback, writes a `bank_changes` row, updates the beneficiary in Airwallex and reads it back. It compares with the latest original that became a transfer, or, for an invoice held before paying, with the payment `lastPaidTransfer` finds for the beneficiary. With neither, the form says why: PayOnce has not paid the supplier, or paid it only before it kept which account each payment went to.
- `src/approvers.ts`: the approval policy. `policyFromEnv` reads `APPROVERS` (name:limit pairs), `TWO_APPROVERS_ABOVE` and `APPROVAL_TTL_MINUTES`. `signoffsNeeded` says how many approvers a payment needs and why, `eligibleApprovers` who could approve it, `checkSigner` says why a person may not approve one, and `signoffProblem` checks an approval, an invoice's or a run's, against the policy as it is now. All four take a `PaymentAmount`, never a bare number. `personName` is the one check for a name a person types, `knownName` gives a stored name only when it follows that rule, and `sameName` says whether two names are one person (see Names).
- `src/emails.ts`: `EmailReader` interface (a `name` shown on the page, and `read`), `EmailFindings` (three findings), `summarise`, `unverifiedSenders` (From and Reply-To, ASCII only), `emailEvidence` (the email part of approval terms) and the fixture loader.
- `src/eml.ts`: `parseEmail` reads an uploaded raw email (bytes) into sender, Reply-To, subject, body, `styleText`, attachments (name, type, size), `notes` (fixed codes, `NOTE_TEXT`) and `partial`, or refuses it with PayOnce's own words. `cleanText`, `cleanLine`, `validAddress`, `validDomain`, `noteTexts`.
- `src/html-text.ts`: `htmlToText`, the one-pass HTML scanner, returning the text, `styleText` and whether styles or markup could draw characters PayOnce cannot read.
- `src/css-text.ts`: `scanCss`, the CSS tokenizer that takes out every string and any text that is not CSS, and applies the fail-closed rule.
- `src/intake.ts`: `takeParsePlace` (a place in the parse queue, taken before the upload's body is read; at most four wait behind the one being parsed, and `ParserBusyError` refuses the next), `parseUpload` (runs `parseEmail` in a worker thread, one upload at a time), `storeUpload`, `candidatesFor` (the invoices an upload names; it takes an `InvoiceIndex` from `invoiceIndex`, so several uploads matched against one ledger share one index), `deliverUpload` and the timeline lines for a delivery.
- `src/parse-worker.ts`: the worker thread `parseUpload` starts. It parses the one email it is sent and posts what `parseEmail` made of it.
- `src/model-reader.ts`: `ModelReader` reads the emails it is given with one chat completion over plain `fetch`, with no SDK. The engine gives it one email at a time. It exports `DEFAULT_BASE_URL`, `DEFAULT_MODELS`, `REQUEST_TIMEOUT_MS`, `ModelError`, `keyRefused` and `redactKey`, which the explainer and the Airwallex client share, so the reader's own requests are unchanged. `redactKey` cuts the key out of error text: as written, URL-encoded, as base64 or base64url at each byte alignment, and any run of 20 or more characters from one of those forms, whatever the case of its letters, since a service can echo the key upper-cased. Each cut becomes its `label`, `[key]` unless the caller gives another.
- `src/reader.ts`: `readerSettingsFromEnv` reads `READER_API_KEY`, `READER_BASE_URL` and `READER_MODEL` (null without a key), and `readerFromEnv` picks `ModelReader` from them, or the keyword placeholder without a key. `readerNamesFromEnv` gives every name the stored findings may give for whoever read an invoice's emails: the models in `READER_MODEL`, the default models and the keyword placeholder.
- `src/why-facts.ts`: the facts "Ask why" sends (see Ask why). `whyFacts(ledger, invoiceId, settings)` reads the ledger and the settings only, in one `Ledger.readSnapshot`, and returns the facts, the `legend` (alias to real value, never sent), `asOf` (the timeline's length and last line id) and how many reasons it did not recognise. `REASON_PARTS` and `WHY_PARTS` are the reason grammar, built from the exported reason constants. Each reason part carries the `ReasonCode` the metrics count a reason under when it leads, and `REASON_LEADS` exports the parts with their codes. `KNOWN_CODES` and `FAILURE_WORDS` are exported for the metrics too. `LINE_RULES` and `FIXED_LINES` are the allowlist of timeline templates, each bound to the kinds and topics PayOnce writes it with. `Aliases` numbers people and other invoices in order of first appearance.
- `src/explainer.ts`: `Explainer` (one chat completion per model, in the list's order), `EXPLAIN_SYSTEM`, `promptOf` (the user message), `explainerFromEnv` (null without `READER_API_KEY`), `shownAnswer` (cleans and caps the answer and swaps the aliases back), `factsKey` and `ExplainLimiter` (the page's limits and the answers it remembers). `ExplainError.limited` is true when every model answered 429. `Explainer.host` is the host the facts go to, and `googleFreeTier` says whether it is Google's endpoint.
- `src/keyword-reader.ts`: the fallback reader. It matches a handful of phrases.
- `src/server.ts`: `node:http` server for `web/` and the JSON API. It runs scenarios in the background, starts the watcher and connects webhooks.
- `src/mcp.ts`: the read-only MCP server over stdio, and the only file that imports `@modelcontextprotocol/server` and `zod`. `serveStdio` picks each connection's protocol era. It parses only the lines of `<root>/.env` that set an `ENV_ALLOWED` key, finds the ledger (`PAYONCE_LEDGER`, absolute or from the repository root, else `<root>/payonce.db`), registers the eleven tools and runs each call through `answer`. `serverBalances` reads `GET /api/cash/cached` on `PORT`. See MCP server.
- `src/mcp-views.ts`: what the MCP tools answer, from the ledger alone: `incidentsView`, `incidentView`, `runsView`, `runView`, `outagesView`, `cashView` and `auditView`, in the JSON API's shapes without `busy` and `watching`. `cachedBalances` takes the balances and floors, as numbers, from the server's answer. `ToolRefusal` is a refusal in PayOnce's words. It keeps its own copy of the incident and run views, so `server.ts` is not imported. `incidentsView` gives each invoice the incident list's headline: the board's `why` while it is on the board, otherwise its latest line from `Ledger.headlines`, never an error, an email or a draft. `suppliersView` and `supplierView` call `suppliers.ts`'s own builders, the second without `inbox` and `drafts` and with `viaInvoice`, so they have no copy to drift.

## Rules the engine keeps

- The agent learns what the bank did only by reading Airwallex. A webhook or the watcher wakes it, and it reads the transfer itself. Nothing in a webhook's body feeds a decision.
- In `pnpm ui` and `pnpm recover` every step on an invoice goes through the `Dispatcher`, including a person's approve and close on the page, so two steps never run on one invoice at once in that process. `pnpm approve`, `pnpm close`, `pnpm outbox` and `pnpm outage end` call the engine directly, and the ledger's transactions keep their writes apart from the server's.
- The engine writes an attempt row, with its `request_id`, before the Airwallex call. A 4xx marks the attempt failed, except a 429. Any other error, a 429 included, leaves it pending, because the transfer may exist, and a later look retries it under the same `request_id`. This holds for every payment, not only pay run rows. PayOnce fails a pending attempt without a refusal only when something else may pay the invoice (a paid payout sent outside PayOnce, a late transfer the bank has live, or a paid mismatched transfer), or when the record no longer holds the account the attempt keeps (`ACCOUNT_CHANGED_REASON`, see below). In each case it waits until Airwallex lists no transfer for the attempt a bank deadline after its last create try (see the retry rule below).
- Once an invoice is escalated, only a matching approval releases a payment, even if the policy would now replace.
- After sending a replacement the agent waits for the bank. It closes the incident on the look that reads the replacement as paid. A replacement already out is never approved a second time.
- Waiting on the bank has a deadline: the transfer's `created_at` plus `BANK_DEADLINE_LOCAL_MINUTES` (default 3) or `BANK_DEADLINE_SWIFT_MINUTES` (default 5). The look saves it in `obligations.look_at`, and the watcher wakes the invoice when it comes. `startPayment` saves it too, as soon as a new invoice's original is sent, so the look at the deadline comes even when no look runs before it, as when the sandbox bank's script fails. If the send's outcome is unknown, `startPayment` moves the next look a minute on, as a failed look does. An original still in flight then escalates. A replacement still in flight escalates too, with nothing more sent, and the incident still closes if the bank pays it.
- A look that throws leaves the next look as it was. If that time has passed or was never set, it moves a minute on, so a failing look is retried once a minute and not on every check. The watcher wakes an invoice for an approved or expired approval only when no later look is planned. A request that becomes approved makes the invoice's next look due at once, so a watcher in another process uses it on its next check.
- If a replacement has failed, the policy escalates instead of sending a third payment.
- Approvals follow the policy in `src/approvers.ts`, on the page and in `pnpm approve` alike. A name must be in `APPROVERS` and within its limit, compared with what the payment takes from the wallet it leaves, in that wallet's currency (`paymentAmount`). The person who started the incident (`obligations.started_by`) cannot approve. Two different approvers are needed above `TWO_APPROVERS_ABOVE`, for a payment to an account the original did not go to, and when `started_by` is null or a name `knownName` does not take, such as one stored before names were checked. A held invoice's first payment also needs two when PayOnce has never paid the beneficiary, paid it only before it kept which account each payment went to, last paid it another account, or has never paid it on a person's approval (`payeeRule`), as a pay run row does. Paid on a person's approval (`Ledger.paidOnApproval`) is a paid payment opened on an approval that was used (`approval_id`), or the original of a released pay run row. A single incident's original and an automatic replacement count as the account PayOnce last paid, but not here, so paying a payee once by itself never stands in for the two approvers. Attempts from before `approval_id` was kept do not count. Without `APPROVERS` every approval is refused.
- An approval request expires `APPROVAL_TTL_MINUTES` after it was opened. `escalate` returns the expiry as the next look, and that look opens a new request. `signOff` refuses an expired request inside its transaction, and a request it completes gets at least `APPROVED_USE_WITHIN_MS` (10 minutes) to be used. An approved request that expired before use is voided. A request recorded before expiry existed counts as expired, and the watcher wakes its invoice. For an expired request `pnpm approve` says "This request has expired. PayOnce opens a new request on its next look, and pnpm approve shows it then" and offers no command. Given a name, it records nothing and exits 1.
- `escalate` opens no request when `APPROVERS` is unusable or fewer approvers could sign than the payment needs (`eligibleApprovers`). It withdraws any open one and says so on the timeline.
- When one request replaces another that already had signoffs, the timeline says those approvals no longer count.
- An approval is spent with `useApproval` (or `releaseFor` for a held invoice), which only moves an `approved` row that has not expired to `used`, so one another process voided meanwhile, or one that expired during the look, is not spent. `useApproval` also spends nothing unless the invoice is still escalated and has no live outside payout, checked inside its transaction as `releaseFor` does. Each opens the payment's attempt in the same transaction, after the check that the record still holds the approved account, so the money counts as approved or as being sent at every moment and a failed check leaves the approval unspent. The attempt records the approval it was opened on (`approval_id`). `openAttempt` copies the quote from that approval's own terms, so a cross-currency attempt carries the quote that was approved and no other. The outside payouts are read again after the last list of transfers.
- The policy escalates a replacement above `TWO_APPROVERS_ABOVE` instead of sending it unprompted. Once the original has failed, `assess` asks `paidDuplicate` for a paid invoice among those `likelyDuplicates` finds, and keeps it on the assessment. Where the policy would replace, it escalates with "it looks like a second bill for X, which is paid", on every look. Where the policy escalates for another reason, `namingPaidDuplicate` adds ", and it looks like a second bill for X, which is paid" to the reason in the approval terms, after the floor clause, in `withFloorReason` and in the terms `requestedDecision` rebuilds. So every replacement request names the paid match whatever sent the invoice to a person, and an approval of terms that did not name it is void. `replaceUnderLock` looks again under the lease and builds its reason the same way, so the next look keeps its request. With no paid match nothing is added to the terms. `continueEscalated` checks again under the lease too. `useApproval` runs a check inside its transaction and spends nothing when `paidDuplicate` gives a different answer from the one `assess` got, as happens when another process records the match paid during the look. The next look is due at once: it voids the approval and opens a request naming the match. When the policy escalates for another reason, `escalate` also writes a standing `second-bill` warning, "Also, it looks like a second bill for X, which is paid", because the decision line does not name the match.
- `ApprovalTerms.accountKey` is a hash of the full bank details the payment goes to, because `payTo` shows only the last four digits. Whether two sets of details are the same account is a different question, which `routeKeyOf` answers (see Accounts).
- New bank details never come from an email or the reader. A person records a callback with `recordBankChange`: the number they called must match `obligations.supplier_phone` by its digits, with or without the country code, and it is only accepted once the invoice is escalated and every payment for it has failed, or it was held before paying a supplier PayOnce has paid with a checked payment, as after a `LAST_PAID_CHANGED_REASON` hold with a phone on file. A supplier never paid, or paid only before payments kept their account, has nothing to compare with, so the form says which and to approve paying the account on file or close the invoice. The details they type are merged into the beneficiary record, sent with `updateBankDetails`, and read back. The change is `applied` only if the record then holds every typed field but `bank_name` (the deny-by-default rule of Accounts), with `applied_key` set to the record's `bankDetailsKey`. Typed details that hold what the compared payment went to by the same rule are refused as nothing to verify.
- When the record's bank details differ from the original's, `escalate` requests an approval only if `verifiedBankChange` finds an applied change for that beneficiary whose `applied_key` goes where the record now does (`routeKeyOf`), so a bank name Airwallex rewrote after the callback does not undo it. Otherwise it opens nothing, withdraws any open request and waits for a callback. The terms carry the callback in `evidence.bankChange`, the request needs two approvers, and the person who recorded the callback is barred.
- Recording a callback withdraws the open request for the old account. It is refused while another open invoice to the same beneficiary has a pending attempt or an unspent approval, or a pay run row to it is approved or released and not sent (`payRunRows`), because the change would move that payment's account outside its turn. The fields not on the form must equal those of the transfer it is compared with (the original, or the last paid one for a held invoice), and the call must come after that transfer was created. Only the latest applied callback for a beneficiary counts, and everyone who recorded a callback for an account is barred from approving payments to it.
- Every attempt keeps the account it was decided or approved for in `attempts.account_key`, written by `openAttempt` before the Airwallex call: the approval's `terms.accountKey` for one opened on an approval, a pay run row's approved key, the record as `assess` read it for an automatic replacement, and the record as `startPayment` read it under the lease for any other first payment. Every replacement re-reads the beneficiary before it is sent and refuses if `accountKeyOf` the record differs from the approved terms' `accountKey`, or from the details the automatic decision was made on. `checkAccount` compares every transfer an attempt gains (in `send`, after a retry, when found by `request_id`, and in `recordLateTransfer`) with that key, every detail alike: one that went to other details, or that shows no bank details at all, is marked `misdirected` and escalates with a warning, so a payment nobody could check never counts as checked. It and `checkRate` run as the `Decide` of `sendAttempt` and `syncTransfer`, inside the transaction that records the transfer, and their warning lines are written after it, so a line that cannot be written never leaves a transfer recorded and unchecked. `settle` never closes an invoice by itself while a misdirected attempt is live at the bank: `closeRefused` writes a fixed waiting line and the close card offers it, as for a rate mismatch. A pending attempt is first looked up by `request_id`, and `retry` sends it again only if the record still holds the key it keeps. When it does not, `retry` throws `AccountChangedError` and the look hands the attempt to `failNeverSent` with the fixed `ACCOUNT_CHANGED_REASON`: the invoice waits for a person, who can restore those details in Airwallex so the next look sends it. Once a bank deadline has passed with nothing listed under its request id, it is marked failed, a waiting line says that restoring the details no longer sends it and that paying the invoice now takes an approval, and the invoice carries on with a person like any whose payment failed. An attempt from before the column falls back to the old checks: a used approval's account, then the original's for a replacement, then a run row's.
- The open that adds `attempts.account_key` fills it for the attempts already there, under the same write lock (`backfillAccountKeys`), from what shows a person or the engine checked the account: the `terms.accountKey` of the approval the attempt was opened on (`approval_id`); else that of the `used` approval of its invoice for the same kind of payment (`replace` for a replacement, `pay` for an original) whose last signoff came before the attempt opened and after the invoice's attempt before it, the opening taken from `opened_at` or else from the first timeline line saying it was sent; else, for a released pay run row's original, `run_rows.account_key`. It never takes an approval only because it is the invoice's latest. Any other attempt keeps none, and `lastPaidUnchecked` reads the latest paid one of those for a beneficiary. On a copy of the main ledger it keyed two of the 13 attempts, the two paid on approvals that named an account, so the demo supplier's last checked payment is `P261028-2IURNV2`.
- Before an approval is used, `approvalProblem` checks it against the policy as it is then: every signoff has the request's binding, there are enough of them, and each signer still passes `checkSigner`.
- A payout PayOnce did not send, whose reference names an invoice in the ledger, is tied to that invoice. So is one that `nearlyPays` an invoice: same supplier, amount and currency, with a reference `sameInvoiceNumber` matches. The sweep ties a near match to an invoice not yet closed first, then to the oldest. A failed payout that only nearly matches a closed invoice is not tied: it becomes an incident of its own, with a warning naming the closed invoice. The check before a payment ties a near match to the invoice being paid, unless the reference names another invoice exactly. While one is in flight, paid or in an unknown status, the policy escalates before any other check, an open approval is withdrawn and nothing is sent. A settled or rejected invoice that gains one is reopened as escalated, in the transaction that ties it, which also makes an open or escalated invoice's next look due (`Ledger.lookNow`). A tied payout counts as paying the invoice (`paidOutside`, a person's close as paid outside, the close card's kind, the alert's `close` need and the board's group) only when `payoutPays`: it took the invoice's amount in its currency (what `debitOf` read), and went to the invoice's beneficiary (`outside_payouts.beneficiary_id`) or to an account PayOnce decided for that beneficiary by a known routeKey. A paid one that only names the invoice still holds PayOnce's payments, is listed on the close card as `namesOnly` (reference, amount, currency, last four of the account, never the payee) and does not stop a close without paying (`reject` and `rejectAgain` test `BLOCKING_OUTSIDE_PAYOUT`).
- Before any payment, an original or a replacement, automatic or approved, the agent lists the transfers again and ties any new payout for the invoice. If it finds one, it sends nothing, leaves the approval unspent and looks again at once. For a new invoice's original, `startPayment` holds the invoice when the payout it ties is live, and sends anyway when that payout has already failed.
- That includes every retry of a pending attempt with no transfer, after `findTransferByRequestId` found none: `linkUnseenPayouts`, then `syncOutsidePayouts` reads every tied payout, including one tied just now. While `paidTwice` finds a late transfer, `failNeverSent` holds the attempt with `holdPaidTwice` (see below), and while a mismatched transfer is in flight, `holdMismatched` holds it. Once that transfer is paid, `failNeverSent` holds the attempt with `holdMismatched` and marks it failed by the rule below, so a person can close the invoice. While a payout is live the attempt is not sent: it stays pending under its request id (so it keeps the duplicate lock), the invoice is escalated with `OUTSIDE_PAYOUT_REASON`, a standing `retry` warning says so, and `holdForOutsidePayout` withdraws any open request. The watcher wakes the invoice when that payout fails, and that look retries the attempt. A payout tied in this look that has already failed holds nothing: the invoice is not escalated, and the next look, due at once, retries the attempt. Inside the lease, just before `sendAttempt`, `retry` reads the invoice's outside payouts and the attempt from the ledger again. If a payout is live, the invoice is settled or rejected, another payment for it is live at the bank (`liveAtBank`), or the attempt is no longer pending with no transfer, it sends nothing and the next look comes at once, because another process may have tied a payout, recorded a late transfer, closed the invoice or changed the attempt while this look waited up to 45 seconds for the lock. When a tied payout is paid, `paidTwice` finds a late transfer the bank has live, a mismatched transfer is paid, or `retry` throws `AccountChangedError`, `failNeverSent` escalates the invoice with `OUTSIDE_PAYOUT_REASON`, `LATE_TRANSFER_REASON`, `MISMATCHED_TRANSFER_REASON` or `ACCOUNT_CHANGED_REASON` and holds the attempt, with a `retry` warning, until `neverSentAt`: the bank deadline of the invoice's method after `attempts.tried_at`, or after `opened_at` if the attempt was never tried. It plans the look for then. `sendAttempt` writes `tried_at` just before every create call, so a 5xx retried each minute keeps pushing the deadline back. Once the deadline has passed, `failNeverSent` takes the lease of the wallet the attempt pays from, which a retry holds from its create try to recording the transfer. Under it, it reads the attempt again (a try since then moves the deadline, and an attempt no longer pending with no transfer gets a look at once) and lists the request id with `findTransferByRequestId`, its only listing. If that lists nothing, `failAttempt` (which changes only an attempt still `pending` with no `transfer_id`) marks it failed with a `payment` line on the `retry` topic, which releases the duplicate lock and its `sending` line. For a paid payout, `paidOutside` then offers the close card, and for a paid mismatched transfer `paidMismatched` does. For a late transfer, the next look, due at once, records it in its own state, and it takes the lock. A transfer listed by then is not failed: the next look, due at once, records it. When `tried_at` is added to an older file, every pending attempt with no transfer gets that moment, and an attempt with neither time gets one on its first look, so neither is failed before a full deadline has passed.
- A transfer Airwallex lists under the request id of an attempt marked failed with no `transfer_id` goes on that attempt through `recordLateTransfer`, in the state the bank gives it, with a timeline line, and `attempts.found_late_at` records when. This corrects an attempt that `failNeverSent` or a refusal marked failed before Airwallex listed its transfer. It runs `checkRate` and `checkAccount` on the transfer, unless the transfer failed on a closed invoice. Those checks, the `LATE_TRANSFER_REASON` escalation or the reopen of a closed invoice, and a look due at once are written in the transaction that records the transfer, and its line after, so a step that stops between them leaves either nothing, for the next sweep to find, or everything but the line. Keeping a mismatched transfer (`addMismatched`), a change of its status (`setMismatchedStatus`) and adopting a found payout (`adoptPayout`) also make the invoice's next look due in their own transaction. `unrecordedAttemptOf` matches the request id and also wants the invoice's number as the transfer's reference, with the invoice's amount and currency. A transfer under such a request id without the invoice's number, amount and currency is not recorded as the attempt's payment. `noteMismatchedTransfer` keeps it beside the attempt (`mismatched_transfer_id`, `mismatched_reference`, `mismatched_status`, and what it took from its wallet as `debitOf` reads it, `mismatched_amount_minor` and `mismatched_currency`, written when it is tied and on every read), writes a `warning` once and escalates the invoice with the fixed `MISMATCHED_TRANSFER_REASON` through `escalateUnlessSettled`, so a settled invoice stays settled. Later reads only update its status, with a `bank` line when it is paid or failed. The sweep calls it in the invoice's turn and wakes the invoice only when it first keeps the transfer or the status changes. `linkUnseenPayouts` calls it too, so the check before a payment looks again. The sweep records a late transfer in the invoice's turn, and wakes the invoice only if it is open or escalated afterwards. `linkUnseenPayouts` records one for the invoice's own failed attempts and then returns true, so the check before a payment sends nothing and looks again at once. A pending attempt's transfer is left to its look: the sweep only wakes the invoice, and the look lists the attempt by request id and records the transfer, so `checkRate` and the bank hook run as for any payment it sends. A webhook for a failed attempt with no transfer asks for a sweep.
- `paidTwice` finds a payment that may have paid the supplier a second time: a late transfer the bank has not failed, or a transfer the ledger keeps failed while the bank shows it live, while another payment for the invoice, PayOnce's or one sent outside it, is live at the bank too. Both are judged by `liveAtBank`, so two late transfers count even when the ledger keeps one of them failed. The ledger keeps one failed because `Ledger.record` never breaks the duplicate lock: when the bank's state would make a second live attempt, it records everything but the state, `bank_status` included. `recordLateTransfer` then writes a `warning` and escalates the invoice with the fixed `LATE_TRANSFER_REASON`, reopening it if it was closed. A look checks `paidTwice` after syncing its payments and outside payouts, before the policy, before a paid payment can close the incident and before any retry, and `retry` checks inside the lease that no other payment is live at the bank. While it finds one, `holdPaidTwice` escalates with that reason, withdraws any open request and sends nothing. The policy never runs, so it never replaces the reason with `OUTSIDE_PAYOUT_REASON`. The alert's need is `twice`, and the close card gives the reason once a payment is paid and nothing else is still with the bank. An attempt still pending with no transfer beside a late transfer goes to `failNeverSent` (see above), so it is marked failed once a bank deadline has passed with nothing listed. With no other live payment, a late transfer is followed like any payment, and a rejected invoice whose late transfer has not failed is reopened as escalated.
- A transfer the bank has live counts as live everywhere, whatever state its attempt has in the ledger. `liveAtBank` is the test: an attempt that is not failed, one with a transfer whose `bank_status` is not `FAILED` or `CANCELLED`, one found late whose status was never read, or one with a mismatched transfer the bank has not failed. `LIVE_ATTEMPT` is the same test in SQL, built from the same status list. `insertAttempt` refuses an attempt while one is live (`DuplicatePaymentError`), so `openAttempt` (and with it `startPayment`, `replaceUnderLock`, `useApproval` and `releaseFor`) and `tryLock` never open a second payment beside a transfer the ledger keeps failed. `useApproval`, `releaseFor` and `reject` change nothing while one is live, and `retry` sends nothing inside the lease while another payment is. `Ledger.releaseRun` opens no attempt, so its rows meet the test when `startPayment` opens theirs. The policy's inputs follow the bank too: the original the policy goes by is the latest the bank has live, else the latest, and `replacementFailed` counts a replacement only when the bank does not have it live (`liveAtBank`), one Airwallex refused included, so an invoice with a live late transfer is never replaced. The look records a kept transfer again after reading the others, so it takes its own state, and the duplicate lock, in the look that finds the other payment failed, with a `bank` line. If one is still kept after that, the look decides nothing and looks again at once. The watcher reads a kept transfer the bank has in flight, a webhook for one wakes its invoice, the cash panel lists it as `with-bank` and books no lost fee for it, the board counts it with the bank, `paidOnce` and `paidOutside` do not take it for failed, and a callback is refused while it is live.
- While a mismatched transfer is live, the look reads its status first, and `holdMismatched` escalates the invoice with `MISMATCHED_TRANSFER_REASON`, withdraws any open request and sends nothing, before a retry and before anything else is decided. Just before that hold the look reads the invoice's payouts sent outside PayOnce, so one the bank has paid or failed is recorded and the watcher stops waking the invoice for it. While the bank has the transfer and has not paid it, the cash panel lists it as `with-bank` in the wallet it left, on an invoice that is not closed. For one tied before its amount was kept, the line holds an estimate of what the attempt would take from that wallet (`lineAmount`): the invoice amount, the quote's sell amount for a payment from another currency's wallet, or 0 with no quote. Once it is paid, `paidMismatched` lets a person close the invoice from the close card (kind `mismatched`), and `settle(invoiceId, true)` accepts it. A paid mismatched transfer and a paid payout sent outside PayOnce do not rule each other out: `paidOutside` asks only that no PayOnce payment is live or still with the bank, and only an outside payout in flight or in an unknown status stops `paidMismatched`. Once every mismatched transfer has failed, the look rewords `MISMATCHED_TRANSFER_REASON` to the fixed `MISMATCHED_FAILED_REASON` with `rewordEscalation`, and the invoice carries on with a person. Only a person clears it. `pendingClose` lists the uncleared mismatched transfers in `CloseReview.covered` (`CoveredTransfer`: transfer id, short reference, status, attempt kind). The close card shows them under "This close covers" and sends the transfer ids it shows. `pnpm close` prints them and closes only when `--covers=` names every one of them, by short reference or transfer id, and nothing else. `closeIncident` takes those ids (`shown`). It refuses when one on file is not among them, as when one was found since the card was shown, and when the caller names none (`covered` left out of the request) while any is on file, saying the close must name them. Otherwise `settle`, `reject` or `rejectAgain` set `mismatched_cleared_at` on exactly those, inside the transaction that closes the invoice. One tied between that check and the transaction stays uncleared. Until a person clears it, PayOnce never closes the invoice by itself. When a look's own close is refused for an uncleared mismatched transfer or a live outside payout, `closeRefused` sends the invoice to a person with `Ledger.escalateIfOpen`: an open one with `MISMATCHED_FAILED_REASON` (`MISMATCHED_TRANSFER_REASON` while one is live, `OUTSIDE_PAYOUT_REASON` for a live payout), while an escalated one keeps its reason. A waiting line names the transfers to check, and no next look is planned, so the watcher leaves it alone. The close card and the `close` alert follow. `escalate` writes the same waiting line for an invoice paid once.
- A pending original held for a live outside payout (`holdRetryForOutsidePayout`) leaves the invoice escalated with `OUTSIDE_PAYOUT_REASON`. When that payout fails and the original goes out and is paid, the invoice is still escalated, so a person closes it from the close card: a resume never closes an escalated invoice that its original paid. An original `startPayment` held before paying goes out only on an approval, and `releaseFor` reopens the invoice, so once that original is paid the policy closes it by itself. A held replacement closes by itself once paid, like any paid replacement.
- Any other payout PayOnce did not send becomes an invoice with origin `outside` once it has failed or is in flight past its deadline. The policy escalates where it would replace, so a person approves the replacement.
- No approval is requested for an invoice the ledger shows as paid once.
- Before a new invoice's original is sent, `startPayment` ties any unseen payout for it sent outside PayOnce. For any first payment but a pay run row's, it reads the beneficiary record last under the lease and keeps its account on the attempt, which is one beneficiary read more for every original. A record Airwallex no longer has, or one with no bank details, holds the invoice ("the beneficiary is no longer in Airwallex"). It then holds the invoice for a person if `likelyDuplicates` finds another invoice, not `rejected`, to the same supplier (same beneficiary or same name) for the same amount and currency, with a number `sameInvoiceNumber` matches; if `sameNumberForSupplier` finds such an invoice for any amount or currency, because PayOnce pays an invoice number once; or if an outside payout for it is live. After those `lastPaidHold` holds it with the fixed `LAST_PAID_CHANGED_REASON` when `lastPaidTransfer` finds a payment to the beneficiary whose account the record no longer holds by where the money goes (`Ledger.holdsAccount`: the attempt's `route_key`, else its full `account_key`), whether or not a callback verified the record. Without a callback, `continueHeld` waits for one before any approval opens, exactly as for a replacement. With one, the request carries the callback, needs two approvers and bars whoever recorded it, so a callback recorded on one invoice never lets that person, or anyone alone, pay another invoice to the new account. With no checked payment to the beneficiary but one `lastPaidUnchecked` finds, it holds the invoice with the fixed `UNCONFIRMED_ACCOUNT_REASON`: no callback is needed, and paying it takes two approvers. A beneficiary PayOnce has never paid is not held for this. Once a checked payment to the account on file is paid, later invoices to it go out as usual. These checks run in the transaction that opens the attempt. A held invoice is `escalated` with no attempt and `obligations.duplicate_of` listing the matches. Nothing is sent.
- `sameInvoiceNumber` ignores case, spaces, dashes and other marks, and leading zeros. It also matches a number to the same number with up to four letters added after the last digit, but not two numbers with different letters (`INV-42A` and `INV-42B`, `RENT-2026-OCT` and `RENT-2026-NOV`).
- `heldBeforePaying` is an escalated invoice that has sent nothing: every attempt, if any, failed without a transfer. Airwallex refusing every original (a 4xx on create) escalates the invoice, at once on the first send and otherwise on the next look, so it is held the same way.
- A held invoice pays only on an approval of `HeldPaymentTerms` under the same policy. Each look adds any invoice that `likelyDuplicates` now finds to `duplicate_of`, so one started later, or one that came first while this one was held for another reason, is listed too. The terms list each matched invoice with its state, the payment that paid it, and whether that payment, or one still with the bank, went to the same account. A change in any of them voids the approval. When the payment that paid a matched invoice, or else one still with the bank, went to another account than the one on file (`sameAccount` false), the request needs two approvers and the timeline warns. A match that was paid to the same account does not by itself need a second approver.
- On a matching approval, `continueHeld` ties unseen payouts and checks the record still holds the approved account. `Ledger.releaseFor` then spends the approval, moves the invoice back to `open` and opens the original's attempt in one transaction, which changes nothing if the approval is no longer approved, the invoice has been closed or has sent something, or an outside payout for it is live. It also changes nothing when `duplicatesOnFile` (each matched invoice's state and its payments that have a transfer) differs from what it was when `continueHeld` built the terms, or when `likelyDuplicates` finds an invoice the terms do not list. The next look adds that invoice to `duplicate_of` and to the terms. The invoice then carries on like any other. A pending original paid on such an approval is retried only if the record still holds the approved account.
- A person closes an escalated invoice without paying through `closeIncident`, which calls `Ledger.reject` with their name, and the note goes on the timeline: state `rejected`, with `rejected_by` set, and any open request voided in the same transaction. Any escalated invoice qualifies once nothing for it is live at the bank (no attempt `liveAtBank`, no live outside payout): one held before paying, one whose payments all failed while a replacement request is open, and one whose new bank details nobody can verify because no phone is on file. `pendingClose` offers it as kind `duplicate` for a held invoice whose `duplicate_of` lists matches and `unpaid` otherwise, with the escalation reason. Nothing is sent, and a rejected invoice opens no request again. The invoices a held one matched get a line on their timelines. The alert's need stays the one its reason gives for an invoice that sent a payment; only a held invoice, or one closed before, gets `held`. A rejected invoice that gains a live outside payout is reopened, and when that payout fails, `continueHeld` closes it again without asking anyone to pay it. One reopened by a late transfer is closed again by `continueEscalated` once every payment has failed. Both use `Ledger.rejectAgain`, which changes only an escalated invoice with `rejected_by` set and nothing live at the bank, PayOnce's or sent outside it. By itself it refuses while a mismatched transfer no person has cleared is on file: the look writes a waiting line, the close card offers the invoice as kind `unpaid`, and `closeIncident` closes it again with `rejectAgain(invoiceId, true)`, keeping who closed it first. No approval request opens for an invoice with `rejected_by` set, and `useApproval` spends nothing on one.
- `releaseFor` only changes an escalated invoice that has sent nothing, and `reject` only one with nothing live at the bank, both with no live outside payout. Each is a conditional update on `state = 'escalated'` under the write lock, so a release, an approved replacement and a close from different processes cannot both succeed.
- Pay again never reaches Airwallex. `Ledger.tryLock` inserts a replacement attempt inside a transaction and always rolls it back, so the lock either refuses it or nothing is left behind. When the lock does not refuse, the timeline says why nothing was sent.
- A look writes a `bank` line when it finds a payment the ledger had in flight now paid or failed.
- Approval terms take the pay-to account from the beneficiary record as it is now, and the policy escalates if that differs from the account on the original transfer. The timeline carries a warning whenever they differ, whatever reason the policy escalates for.
- A reader failure marks the thread unread, which escalates. The next look reads from the email that failed, and keeps the count of those read before it.
- A non-finite amount throws in `toMinor`, and the policy escalates if the cash position is not a number. `readMinor` gives null instead, for amounts that are only recorded or shown.
- The reserve floor is per currency, from `RESERVE_FLOORS`. In a currency not listed every automatic replacement escalates ("no reserve floor is set for this currency"). That check comes last, just before the policy would replace, and with no floor set the cash is not checked, so it never takes the place of a more specific reason. A payment sent outside PayOnce is checked before the cash, so the policy's reason for it does not move with the balance or the floor. `CUR:0` means no floor on purpose. A setting that cannot be parsed makes every floor unreadable (`floorFor` returns NaN), so every automatic replacement escalates as "the cash position could not be read". `obligations.invoice_floor_minor` lets an invoice be stricter than its currency, never looser. Of new invoices only `eur-swift-low-reserve` sets one, and invoices from before `RESERVE_FLOORS` keep the floor they carried. An invoice floor above 0 counts as set when the currency is not listed.
- Before an automatic replacement the policy takes off `committedMinor`: money promised to other invoices in the same wallet that has not left `available` yet. That is attempts being sent with no transfer yet, `approved` approvals not used or expired on invoices that could still pay, and pay-run rows of an approved waiting run or released and not sent. Money with the bank is already out of `available`, and requests waiting on a person are not counted, so one held invoice cannot block replacements elsewhere. `assess` adds it up before it reads the balance, so a payment that gets its transfer in between is counted twice, never missed. The checks made under the currency lock (`replaceUnderLock`, a run row's floor check in `startPayment`, and a run's `cashCheck`) add it up before the read and again after it, and `committedAcross` takes each invoice at the larger of the two, so a payment promised in between is not missed either. The panel's headroom takes off the same lines. For a cross-currency invoice the wallet is the source wallet and a line's amount comes from `lineAmount`. A pay run's USD cash check therefore counts a EUR invoice paid from USD at its quote's USD amount.
- Every replacement request names the floor when it applies, the first one included. `act`, `continueEscalated` and `replaceUnderLock` (when its decision under the lease escalates) all run `withFloorReason`, which calls `floorReason`, the check `decide` makes, on the same `floorFor` and `committedMinor` figures, so the two cannot disagree. When the original failed, no outside payout is live and the policy escalated for another reason first (sent outside PayOnce, two approvers, and the like), a floor reason that also applies (below the floor, unreadable or not set) is added to the reason in the approval terms as "<reason>, and <floor reason>". With no floor set the added part is `NO_FLOOR_CLAUSE`, "no reserve floor is set for this currency", because the other reason already says why a person approves. The decision line keeps the policy's order. `escalate` then writes a standing `floor` warning. It says the approval request names the floor only when a request bound to these terms is open, which is not the case after `awaitApproval` withdrew a request on an old quote. A request that `awaitApproval` opened in the same look on these terms, counted from today, is treated as bound to them. A look that finds the floor no longer applies after such a warning writes a line saying so. That line adds that an approval of a request naming the floor still counts only when such a request or approval is open.
- An approved replacement is checked against the floor again before it is spent. Once the floor applies, an approval of terms without the floor reason is void because the binding changed, and the new request names both. While the floor does not apply, `asRequested` rebuilds the terms with only the floor changed (below it, unreadable, not set). A request or approval that has not expired and whose binding matches one of them still counts, so a refund that lifts cash above the floor neither voids an approval nor reopens a partly signed request. A request opened because the approval was void for another reason, or because the payment now needs more approvers, gives the terms as they are now, without the floor. An approval of a request that named the floor is spent however far below the floor cash has fallen since, as in `eur-swift-low-reserve`. The terms carry no shortfall figure, because one would void approvals on every balance move. For a cross-currency invoice the rebuilt terms keep the open request's quote, because `rateFor` offers that quote while the request is open, and the binding can still match. The floor figures are in the source wallet at the quote's amount.
- The cost line on the timeline appears when the replacement pays a fee or something is committed elsewhere, and names the committed amount. The policy's floor reason is unchanged, so no approval is voided by wording.
- A single incident's original, and an original released after a hold, are not checked against the floor. A pay run's rows are, at the check, under the lock at release, and under the lock when each is sent.
- Every payment PayOnce creates holds the lease of the wallet it leaves (`withCurrencyLock` on `debitCurrency`, the source currency for a cross-currency invoice) from its last Airwallex read through creating and recording the transfer: an original from `startPayment`, an automatic replacement (`replaceUnderLock`), an approved replacement (`continueEscalated`, which takes it before it spends the approval), a held invoice's original paid on an approval, and a retry of a pending attempt, the last try of a lapsed quote included. `failNeverSent` lists and fails an attempt under the same lease. `openAttempt` refuses a lease in any other currency. The lease is a `currency_locks` row taken by a conditional upsert under `BEGIN IMMEDIATE`, so the CLI and the server take turns. It lasts 60 seconds, is renewed every 20 while held, and runs out by itself after a crash. Waiters get it in the order they asked (`currency_lock_waiters`), so a run sending its rows back to back cannot starve a payment that started waiting meanwhile. A payment waits up to 45 seconds behind the payments ahead of it, then fails with `CurrencyBusyError` having sent and spent nothing, and the next look comes a minute later (`resumeIncident` plans it, or `startPayment` itself when the scripted run called it). It is not re-entrant. `openAttempt`, `useApproval`, `releaseFor` and `Ledger.releaseRun` check inside their transaction that the lease row still names the holder and has not expired, and throw `LeaseLostError` if not, so a holder whose lease ran out opens nothing. Payouts sent outside PayOnce take no lease, so one created in the window between a balance read and the attempt is the one case the lock cannot see.
- An automatic replacement takes the lease, ties unseen payouts, checks the record still holds the account, reads the balance again, and runs `decide` again, with the fresh balance and the committed money as it is now, in the transaction that opens the attempt. Anything but replace escalates with that reason. That transaction first checks that the invoice is still open, and that no payout sent outside PayOnce tied to it is live, as `useApproval` and `releaseFor` check, so one another process tied while this look waited for the lease or read the balance stops it, and the next look comes at once. If another process sent it to a person, or a person closed it without paying, while the look waited for the lease, nothing is sent and the next look comes at once.
- Fees are stored on attempts and outside payouts from the transfer's `fee_amount` and `fee_currency`, and are 0 when `fee_paid_by` is `BENEFICIARY`. Decisions still read the fee from the transfer they just fetched, never from the ledger. The panel books a transfer to the wallet it took money from, which for a payout paid from another currency is its `source_currency` with its `source_amount`, and a fee to its own `fee_currency`. No figure adds two currencies together.
- The cash panel caches balances for 30 seconds. The policy never uses that cache: `assess` reads the balance fresh on every look.
- An invoice with a `sourceCurrency` other than its `currency` (`crossCurrency`) is paid by one transfer per attempt that converts on a quote: `source_currency`, `transfer_currency` and `quote_id`. The quote buys exactly the invoice amount. There is no separate conversion.
- Every cross-currency payment goes out on a quote a person approved. `startPayment` holds the original before paying (reason "it is paid from USD, so a person approves the exchange rate before PayOnce pays it", after the missing-beneficiary hold, the duplicate, same-number and outside-payout holds, `lastPaidHold` and `EMAILS_BEFORE_PAYMENT_REASON`). `decide` escalates a replacement after the cash, outside-origin and two-approver checks and before the no-floor check. `openAttempt` refuses a cross-currency attempt unless the approval it is opened on carries a quote, and `sendAttempt` refuses an attempt with no `quoteId` before calling Airwallex.
- The quote is `terms.fx` and is in the binding. It is added only on a cross-currency payment, by a conditional spread right after `accountKey`, so every other payment's terms, and every existing binding, are unchanged. `changedFields` names a change as "exchange rate".
- One quote rule: a new approval request never opens on a quote an earlier request showed. While a request is `requested` or `approved` and not expired, `rateFor` builds the terms on its quote, so the binding holds still across looks. Otherwise it offers the invoice's last quote (`obligations.last_quote`) when the latest request did not show it and it still has more than 22 minutes left (`2 * APPROVED_USE_WITHIN_MS + QUOTE_MARGIN_MS`), so a request opened on it stays open at least 10 minutes. Only when it cannot does it take a fresh quote, which becomes the last quote. A look that opens no request, for example because nobody on the list can approve the payment, takes no new quote while the last one holds. When a new request is needed and the terms carry an open request's quote (other evidence changed), `awaitApproval` withdraws the open one and returns now, and the next look takes a fresh quote. A rate line (kind `payment`) is written only when a request opens on a quote, with the last request's rate when it differs. The waiting line for a payment nobody can approve names no rate, only roughly what the payment takes from the wallet.
- A cross-currency request expires at `min(opened + APPROVAL_TTL_MINUTES, quote end - APPROVED_USE_WITHIN_MS - QUOTE_MARGIN_MS)`, with a 2 minute margin. The quote end is the earlier of `valid_to_at` and arrival plus the quote's validity, so a clock that differs from Airwallex's cannot stretch it. With the approved use window this ends any approval at least 2 minutes before its quote. A short TTL, such as 2 minutes for the demo, still opens a request. `FX_QUOTE_VALIDITY` takes `MIN_30` or longer, and a quote that holds less than 12 minutes is refused.
- Approval limits, `TWO_APPROVERS_ABOVE`, `eligibleApprovers`, `signoffsNeeded` (in `continueHeld` too) and `signoffProblem` use `paymentAmount(terms)`: the quote's sell amount in the sell currency for a cross-currency payment, the invoice amount otherwise. `decide` uses `incident.sourceAmountMinor` for the cash check and the two-approver check. The fee stays out of the limit.
- The attempt keeps `quote_id`, `quote_valid_to` and the approval it was opened on (`approval_id`), all written before the Airwallex call by `openAttempt`, inside `useApproval` or `releaseFor`, from the approval's own terms. Every attempt opened on an approval keeps its `approval_id`, including a same-currency one. A retry sends the same request id and quote, never a new one, under the source wallet's lease. Until `quote_valid_to` plus the transfer method's bank deadline, a 4xx on a retry (`sendAttempt(..., "retry")`) never fails a cross-currency attempt: it stays pending and holds the lock, and the look runs again a minute later. The first send's 4xx still fails it as before. After that time the look makes one last try under the same request id (`"lapsed"`). `duplicate_request_id` records the transfer it names. A quote refusal (`quote_expired` or `quote_id_invalid`, the codes Airwallex documents; the sandbox has not shown its own) fails the attempt if `findTransferByRequestId` also comes back empty, because Airwallex checks the request id before the quote, and the timeline says why. Any other error on the last try, a 429 or 401 included, or a listing that throws, leaves the attempt pending: the look takes the refused path only when the ledger shows the attempt failed, and otherwise throws and is retried a minute later. `failAttempt` changes only an attempt that is still pending with no transfer. A held original then goes back to a person through the refused-original path, and a replacement through the policy, each for a new approval on a new quote.
- `checkRate` compares the transfer with the `fx` of the approval the attempt was opened on (`Ledger.approvalOf`: by `attempts.approval_id`, or the latest approval for an attempt without one), through `rateMismatch`: `currency_pair`, `rate`, and the source amount and currency `debitOf` reads, never inverted, and a transfer with no `conversion` counts as a mismatch. The retry's account check and the panel's `lineAmount` read the approval the same way. It runs wherever an attempt first gains a transfer: in `send`, after a retry, when found by `request_id`, and in `recordLateTransfer`. A mismatch is recorded on the attempt (`rate_mismatch`) and escalates with a warning. The look reads the obligation again after syncing its attempts, so an invoice escalated that way takes the escalated path in the same look. Only a person then closes the invoice, whether the attempt was the original or a replacement: `settle` refuses unless `closeIncident` calls it, and `pendingClose` gives the mismatch as the close card's reason. An attempt with a mismatch that then failed does not block the automatic close once another payment is paid.
- The cash check reads the source wallet. `assess` takes a quote for a cross-currency invoice only once its original has failed, and uses the original's fee if `fee_currency` is the source currency or missing, else NaN, so the policy reads the cash as unreadable. The cost line is in the source currency.
- `debitCurrency` is the source currency, so the reserve floor, `committedMinor` and the cash panel use the source wallet. `lineAmount` gives a line's amount: what `debitOf` read from the transfer (`attempts.amount_minor`), else for a cross-currency payment the sell amount of the quote the attempt was sent with or the open request is on, else the last quote's (`obligations.last_quote`), estimated, else 0, estimated. A line whose amount comes from a quote has `fromQuote`, and the page notes it.
- A failed cross-currency original is replaced from the same source wallet on a fresh quote. Paying from the currency Airwallex refunds a failed converting transfer in is not built.
- Pay runs do not use FX: each row pays in its own currency from that currency's wallet. A file with a `source_currency`, `paid_from`, `pay_from` or `sell_currency` column is refused, `Ledger.releaseRun` writes `source_currency` as null, and `startPayment` refuses a run row whose invoice would convert. A run's approval limits go through `runAmount(terms)`, the largest currency total taken from the run's terms, so `checkSigner`, `eligibleApprovers` and `signoffProblem` get the same branded `PaymentAmount` for a run as for an invoice.
- On resume, a paid replacement closes the incident unless an outside payout for the invoice is live or the payment that paid it went out at an unapproved rate or to other bank details than it was decided or approved for (`misdirected`). Before that, a live mismatched transfer (`holdMismatched`) or a late transfer (`paidTwice`) holds the invoice for a person, and an uncleared mismatched transfer makes `settle` refuse, so `closeRefused` hands it to a person. A paid original goes to the policy, which first escalates for a live outside payout, new bank details, the ask not to pay, a changed record, an unverified sender or emails it could not read in full, and otherwise closes it only if no supplier email reports the payment missing.
- An escalated invoice is closed by a person through `closeIncident` once the bank reports it paid once: by PayOnce's original, by a replacement whose close the resume above did not make, by an outside payout that pays it (`payoutPays`) after every payment PayOnce sent failed, or by a paid transfer under one of its request ids that does not match it (`paidMismatched`). Without a payment, a person closes it without paying once nothing for it is live at the bank (see above). `pendingClose` says when either applies. Closing sends nothing and is not bound to terms.
- A settled or rejected invoice is left alone on resume: the look syncs its payments and outside payouts and reads new emails, then decides nothing and sends nothing, and `retry` refuses one inside the lease. The look leaves a rejected invoice that never sent a payment at once, before any payout sync or email read.

## Uploaded emails

- A person uploads an `.eml` file or pastes raw source on the page. There is no CLI for it. `parseEmail` works on bytes with no dependency, never throws on input and refuses with PayOnce's own words: over 2 MiB, an Outlook `.msg`, text that is not raw source (the first line must be a header field, and the top headers must have a From, Subject or Content-Type), no blank line within 64 KiB of headers, headers over 256 KiB in all, more than 300 fields in one header block, a From, Reply-To, Content-Type or Content-Transfer-Encoding field over 16 KiB, more than 32 parameters in one header, 100 MIME parts, multipart nesting deeper than 8, a bad or colliding boundary. Every scan moves forward, a style or script nested in one already read inside `<svg>` or `<math>` is not read again (it makes the email partial instead), and no regex can backtrack on a long run, so the work is linear. The slowest 2 MiB worst case, an unclosed style full of strings, takes about 200 ms to parse (215 ms at most measured).
- The server parses each upload with `parseUpload` in a worker thread, one at a time. At most four uploads wait behind the one being parsed, because each holds its bytes. An upload takes its place (`takeParsePlace`) before its body is read, so a body still being read, up to 3 MB, counts as waiting too. The next is refused with 503, "PayOnce is reading other emails, try again in a moment", before its body is read or anything is kept. The body of an email upload or a pay run file has 30 seconds to arrive (`UPLOAD_BODY_MS`). Past that `readJson` refuses it with 408, "The upload took more than 30 seconds to arrive, so PayOnce stopped reading it and kept nothing", the upload gives its place back, and the connection closes once the answer is sent. A slow sender therefore holds a place for at most 30 seconds instead of Node's five minute request timeout. Any error answer sent before a request's body was read to its end closes the connection. The parse has a 2 second budget, counted from when the worker is ready, and a 256 MB heap limit (`resourceLimits`). Past either, the worker is terminated, nothing is kept and the upload is refused with "PayOnce gave up reading this email", the reason (time or memory) and what to do. So a slow path nobody has found yet refuses one upload instead of stalling the dispatcher, the watcher and the page. Starting a worker takes about 0.1 s, and through the worker the worst cases answer in under half a second (430 to 470 ms measured).
- Headers: unfolded, raw UTF-8 decoded, RFC 2047 words decoded only in the subject, display names, file names and the From line as written (`fromAsWritten`, which is only shown). From and Reply-To use a strict ASCII grammar: two From fields or two Reply-To fields, more than one From mailbox or more than five Reply-To mailboxes, groups, a quoted local part, an address literal or anything outside ASCII give `SENDER_UNREADABLE` or `REPLY_TO_UNREADABLE`, which the sender check flags. The display name is never compared, but a client shows it, so both readers get it as `fromName` (the keyword check reads it with the subject, the model in a `<from_name>` tag) and the page shows it as "Name in the email (not checked)". The Sender header is ignored: only From and Reply-To are read and checked.
- Every text part is read, plain and HTML; a part is dropped only when it is identical to one already read after whitespace and case are collapsed, and a `multipart/alternative` that kept two gets `versions-differ`. Charsets go through `TextDecoder` under WHATWG labels, with four aliases; `utf-7`, `x-user-defined` and labels it refuses mark the part undecodable. Base64 decodes across early padding. Pasted source is UTF-8 for unencoded parts. `multipart/signed` reads its second part as the signature only for pgp and pkcs7 signature types.
- HTML: script and style content is left out of the text, except inside `<svg>` and `<math>`, where it is read as text too. Comments end at `-->` or `--!>` or the end of input, nothing in them opens or closes an element, and their text is kept. Every string in a style block or `style=""` attribute (CSS escapes decoded), style text that is not CSS PayOnce can parse, and every script's text go to `styleText`, "text found inside styles", which the reader reads and the page shows. Font names cost nothing there. A form field's text is read as `[form field: ...]`, beside an image's alt text: an `<input>`'s `value`, and the `placeholder` of an `<input>` or `<textarea>`. Inside `<svg>` and `<math>`, `<![CDATA[` is text up to its `]]>` or the end of input; elsewhere it is a bogus comment.
- One fail-closed rule for CSS: anything CSS could make a client show that is not a string PayOnce took out makes the email partial. That is a `content` value with anything but strings, comments, `none`, `normal` or `!important`; `counter()`, `counters()` or `attr()` anywhere; an `@font-face` with `src` (Outlook's blocks with only `font-family` and `panose-1` are fine); `@counter-style`; `unicode-bidi` other than `normal` and `<bdo>`; a style or script nested in one already read inside `<svg>` or `<math>`; `@import`, a linked style sheet, or a URL in `url()`, `src()`, `image()` or `image-set()` outside the email (not `cid:`, `data:` or a fragment); and CSS left open: a comment, a string or an unquoted `url(` with no end. A `<style>` with no closing tag is not partial by itself. Its content runs to the end of the input and is read as text, and the rest of the input is scanned as CSS once, at the first such style, under this rule. No special case is added beyond this rule.
- PayOnce does not reproduce a mail client's layout. Reordering (flex `order`, bidi in SVG, positioning) and list numbering can make what a person sees differ in order from what the reader gets. That is accepted because no protection depends on rendering: bank details change only through a callback to the number on file, the sender check works on addresses, approvals bind the account read from Airwallex, and findings only add caution.
- `partial` is set by any note in `PARTIAL_NOTES`: text past 32,000 characters, style text past 8,000, a text part sent as an attachment (or `text/calendar` and the like, a `message/*` part such as a delivery report, or Outlook's TNEF `winmail.dat`), a forwarded `message/rfc822`, encrypted or opaque-signed mail, more than 16 text parts, an undecodable part, a skipped header line, a line among the email's own headers that is not a field (`header-text`: that line and the lines after it, up to the blank line, are read as text, and those that are fields are read as fields too), a Content-Type that cannot be parsed (`odd-type`: the part is read as plain text, so HTML in it skips the CSS rule), a repeated Content-Type or Content-Transfer-Encoding, any parameter given twice in a Content-Type or Content-Disposition (a boundary, a charset or a file name among them), an encoded header in a refused charset, a signed section with more than two parts, and the CSS rule above. Notes are codes kept outside the body, so a sender cannot forge one.
- Attachments are listed by name, type and size from the encoded length, and never decoded, stored or opened. Links are never followed and images never loaded.
- Matching (`candidatesFor`) reads the subject, the body and attachment names, never the sender, amount or supplier. Tokens with a digit (up to 5,000, each at most 128 characters), the same without a file extension, and a word followed by a number ("inv #5001") are looked up by `numberOf` keys, so exact is `sameNumberExactly` and near is `sameInvoiceNumber`. An invoice is offered first only when exactly one invoice matches, in any state, that invoice is open or escalated, and its number was not found as all digits next to other digits. Nothing is delivered by itself: a person picks the invoice, or types another, and confirms. The page keeps that pick, the typed number and the name across polls that rebuild the card, drops a pick that is no longer offered instead of moving it to the suggestion, and names the invoice on the button ("Deliver to INV-...").
- `deliverUpload` runs in the invoice's turn. `Ledger.deliverUpload` moves the upload from waiting to delivered, adds the email and makes an open or escalated invoice's next look due, in one transaction. The timeline then says who uploaded and delivered it, the sender and Reply-To check, text nobody read, another invoice it names, an upload with the same Message-ID, and for a closed invoice that the email is on file and does not reopen it. PayOnce's words come first and the subject last.
- Each new email is read on its own and ORed with the stored findings, so findings only ever add caution. The timeline line says what the emails read in that look found ("Read 1 new email: ...") and, when that differs, the invoice's findings so far. The reader has a third finding, `asksNotToPay` (hold, cancel or not pay, sent in error, paid another way), which escalates. An email with `partial` escalates with "part of a supplier email could not be read".
- While the `asksNotToPay` finding is on file, the escalation reason names it. `namingNotToPay` adds `NOT_TO_PAY_CLAUSE` last ("<reason>, and the supplier asks to hold, cancel or not pay this invoice") to any reason that does not already start with `NOT_TO_PAY_REASON`. For a replacement it runs in `withFloorReason`, after the floor and second-bill clauses, and in the terms `requestedDecision` rebuilds; it adds something only when a payout sent outside PayOnce or new bank details came first in the policy. `assess` adds it to the decision line as well. The floor and second-bill clauses stay off that line, because their standing warnings say them. For a held invoice, `continueHeld` rewords the stored reason with `Ledger.rewordEscalation`, which changes only an invoice still escalated with the reason the look read, and writes a decision line. When it changes nothing, another process changed the invoice since the look read it, so the look opens no request on the old reason and comes again at once. The approval request, the alert and the approval card then name the ask, and a person can still approve paying. Without the finding nothing is added, so every other invoice keeps its terms and its binding.
- An invoice with no supplier domain on file (a pay run row without `supplier_domain`, a found payout) flags every sender.
- An invoice with any email on file before its first payment is held for a person (`EMAILS_BEFORE_PAYMENT_REASON`), pay run rows waiting their turn included. A held invoice reads its emails in `continueHeld`, opens no request until they are read (and looks again a minute later after a reader failure, or at once when another process delivered an email while the others were being read), and its `HeldPaymentTerms.evidence.emails` carries the evidence, added only when it has emails, so other held invoices keep their binding.
- `emailEvidence` in approval terms is the findings' summary, the number of emails on file, how many have text PayOnce could not read and how many senders the check flags. It names no address. Every new email changes it, so it voids an open approval. A replacement request opened before the count existed is replaced once. Its timeline line says only why the request no longer matches. The step that withdraws the request, opens a new one or ends approvals given on it says so, once. The approval card and `pnpm approve` show it for a held invoice as for a replacement, and `pendingClose` gives it as `CloseReview.emails`, which the close card and `pnpm close` show.
- `useApproval`, `releaseFor` and the automatic replacement's transaction spend nothing when the invoice's email count differs from the one the look assessed.

## Names

- Every name a person types goes through `personName` in `src/approvers.ts`: who started an incident, an approver, who uploaded or cancelled a pay run, who recorded a callback, who ended an outage, who uploaded, delivered or dismissed an email, who created, copied, sent or dismissed a draft, and who closed an invoice. It trims the name, collapses runs of spaces and accepts only ASCII letters, digits, spaces, dots, hyphens, apostrophes and underscores, 1 to 80 characters with at least one letter or digit. Anything else is refused with `NAME_RULE` (`NameError`), so a zero-width space, a bidi control or a Cyrillic letter cannot make a name that reads as someone else's. The normal form is what PayOnce records. Underscores are there for login names.
- The check runs in the functions that record the name (`checkSigner`, `closeIncident`, `uploadRun`, `cancelRun`, `endOutage`, `recordBankChange`, `createDraft`, `markDraft`, `storeUpload`, `deliverUpload`, `openScenario`, `explainBreaks`), so the page and the CLI refuse the same names. The server's `name` helper runs it first and answers 400 with the rule, and `pnpm recover`, `pnpm close` and `pnpm payrun upload` run it before they record or send anything, `pnpm recover` saying when the login name it uses without a NAME is not one, and asking for NAME. Who a person spoke to on a callback is the supplier's contact, not a PayOnce name, and is not checked this way.
- `APPROVERS` names follow the same rule once each run of whitespace in an entry, a tab or U+FEFF included, is one space, or the list cannot be read and every approval is refused, because nobody could type a listed name the rule refuses. So does a list with two names `sameName` takes for one person, such as `Alex` and `alex.`, and the message names both. The start-up line and every refusal quote the entry, with any character outside printable ASCII written as its code point (`Al\u{200B}ex`), and give the rule.
- `sameName` says two names are one person when both follow the rule and their letters, digits and the spaces between words match, lowercased, with other characters dropped and runs of spaces collapsed, so `Alex.` and `alex` are one person, and so are `Mary-Jane` and `MaryJane`. A stored name that does not follow the rule (`knownName` gives null), such as a `started_by`, a callback recorder or an uploader written before names were checked, is nobody PayOnce knows: it bars nobody, the payment needs two approvers as when `started_by` is null (`signoffsNeeded`, and `runRule` for an uploader), and the why facts give the starter as not known. Names already in the ledger are left as they are, and the page shows each one through `whyText` (see Supplier view).

## Accounts

- Two keys name bank details. `accountKeyOf` hashes every field (`bankDetailsKey`). Approval terms (`accountKey`), run terms and every stored `account_key` carry it, so a binding pins exactly the details a person saw. `routeKeyOf` says where the money goes. It hashes every field except `NOT_ROUTING_FIELDS`, so a field nobody listed counts, each string read with spaces dropped and upper-cased, and every key starts with `ROUTE_SCHEME` (`r2:`). `NOT_ROUTING_FIELDS` holds only `bank_name`, which Airwallex rewrites from the routing number when a record is updated (seen on 2026-10-28). A field joins the list only with evidence that it cannot route money, written beside it in `assess.ts`.
- Wherever a decision or an approval pinned an account, PayOnce compares the full key: `requireAccount` (every replacement, a held invoice's release, every retry, so before `useApproval` and `releaseFor` spend anything), a run row's approved key in `startPayment` and `continueHeld`, `checkAccount` on every transfer, and `sameAccount` in held terms. A bank name changed after an approval therefore voids it, and the next look opens a new request.
- The route key is for the tests that would otherwise stop a supplier being paid after such a change: `sameBankDetails` (a replacement's new bank details) and its warning, the first-payment hold and `payeeRule` against `lastPaidTransfer`, the callback's nothing-to-verify and read-back checks, `verifiedBankChange`, `bankChangeRecorders` and `barredFrom`, the pay run account checks, `payeeOf` and the supplier view.
- Route keys sit beside the full keys and never in terms, so no binding changed when they were added: `attempts.route_key` (written by `openAttempt` from the record its caller just checked) and `sent_route`, `outside_payouts.sent_route`, `run_rows.route_key` and `approvals.route_key`. `Ledger.holdsAccount` compares a stored account by its route key when `knownRoute` takes the key, and by its full key otherwise, so a key from another scheme, or none, never passes for the same account. `barredFrom` bars every recorder of a callback for the beneficiary when it cannot read the account's route or the callback's, and `bankChangeRecorders` lists a recorder whose callback details it cannot read.
- `meta.route_scheme` names the scheme the stored keys were built with. When it is not `ROUTE_SCHEME`, the writable open rebuilds them under the write lock that adds columns (`rebuildRoutes`): it clears every route column, then gives each key equal to the full hash of details a callback kept (`applied_key` or `old_details`) the route of those details. The rest stay null. Bump `ROUTE_SCHEME` whenever `routeKeyOf` or `NOT_ROUTING_FIELDS` changes. On a copy of the main ledger the rebuild keyed both checked attempts, and one look per open invoice under main and under this code wrote the same approvals, terms, bindings and lines, byte for byte. Live requests and approvals made by main's code kept their bindings, and the approved ones were spent.

Checked on 2026-11-03 with stubbed Airwallex: after a change to `bank_name` alone, new invoices, a replacement and a pay run row to the supplier were paid as before; after a change to `account_routing_type1` or `local_clearing_system` alone, the first payment was held, the replacement escalated, the run row was skipped and a transfer sent there was marked misdirected, as on main. On a ledger written by the six-field allowlist the route key first used, this code held the first payment and barred the callback's recorder.

## Route advisory

- The advisory is for people and never decides. `decide` does not read it, and a payment that may arrive late is sent, replaced, held or approved exactly as it would be without a due date. PayOnce does not switch routes: a beneficiary record holds one transfer method, and paying another way needs another record. The account checks key on the record (`lastPaidTransfer`, `verifiedBankChange`, `payeeRule`, the run check), so another record is another supplier: no callback recorded for the first counts for it, a callback on an invoice held before paying it is refused while PayOnce has not paid that record, a single incident's first payment to it goes out like any first payment, and a held invoice or a pay run row to it needs two approvers because PayOnce has never paid it.
- `obligations.due_date` is optional, from the start form, `POST /api/incidents` or a pay run row's `due_date`, as YYYY-MM-DD. `dueDateProblem` refuses anything that is not a calendar day from 2000 to 2099. A day in the past is taken, and every estimate says it has passed.
- Business days skip Saturdays and Sundays only. A public holiday counts as a working day, so a payment may arrive a day or more later, and every place that shows an estimate says so. Airwallex's non-trading-days list needs an admin key, which PayOnce does not have. "Today" is this machine's calendar date. A route not in `CORRIDORS` (any country but the US and Germany, or a US clearing system the table does not list) gets an estimate with no days, which says the arrival is not known.
- Every ACH payment gets 0 to 2 days. Airwallex says it sends ACH as Next Day ACH, 1 to 2 days, above 1,000,000 USD or when the payer is outside the US, and this sandbox account's payer is in Singapore. For those payments the earliest day shown is a day early, so one shown as "may arrive late" may arrive late even at its fastest. The latest day is right either way.
- The fee estimate is `latestFee` for the currency and method, labelled as last seen, or that none has been seen. It is shown on the pay run rows and in `pnpm payrun show`, and it is never in terms, so a fee recorded on another invoice cannot void an approval.
- `send` writes a line after every payment it creates, original or replacement: when it usually arrives, counted from the transfer's `created_at` on this machine's calendar, and against the due date when there is one. It is a warning when the payment may arrive late, arrives late even at its fastest, or the due date has passed.
- For an invoice with a due date, `assess` builds `arrival` for a replacement to the record as it is now. The decision line adds it when the original failed and no outside payout is live, and `termsFor` and `heldTermsFor` add it to the terms by a conditional spread after `fx`. The terms and bindings of an invoice with no due date are unchanged. `changedFields` names a change as "arrival estimate". The decision line counts from today, even while an open request keeps an earlier day.
- One day rule: `arrivalFrom` counts an invoice's estimate from the day of its latest request while that request is requested or approved and has not expired, so a look after midnight keeps the binding. Otherwise it counts from today. When `awaitApproval` opens a new request on terms that kept another day, it first counts them from today with `countedFromToday` (`withArrival` and `ifSentOn`), so a new request always counts from the day it opens. It then compares the recounted binding with the latest request again, so a request another process opened today on the same terms is kept, with its signoffs. `escalate` compares the open request with both the terms and their `countedFromToday` version, so on the look that opens a request the `floor` and `second-bill` warnings already say it names them.
- An approval can be spent on an estimate from an earlier day. The day holds while the request is open, which is up to `APPROVAL_TTL_MINUTES` (no cap) plus `APPROVED_USE_WITHIN_MS`. The terms say "if sent on" that day, so they stay true as written. When that day is before today, the approval cards, `pnpm approve` and `pnpm payrun approve` add when the payment usually arrives if it is sent today. For a route with no figures they add a line only when the due date has passed since that day. That line is not in the terms.

## Pay runs

- A run file names each row's beneficiary by id, with the supplier, the amount (major units, a dot, at most two decimals, parsed as a string so nothing is rounded), a two-decimal currency, and optionally the method, `due_date`, `sandbox_outcome` and `supplier_domain` (a plain ASCII domain, only A to Z lowercased; anything else is a row problem). A due date `dueDateProblem` refuses skips the row. A cell with a line break ("The X cell has a line break in it"), one over 100 characters ("The X cell is longer than 100 characters"), and one with a control character, a format character, a default-ignorable or a tag character ("The X cell has a control character or a character nothing draws in it") is a row problem that names the column. The supplier cell alone may hold U+200C and U+200D (zero-width non-joiner and joiner, which Persian names and emoji sequences need) and the variation selectors U+FE00 to U+FE0F (`NAME_JOINERS`); bidi controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069), the tag block and every other format or default-ignorable character stay refused there, and every other cell refuses the joiners and selectors as well. A cell that fails any of these checks is never repeated in a reason: it reads as empty for the other checks, which add no second problem for it, so a reason repeats only a cell that passed all three. Nothing else is read from a file: no bank details and no phone number. An unknown or repeated column, a missing required column, an unclosed quote, no rows, more than 50 rows or more than 40,000 characters refuses the file and stores nothing. A problem in the header names the header's line, and an unclosed quote names the line it opened on. A problem with the file as a whole (no name, empty, no rows, too many rows or characters) has no line. The unknown-column problem prints the column's name through `printable`, and `cleanFileName` drops C0 and C1 controls, format and default-ignorable characters from the file name.
- `checkRows` skips a row, with every reason found, for a cell problem; an invoice number in the ledger exactly (`alreadyInLedger`), or by `sameNumberExactly` for the same supplier whatever the amount; a number on an earlier row (exactly, or by `sameNumberExactly` for the same beneficiary); an earlier row `sameBillAndNumber` matches; a beneficiary Airwallex does not have or with no bank details; a supplier cell that is not the record's `account_name` once case, spacing and punctuation are dropped; a currency other than the record's `account_currency`; a method the record does not take, or none when it takes both; or bank details that do not go where the last paid transfer went (`routeKeyOf` of both) with no `verifiedBankChange` for the record. The skip message for a changed account says to check with the supplier, pay outside PayOnce, or restore the old details, because no callback can be recorded outside an incident.
- `lastPaidTransfer` is the latest paid attempt on an `origin = 'payonce'` invoice to the beneficiary that kept an `account_key` and is not `misdirected`, with that key, so a payment that went out unchecked never becomes the account PayOnce last paid. `payeeRule` and the first-payment hold compare the record with that key and read no transfer. `checkRows` reads that transfer from Airwallex and compares the account it went to with the record (`readPayees`); the same read gives the skip message. With no checked payment to the beneficiary it takes the one `lastPaidUnchecked` finds, paid before attempts kept their account, as before the column. A row to a beneficiary with neither is a new payee, and so is one to a beneficiary PayOnce has never paid on a person's approval (`paidOnApproval`), whatever it paid by itself; the account check still compares with the last payment, automatic or not. A row whose account a callback verified carries `bankChange`. A pay row keeps the record's `routeKey` in `run_rows.route_key`, and a release keeps it only when the row's last check read the account the run approved.
- A row that `likelyDuplicates` matches against the ledger is a pay row with `heldFor` listing the matches. It counts in the totals, is released with the run, and `startPayment` holds it when it comes to send it. `likelyDuplicates` itself is unchanged.
- The cash check runs per currency over the pay rows: one `getBalances` read, less `committedMinor(currency, { runId })`, less the rows and their fees (`latestFee` by method, 0 and "not known" when none is recorded). When that leaves less than the floor, every row in the currency is skipped with the shortfall in the reason. A skipped row goes through `skipRow`, which clears `heldFor`, `newPayee` and `bankChangeId`, because those only matter on a row that pays. A currency with no floor set does not block, and the terms carry `reserveFloorMinor: null`. An unreadable `RESERVE_FLOORS`, or no balance in the currency, skips the currency's rows.
- Only one run waits at a time (`one_waiting_run`), and a file whose run is not cancelled cannot be uploaded again (`one_live_run_per_file`). Both are checked before Airwallex is read and again inside `createRun`'s transaction, which also skips a row whose number reached the ledger meanwhile. `POST /api/incidents` refuses a number on the waiting run's pay rows.
- `RunTerms` hold every pay row in file order (line, invoice, amount, currency, beneficiary, method, `payTo`, `accountKey`, `heldFor`, `bankChange`, `supplierDomain` on a row that gives one, and `arrival` for a row with a due date) and a total per currency with its floor. Skipped rows, new-payee flags, sandbox outcomes, fees and how many approvers are needed are not in the terms. A file with no due dates and no domains binds as it did before either column.
- Every pay row gets `arrival`, stored in `run_rows.arrival` and shown on the rows card. A check counts it from the day of the run's latest request while that request is requested or approved and has not expired, so a check after midnight keeps the request and its signoffs. Otherwise it counts from today. When `settleRunRequest` opens a new request on rows that count from another day, it counts them from today first and rewrites `run_rows.arrival` with `setRunArrivals`, then compares the recounted binding again and keeps a request another process opened today on the same rows. `releaseRun` checks again counting from the day in the approved terms, so a release after midnight still matches, and a refused release stores rows counted from today. A released row keeps its due date on the obligation.
- `runRule`: two approvers when a row pays a new payee ("which PayOnce has never paid on a person's approval"), when a row pays a callback-verified account, when a row's `supplier_domain` has a caution, when any currency's total is above `TWO_APPROVERS_ABOVE`, or when the uploader's stored name does not follow the name rule (`knownName`). `domainChecks` gives a caution when the domain differs from the latest invoice to the beneficiary with one, when the run gives the same beneficiary another domain, or when it is the first domain for a beneficiary PayOnce has paid once. A first domain for a beneficiary never paid gets a note only. The approval card and `pnpm payrun show` and `approve` show each row's domain with its caution or note. Limits are checked against the largest currency total (`runAmount`, which `largestTotal` shows), because limits are bare numbers. `runBarred`: the uploader, and the callback recorders of every `bankChange` row. Approving follows `approvePayment`: the request on screen, `checkSigner`, `signOffRun`, the binding.
- A run request expires after `APPROVAL_TTL_MINUTES` and is not renewed by itself. `recheckRun` ("Check again", `pnpm payrun check`) runs every check, then in one transaction (`setRunRows` running `settleRunRequest`) rewrites the rows and keeps a request, requested or approved, with the same binding that has not expired. Otherwise it opens a new one, saying when signoffs no longer count. With nothing left to pay, or too few eligible approvers, it opens none and says why. It is refused while the run's latest request is approved and has not expired, because the release pays those rows.
- `releaseRun` runs in the run's turn (`runKey`). It checks every row again. If the approval expired, the binding differs, or `signoffProblem` finds a problem, the approval is voided and the rows rewritten in one transaction, which changes nothing if another process has released the run or opened a newer request since, and the run waits for a person to check it again; no request opens by itself. Otherwise it takes the lease of every currency the run pays, in code order, and runs the cash check again on a fresh balance. A shortfall voids the approval and the run waits for a person. Else `Ledger.releaseRun` spends the approval and marks the run released, writes each pay row as an `open` invoice (supplier = the record's account name, `started_by` = the uploader, `run_row_id`, `look_at` now, the approved `supplierDomain` or none, no phone) with its first chained line naming the run, row, file hash, approvers, request and binding, and sets each released row's `account_key` and `pay_to` from the approved terms, all in one transaction that first checks every lease. A check that rewrote the rows meanwhile cannot change the account a row pays. A plain INSERT that fails on a taken number rolls back to a savepoint and drops that row. Timeline lines on the run come after the commit, except the release line, written in the transaction.
- After the commit the release wakes each released invoice in file order with the run's turn (`wake(invoiceId, true)`) and waits for it before the next, so a run never sends a burst. The approve route and the watcher start a release without awaiting it. `pnpm payrun approve` only signs, and the server's watcher releases the run on its next check; a run approved while no server runs waits, and is void once its use window has passed.
- A released row's first look with the run's turn calls `startFirst`, which sends the original through `startPayment` with the row's `accountKey`. Under the lease it reads the balance, ties unseen payouts and reads the record last. Then, in one transaction, it checks that the invoice is still open with no attempt, the record's account (a missing beneficiary or other details holds the row), `likelyDuplicates`, `sameNumberForSupplier`, a live outside payout and the floor (the committed money without this invoice, so the run's other unsent rows count), and opens the attempt. A row that fails any of these is held, with `CASH_HOLD_REASON` for the floor and `RUN_ACCOUNT_CHANGED_REASON` for other details on the record.
- Only the release, or the server's watcher once the run's key is not busy, sends a run row, because only they wake it with the run's turn. Any other look at an unsent row (the resume and bank-change routes, a webhook, the sweep, `pnpm recover`'s watcher) notes that it waits for its turn and makes its next look due, so the server's watcher gives it one. `pnpm recover` refuses a run invoice that has not sent.
- A retry of a pending original on a run invoice checks the key the attempt keeps: a used `pay` approval's account, else the row's `accountKey`.
- `continueHeld` on a run invoice: a missing beneficiary, or a record that no longer holds the row's account and has no verified callback, withdraws any request and waits for a person to close it. On any other held invoice, a record that no longer holds the account `lastPaidTransfer` kept writes a `last-paid` warning. With no verified callback it also withdraws any request and waits for a callback to the number on file (or, with none, for a person to close it or restore the details). With a callback, the request's `HeldPaymentTerms.evidence.bankChange` carries it, added only then so other held invoices keep their binding, and its recorder is barred. On every held invoice two approvers are needed when PayOnce has never paid the beneficiary, paid it only before it kept which account each payment went to, or last paid it another account (`payeeRule`), as for the run itself.
- `cancelRun` works only on a waiting run. It voids the open request and drops the pay rows, so their numbers are free again. Anyone with a name and a note may cancel.
- The sandbox bank reads a run row's `sandbox_outcome` from the ledger through `runRowOf`, so it survives a restart. The engine never reads it, and it is not in the terms.

## Rail outages

- A rail is `(transfer_currency, transfer_method)` upper-cased, as Airwallex reports them. For PayOnce's own payments that is `(obligations.currency, obligations.transfer_method)`, which every gate reads. An `eur-from-usd` payment runs on EUR SWIFT while its lease is on USD.
- A failure counts when a transfer reads FAILED or CANCELLED with `failure.code` in `RAIL_FAILURE_CODES`. Mixed codes add up, and the outage records the codes it counted (`outages.codes`). Account codes, unknown codes and a transfer with no code never count. Webhook bodies never count.
- `railFailureSeen` is called by the look (after the `bank` line of each attempt its first pass reads as failed, and in `syncOutsidePayouts` for an outside payout that reads failed; the later pass that records a kept transfer again does not call it, and the sweep covers those) and by the sweep for every listed transfer, after it is tied or taken on so the failure names its invoice. Not by the watcher, the listing before a payment or a webhook. It never throws: a failure it could not record is recorded by the next look or sweep.
- A failure is dated by `failed_at`: the transfer's `updated_at` when Airwallex gives one PayOnce can read (when it last changed the transfer, so when it failed, or when it was cancelled a few seconds later), and otherwise when PayOnce first reads it (`seen_at`). It is recorded only if the transfer was created at or after `meta.outages_since` (set on the first open with this code, so an upgraded ledger never counts its old failures). A failure dated by `updated_at` is also left out once that time is a window old, since it could never count. One without `updated_at` is left out once `created_at` plus the method's bank deadline plus the window has passed, so failures read at catch-up after downtime do not count. A `created_at` PayOnce cannot read counts. The window counts `failed_at` (`seen_at` on rows from before the column).
- Two limits. The fallback keeps failures read at catch-up out only while bank deadlines are short, minutes as in the sandbox: with deadlines of days, failures with no `updated_at` read late after downtime are dated when read and can declare an outage together. And PayOnce compares Airwallex's times with its own clock: a host clock more than the window ahead of Airwallex (30 minutes by default) leaves every dated failure out, and one more than the bank deadline plus the window ahead (33 minutes by default for LOCAL, 35 for SWIFT) leaves every undated one out, so no outage is ever declared. A clock behind Airwallex keeps failures counting for longer than the window.
- A payee is `payeeOf`: the payout's `routeKeyOf` (see Accounts), or `beneficiary:<id>` when a payout has none of the account fields (`ACCOUNT_FIELDS`). Two beneficiary records for one account are one payee, and a `bank_name` Airwallex rewrote makes no new one. A payee recorded under an older scheme keeps its key, so for one window after an upgrade the same account can count as two payees, never fewer.
- `Ledger.recordRailFailure`, in one `BEGIN IMMEDIATE`: `INSERT OR IGNORE` the failure (the transfer id is the key, so FAILED then CANCELLED, or two processes, record it once); if the rail has no active outage, count the distinct payees of the rail's failures dated (`failed_at`, else `seen_at`) after `max(now - window, the rail's last ended_at)`; at the threshold, insert the outage, a `counted` hold for each counted invoice and the declared line on its timeline through `appendEvent`. Failures recorded while an outage is active do not count toward the next one, unless Airwallex dated one after the end by this machine's clock, as when Airwallex's clock is ahead (see the two limits above). The partial unique index `one_active_outage_per_rail` backs this up.
- The gate is `openAttempt`: inside its transaction, after `requireLease`, it throws `RailOutageError` on a rail with an active outage. That covers `startPayment`, `replaceUnderLock`, `useApproval` and `releaseFor`, each of which rolls back, so an approval it would have spent stays `approved`. `Ledger.releaseRun` throws it too when any release row's rail has one. An attempt opened before the declaration is a payment already decided: `sendAttempt` and the retry in `look` are not gated.
- Ledger reads before the lease save Airwallex calls and give the hold its kind: `startPayment` checks first (`original`, so a new original waits open with no attempt and no hold for a person), `continueEscalated` and `continueHeld` after `voidIfStale` (`approved`), and `releaseRun` before `checkRows` (`run`). `replaceUnderLock` reads the outage inside its transaction after `decide` says replace, and `escalateForOutage` writes `Escalate: OUTAGE_REASON`, the `replacement` hold and calls `escalate(..., OUTAGE_REASON)`. If the outage ended in the moment between, the next look is due at once and replaces as usual.
- With `APPROVERS` unset or unreadable, an outage turns every replacement PayOnce would have sent by itself into an escalation nobody can approve: `escalate` opens no request, every approval is refused, and ending the outage does not release it, because an escalated invoice pays only on an approval. Those invoices wait until the list is set. First payments and pay runs held by the outage are not affected this way: they go out after the end.
- No binding depends on an outage. `OUTAGE_REASON` is only `obligations.escalation_reason`, written through `escalate`'s `reason` argument, only for an open invoice whose original failed (never `heldBeforePaying`, so `heldTermsFor` never reads it). The request's terms come from the replace decision through `termsOf`, so `evidence.reason` reads "original failed, a resend can fix it and the beneficiary details are unchanged", and later looks rebuild the same terms. Invoices on other rails, and invoices on the rail escalated for another reason, get identical decisions, terms and bindings.
- `resumeIncident` catches `RailOutageError`: it postpones the due look a minute (`postponeDueLook`) and calls `waitOnOutage`, which writes the hold line once per outage per invoice and the standing `waiting` line, naming a kept approval and when it stops counting. `holdForOutage` writes both in one transaction, only while the outage is active, so neither lands after the end line; the standing line is passed as a `StandingLine` whose `wanted` is `lineWanted`, the check `note` makes. `holdRun` writes a run's `release` line the same way. If the outage has ended, the next look is due at once. `runScenario` does the same for its first send and records the scenario's outcome with `expectOriginal`, so the original sent after the end gets it. No `error` line is written.
- Approvals keep expiring during an outage. One that expires is voided by `voidIfStale` and the next look opens a new request on the same terms, as at any other time.
- A pay run with any approved row on a rail with an outage waits whole, its approval neither spent nor void (`holdRun`: one chained `run` hold line on the run's timeline and a standing `release` line). The watcher tries the release once a minute (`RETRY_RELEASE_MS`), each try a ledger read. Only one run waits at a time, so no other run can be uploaded until this one is released or cancelled.
- Ending: `endOutage(ledger, policy, id, name, note, holdingOf)` checks the name with `personName` and trims the note (1 to 200, `cleanLine`). The name must be in `APPROVERS` (`sameName`, recorded as listed) while the list is usable; with `APPROVERS` unset any named person may, and the end line says no approver list was set. While any approval setting cannot be read (`ApprovalPolicy.unreadable`: `APPROVERS`, `TWO_APPROVERS_ABOVE` or `APPROVAL_TTL_MINUTES`), `outageEnders` gives no names and `endOutage` refuses everyone with the reason (`why` `approver`, 403), so a broken setting never opens it to anyone. `Ledger.endOutage`, in one transaction, first records a hold for each invoice and run `holdingOf` lists (what the board shows as held, read while the outage is still active), then conditionally updates the outage to `ended`, writes the end line on every invoice and run with a hold, `counted` holds included (chained), and sets each held open or escalated invoice's `look_at` to now, so a watcher in any process picks it up. The end line says PayOnce looks at the invoice now only for an open or escalated one; a settled or rejected one is told it is already closed and PayOnce sends nothing for it. Two ends at once end it once; the other gets `ended` (409 with `endedBy` and `endedAt`). The server then wakes the held invoices (an unsent run row is left to the watcher's turn) and starts the held runs' release.
- After the end every check runs again on the next look: a waiting original goes through `startPayment` (duplicates, outside payouts, emails, FX hold, a run row's account and floor), an approval is spent if it still matches or voided for its real reason, an invoice the outage escalated stays escalated and needs its approval.
- The cash panel lists a single incident's original waiting on an outage (open, no attempt, not a run row, an active outage on its rail) as `waiting-outage`. It is in the second headroom figure only, not in `FIRM_KINDS`, so `committedMinor`, the floor reasons and every binding are unchanged. A released run row waiting on an outage is already a `pay-run` line. The incident board shows both as first payments the outage holds (see Outages on the board).
- After upgrading, restart every PayOnce process: an older one ignores outages.

## Reconciliation

- Reconciliation reads and records. It moves no money, takes no currency lease, runs in no invoice's turn, and writes no invoice, attempt, approval, binding, timeline line, cash panel figure or board entry. It writes only its own tables in `src/recon-store.ts`, its chain, `recon_events`, and its own keys in `meta`. Nothing in the engine, the policy, the board or the cash panel reads them. The outbox reads its refund missing breaks, read-only, to offer `refund-trace`.
- A check reads, with GETs through `AirwallexClient`, in this order: `balances/current`, `balances/history?account_type=cash` for each window (no currency, so every wallet at once, 500 a page, cursor paging), `balances/current` again, `listTransfersSince(meta.started_at)`, then by id at most 5 transfers that stored payout, fee or reversal movements name and no check has read. A 404, or an answer for another id, stores that id as not a transfer, and it is never asked again. Any other 4xx except 401, 403 and 429 records the id in `recon_lookups` as refused, with the status: the check carries on, the movement waits as "a transfer Airwallex refused to show", and the id is asked again only 10 minutes later (`REFUSED_RETRY_MS`, as `recordMissingFees` does), behind ids never asked, so one refused id cannot hold up the rest. A 401, 403, 429, 5xx or lost connection stops the check, as any other failed read does: `failRun` records the cleaned error on the run and nothing else changes.
- Windows are at most 7 days, because Airwallex refuses a longer range with `time_range_exceed`, and both ends are whole seconds. The last ends 10 minutes after now. A full read (the first check, and once `meta.recon_full_read_at` is 24 hours old) covers every window from `started_at` floored to the second, each starting a minute before the last one ends (`WINDOW_OVERLAP_MS`), so a movement exactly on an edge is read whether Airwallex counts a range's start or its end. Movements are upserted by id, so one read twice is stored once. Any other check reads one window, from the later of that start and 7 days before its end.
- `wallet_movements` is upserted by Airwallex's row id. A read replaces what is stored in the range its windows cover together (`replacedRange`): a stored movement whose `posted_ms` falls in it and that no window listed is deleted, so a movement one window lists on its edge and the next leaves out stays. A seven-day read leaves the first minute of its window alone, because earlier reads covered that edge from inside a window. Times are UTC milliseconds from `airwallexTime`, which reads the sandbox's `+0800` offset, so nothing compares Airwallex's text with a UTC bound. A row whose id, currency or time cannot be read is kept as unreadable, with no amount or balance, under `x` plus a hash of the row when its id cannot be used, and dated to its window's start when its time cannot be read. `description` and `reference` are never read or stored. `source`, `source_type`, `transaction_type`, the short reference, the status and the method are kept only when they match fixed patterns.
- Matching is by transfer id only: `attempts.transfer_id`, `attempts.mismatched_transfer_id` and `outside_payouts.transfer_id`, never a request id or a reference. A found payout's original (origin `outside`) counts as sent outside PayOnce. A transfer kept beside an attempt because it does not match the invoice is labelled and counted apart (`mismatched`), never as PayOnce's payment. Hold rows (the six types Airwallex's bank feed guide names, and source type `PAYMENT_RESERVE`) are matched to no transfer and make no break. They count only in the running balance, and the wallet's totals show them apart from money in and out. A debit is compared with `debitOf`, and a `FEE` row with `feeOf`, never with the fee in the ledger. A refund must be the whole debit back in the wallet it left, or, for a transfer that converts, the transfer amount in the transfer currency.
- Windows for a transfer come from the bank deadlines (`deadlineMinutes`): its debit is due at `created_at` plus the deadline, and a failed transfer's refund at the earlier of its `updated_at` and the first check that read it failed, plus the deadline. `SCHEDULED` and `OVERDUE` wait with no due time. Inside its window an item is waiting, kept in the run's summary, never a break. A transfer created before `started_at` is matched only for paid-then-returned. A movement PayOnce cannot read holds its transfer for that check, or every transfer in its wallet when its source cannot be read (in every wallet when its currency cannot be read either): none of their breaks opens, changes or clears, and a `balance-gap` already on file for an unreadable wallet keeps its state. The `unreadable-movement` break says which transfers wait.
- Kinds that clear by themselves: `debit-missing`, `refund-missing`, `unreadable-movement`, `balance-gap` (keyed by the first movement where the running balance stops following) and `balance-differs` (the last balance against the available balance read just after the history, checked only when the reads before and after agree; its facts are the difference and the newest movement when that difference was first found, carried while it stands). Kinds that wait for a person: `debited-twice`, `debit-differs`, `fee-differs`, `refund-differs`, `refund-unexpected`, `paid-then-returned`, `untied-payout` (waiting until its debit window ends, so the sweep can tie it) and `unexplained-credit` and `unexplained-debit`. Facts never hold a status, a time or a due time.
- `paid-then-returned` has two subjects. A transfer the ledger ties to an invoice (its own attempt, one kept beside an attempt, or a payout sent outside PayOnce) that the ledger records as paid now, or that was paid when a check read it (`recon_transfers.paid_seen_ms`: set when a check reads it `PAID` or finds the ledger recording it paid, and kept), and that Airwallex now shows failed or cancelled, or gave money back for. Keeping `paid_seen_ms` means a look on a settled invoice that later records the payment as failed cannot hide it. And an invoice the ledger settled that has no payment recorded as paid now (no paid attempt, kept transfer or outside payout), keyed `paid-then-returned:invoice:<id>`, left out when a `paid-then-returned` break on file or found now names one of its transfers. A rejected invoice is closed without paying, so only its transfers can have one. The wording names a kept transfer as kept, and no break reopens the invoice.
- `recordBreaks` keeps one row per key in `pending` or `open` (`one_open_break_per_key`). `debit-missing` and `refund-missing` open with a `found` line on the first live check that finds them (`opensAtOnce`), since each waits out its window first. Every other kind, `balance-gap`, `balance-differs` and `unreadable-movement` included, is `pending` when a live check first finds it, with no line, and opens with a `found` line when the next live check finds the same fingerprint. A pending row the next check does not find is deleted. New facts on an open row update its facts and fingerprint with a `changed` line, so an explanation given on the old fingerprint no longer covers it. A row no longer found is `cleared` when its kind clears by itself, and an `untied-payout` when the ledger now ties its transfer to an invoice (`clearReason`). A kind that waits for a person never clears by itself: it gets `gone_at` and a `gone` line and stays open until a person explains it, with a `back` line if it is found again. A key the check could not look at (`unchecked`) keeps its state.
- `reconcileOffline` matches as of the last committed live check (`lastLiveAt`), not now, so a refund or debit window that ran out since cannot open a break from that read. It opens nothing and never creates or changes a pending row. What it finds new waits until a live check finds it, a pending row keeps the facts the last live check found, and an explained break with new facts waits for the next live check. It still deletes a pending row it no longer finds, which can only delay an opening.
- `explain` runs in one transaction. The route and the CLI first refuse a fingerprint that is not 12 to 64 hex characters with `ExplainInputError` (400). Every id must be open: pending or unknown is `ReconUnknownError` (404), and explained or cleared is `ReconChangedError` (409). The stored fingerprint must start with the one shown (`ReconChangedError`, 409), and all must be one kind (`ReconKindsError`, 400). The name goes through `personName` and the note through `cleanLine`, 1 to 200 characters. Its line is "Break N explained by NAME: NOTE. Facts SHA-256" and the fingerprint's first 12 characters. An explanation holds while the same facts are found with no gap. New facts open a new row with a `reopened` line naming the explained one, which ends its episode. Not found, the episode ends with an `ended` line, and the same facts found after that are a new break.
- A run takes its id under the write lock when it starts. `reconcileOnce` awaits the read from Airwallex (`readAirwallex`) first, outside any transaction. `commit` then stores the read, matches and runs `recordBreaks` in one synchronous `BEGIN IMMEDIATE`, with no await inside. It records the run `stale` and writes nothing else when `meta.recon_committed_run` is higher than its id, so a run that started earlier never undoes a later one.
- `recon_events` is one chain in id order. `hash` is SHA-256 of `prev_hash` followed by the JSON `{at, break_id, kind, message}`, and `meta.recon_events_head` is its running hash, set to the genesis only while the chain has never had a line. `meta.recon_first_line_at` is the first line's time, written with it and never again (a ledger from before the key takes it from its first line when opened). A running hash missing when a line is added starts again from the genesis, unless the line is the chain's first (no line, no first-line key, no restart record and no other break opened before it), and the first restart goes in `meta.recon_events_head_restarted`, which the check reports from then on. The check also reports a chain with no line, or whose line 1 is not the line it started with, as lines removed, and lists every break that has opened with no line, since a break gets its first line when it opens. Anyone who can write the file can still rewrite the chain and its running hash, as with every chain in PayOnce. Line kinds are `found`, `changed`, `back`, `gone`, `cleared`, `reopened`, `explained` and `ended`. `pnpm run audit` checks it after the pay run chains, and says "This ledger has no reconciliation" for a file without the tables. The page's audit line checks it in full at most once a minute, and again whenever its line count or last id changes.
- `ReconRunner` runs one check a minute after `pnpm ui` starts, then every `RECON_EVERY_MINUTES` (default 10, `0` for never; any other value falls back to 10 and the start-up line says why), never two at once in one process. `POST /api/reconcile/run` answers 202, 409 while one runs here, and 429 within a minute of the last start, the timer's included.
- Routes, all through `guard`: `GET /api/reconcile` (`reconReport`: the last committed run, the latest failed or stale run after it, the wallets from that run's summary, the newest 500 open breaks (`MAX_OPEN_SHOWN`), `openCount`, counts by kind and how many are pending, all three with `COUNT(*)`, waiting items, the last 50 explained and the audit line; the page and the CLI give the full counts and say how many are not listed), `GET /api/reconcile/movements?currency=USD` (the 500 newest stored movements, with what explains each now, from the matcher run again with no balances), `POST /api/reconcile/run`, and `POST /api/reconcile/explain` (`{ breaks: [{ id, fingerprint }], explainedBy, note }`; 200 `{ explained }`, 400, 404 `{ unknown }`, 409 `{ changed }`).
- The page has a Reconciliation button in the top bar and the view `#recon`, whose internal id is `recon/`; an invoice called recon is written `#%72econ`, so the two never meet. It shows the last check with Check now, a card per wallet with its movements on request, the breaks that need a person by kind with a checkbox each and a name and note form, what is waiting, the last explanations and the audit line, all as text nodes. It loads only while on screen.
- The alert condition is `recon`, standing while any break is open. Its fingerprint is the highest `recon_events` id of kind `found`, `changed` or `reopened` in any state, so a new or changed break alerts and one clearing or explained does not. The break the alert names is the open one with the newest such line, so a break found once and opened on a later check is named on the alert its own line raised. The title is "N wallet movements need a person", or "The USD balance does not add up from its movements" when that break is `balance-gap` or `balance-differs`. The facts are the count, kind codes with counts (the message adds `KIND_LABELS`), currencies, and that break's kind, currency, invoice and short reference, each checked against its pattern. Counts and currencies come from `COUNT(*)` and `DISTINCT` over every open break (`alertState`), never from a capped list. The link is `#recon`. It is urgent while a `paid-then-returned` is open. ## Metrics

- Metrics are display only. `src/metrics.ts` builds eight tables for a period from the ledger: `7d` and `30d` are 7 or 30 times 24 hours up to now, compared as UTC milliseconds after `Date.parse`, and `all` is every row. Nothing PayOnce decides, alerts on, binds or checks reads a metric, and neither do the board or the cash panel. No Airwallex call, balance or setting goes into one.
- Each table names the time that puts a row in the period. Payments, failures at the bank and fees lost go by the transfer's `bank_created_at`, a refused or never-created payment by `tried_at` (else `opened_at`), and a payout sent outside PayOnce by `found_at`. Incidents started and duplicates held go by the invoice's first timeline line, incidents closed by its latest `closed` line, approvals by the signoff that completed the request, outages by overlapping the period, and breaks by `opened_at`. A row whose time is missing or unreadable is left out of `7d` and `30d` and counted in the `notOnFile` beside it (`started.notOnFile` for incidents started, each row's own for approvals), while `all` includes it. A duration with either end missing or unreadable, or one that comes out negative, counts in its spread's `notOnFile`. A row whose currency is not three capital letters stays out of the money and counts in `unreadable`. Payments and incidents also give `leftOut`, the invoices a time is missing for, each counted once whether that left it out of the rows or out of one or more durations, and the page's and the CLI's note under those two tables show it. The payments table's `unreadable` counts invoices too.
- The tables. Payments PayOnce sent (an attempt with a transfer, not a found payout's original) by currency and kind (`first`, `first-approved`, `replacement-auto`, `replacement-approved`), with what the bank did to the attempt's own payment (`ownLive`, so a mismatched transfer under it counts only in `mismatchedPaid`, once paid), the first payments paid the first time, the invoices paid more than once since the ledger started (paid attempts and paid outside payouts) and bank time to pay. For those invoices, `paidMoreThanOnce.extra` is what each paid payment after the first took, wallet by wallet: the invoice's attempts in rowid order, a found payout's original included, then payouts in the order they were tied, each at the amount and currency `debitOf` stored, else, for PayOnce's own payment, the invoice amount from the invoice's own wallet or the sell amount of the quote it was sent with when the approval it was opened on (else the invoice's latest approval) names that quote and wallet, else counted in `notKnown`. A found payout's original with no stored amount counts in `notKnown`. Paid mismatched transfers are counted apart in `mismatchedPaid`, at their stored amount or not known, never as a second payment. Failures by rail, stage (`bank`, `refused`, `never-created`) and code, `refused` when the attempt has a `failure_code` or a `refused_at`, so a 4xx with no code counts as refused (one from before `refused_at` with no code still counts as never created), the code shown only as five digits or one of `KNOWN_CODES` (else `other`, and `none` for null), with `FAILURE_WORDS`, whether it counts toward an outage and whether a resend can fix it (`RESENDABLE_FAILURE_CODES`). Incidents started by origin and closed by currency and how (`first-time`, `replaced`, `person-paid`, `not-paid`), how long they took from the first line, from the first failed original and with a person, and the reason on file when a person's invoice closed. An original PayOnce marked failed and then found late counts toward the first failure only once the bank has failed its transfer too, and then with no time on file, because its `failed_at` is PayOnce's mark. Approvals given, needing two approvers, spent, voided and waiting, the time to approve per episode (from the first request after the last one given to the signoff that completed one, since a request renews every `APPROVAL_TTL_MINUTES`), and requests open now. Fees lost, by the cash panel's own `attemptLostFee` and `payoutLostFee`. Invoices held as a likely duplicate, by their state now: stopped (rejected), paid (settled), released (open again, approved and paying) or still held (escalated). Outages with how long they ran, payees, rail codes and their holds other than `counted`. Reconciliation breaks by kind and state, with the time to resolve. A median and p90 are by nearest rank, every median has its n, and p90 is null below 10.
- An invoice needed a person when `escalation_reason` is set. `reasonCode` matches the start of the reason against `REASON_LEADS` (the reason grammar in `why-facts.ts`: the fixed parts longest first, then the parts with slots) and takes the first lead that ends the reason or is followed by `, and `, so a lead that holds `, and ` itself is coded whole. Anything else is `other`. Only the code leaves it.
- Every string in an answer is a code from a fixed set, a five-digit failure code, a currency code, an ISO time with a four-digit year, or a fixed label: `FAILURE_WORDS` or one of three fixed phrases by failure code, `RAIL_FAILURE_CODES` by rail code (looked up with `Object.hasOwn`, so a stored code such as `toString` is dropped), `REASON_LABELS` by reason code, and `KIND_LABELS` by break kind. `metricsRead` selects no supplier name, reference, facts, note, approver or timeline message. In SQL it reads stored JSON only inside `CASE WHEN json_valid(...)`, because SQLite evaluates both sides of an AND and a JSON function throws on text that is not JSON: `duplicate_of`'s length, and of an approval's terms only its quote's sell amount, compared with the attempt's quote and wallet in SQL. Outage codes come back as text, and `outageCodes` parses them inside a try.
- `GET /api/metrics?period=7d|30d|all`, 7d when left out, answers 400 "The period is 7d, 30d or all" for anything else. The server keeps the last three answers, keyed by the period, `Ledger.changeStamp()` and the minute. The stamp is `PRAGMA data_version` and `total_changes()`, so another connection's commit, or the server's own write, builds the answer again.
- The page's Metrics button in the top bar opens `#metrics` (internal id `metrics/`; an invoice called metrics is `#%6Detrics`). It has three period buttons with `aria-pressed` and keeps the choice in memory only. It asks for the metrics when the view opens, when the period changes, and then 30 seconds after the last ask, whether that one came back or failed (`state.metricsAsked`), drops an answer or an error for a period no longer shown, and clears the old period's error when another is picked. - `pnpm metrics [7d|30d|all] [json]` opens `payonce.db` read-only. It refuses a missing file and a file `schemaGaps` finds gaps in, needs no `.env`, and prints each table in the page's order with times in UTC, or the route's answer through `printableJson`.

## Ledger

- `src/ledger.ts` uses `node:sqlite`, which ships with Node 24, so there is no database dependency or server.
- The file is `payonce.db` in the working directory and is git-ignored. `pnpm reset` renames it with a timestamp, which is also ignored, so the next run starts empty. The rename fails with `EBUSY` while `pnpm ui` has the file open. Transfers already sent in the sandbox stay there.
- The duplicate lock is the partial unique index `one_live_attempt_per_invoice` on `attempts(invoice_id) WHERE state <> 'failed'`. A violation has `errcode` 2067 and is rethrown as `DuplicatePaymentError`. `Ledger.record` never raises it: an attempt whose bank state would break the lock keeps its failed state (see `paidTwice`). Once the lock is free, the next record takes the bank's state. A failed attempt the bank shows in a status PayOnce does not know is recorded `in_flight`, because such a status counts as live. Beside the index, `insertAttempt` refuses an attempt while `LIVE_ATTEMPT` finds one, with the same error.
- `paidOnce` is true when one attempt is paid and nothing else for the invoice is still with the bank: every other attempt has failed at the bank, or the bank has paid it as well, which the look holds for a person. `settle` closes an obligation only then, and not while an attempt live at the bank has a `rate_mismatch` or `lateBesideLive` finds a late transfer, unless a person closes it. By itself it also refuses while a payout sent outside PayOnce is live (`LIVE_OUTSIDE_PAYOUT`) or a mismatched transfer no person has cleared is on file (`UNCLEARED_MISMATCH`). So a payout another process ties between a look's `syncOutsidePayouts` and its close stops the close, and `closeRefused` hands the invoice to a person instead of looking again (see the mismatched transfers above). It runs those checks and the close in one `BEGIN IMMEDIATE` transaction, and changes only an invoice that is open or escalated and, when the caller names one, still in the state the caller read (`settle(invoiceId, byPerson, from, covered)`: the look passes the state it read, `closeIncident` passes `escalated`). So a late transfer another process records between a look's `paidTwice` check and its close stops the close, and the next look comes at once and holds the invoice for a person. It also voids any approval still open.
- `obligations.escalation_reason` holds the policy's last reason for sending the invoice to a person.
- Approvals live in the `approvals` table with states `requested`, `approved`, `used` and `void`. Each approver's approval is a row in `signoffs` with the binding they approved. `signOff` adds one and marks the request approved once it has `needed` of them, in one transaction, so the server and the CLI cannot both count the last one. `approvals.approver` joins the names for display. The binding is the hash of the terms JSON, so build terms only through `termsFor` to keep the key order stable.
- A new request voids any earlier request or approval for the invoice that is still open. An approval is marked `used` before the payment is tried, so it covers one attempt.
- An approval request is created only when the original has failed, or for a held invoice. `requestApproval` opens one only while the invoice is escalated, in one transaction, so it cannot land on an invoice another process has just closed. `pendingApproval` shows none on an invoice that is not escalated. The duplicate lock still applies to an approved payment.
- Supplier emails and the reader's findings are stored per invoice in `emails` and `email_findings`. The findings record how many emails they cover (`emailsRead`). Only new emails are read, one at a time, and the findings are ORed and reused, so a reader that words its summary differently on a second call cannot void an approval. An uploaded email's row also has `inbox_id`, `reply_to`, `style_text`, `attachments`, `notes` (codes) and `partial`; a fixture email's are empty.
- `inbox` holds uploads: who and when, `source` (`file` or `paste`), the file name, `raw_sha256`, `raw_bytes`, `content_hash` (SHA-256 of the raw bytes read as Latin-1, with CRLF as LF, hashed as UTF-8), Message-ID, sender, display name, From as written, Reply-To, date as written, subject, body, style text, attachments, notes and `partial`. The raw bytes are not kept. `state` is `waiting`, `delivered` (with `invoice_id`, `delivered_by`, `delivered_at`) or `dismissed` (with `dismissed_by`, `dismiss_note`), which is final. Each change is a conditional update on `state = 'waiting'`. The unique index `one_upload_per_email` on `content_hash` refuses a second upload of the same email (`DuplicateUploadError`), and `sameMessageId` lists uploads that share a Message-ID and say something different.
- `attempts.sent_key`, `sent_route` and `sent_ending`, and the same three on `outside_payouts`, are where a transfer went as last read: `accountKeyOf` and `routeKeyOf` its bank details, and the last four characters of `account_number`, else `iban`, kept only as 1 to 4 letters and digits (`sentToOf` in `approval.ts`). Both are null when the transfer carries no bank details, or details that are not an object, such as `null`. They are display only, for the supplier view. `sentToOf` never throws: it checks the value is an object first and catches anything else, so a payout with odd bank details is still tied by `linkOutsidePayout`, the check before every payment and `syncOutsidePayouts`, and still taken on by the sweep. `payments.ts`'s `record()` writes them with `Ledger.recordSentTo`, a `COALESCE` update of its own after `Ledger.record`, inside a try so a failure only prints a warning and never changes the payment step. `payoutMoney` writes them on `linkOutsidePayout` and `recordOutsidePayout`, and the sweep's `adopt` on a found payout's attempt. No decision, term, binding, alert, draft or explainer reads them, except that `outside_payouts.sent_route` can make a paid payout pay its invoice (`payoutPays`). Rows from before stay null until a look reads their transfer again, which only happens to live ones. `obligations_by_beneficiary` indexes `obligations(beneficiary_id)`.
- `webhook_events` holds the id of every webhook event taken, so a redelivered event is ignored. `attemptOf` finds the attempt a transfer belongs to by `request_id` or transfer id.
- Approval evidence includes the email summary, so new emails that change the findings void an approval.
- `events` holds the timeline. A line with a `topic` says how things stand: the decision, what the invoice is waiting on, an approval, the cost of a replacement, a bank-details mismatch, a `last-paid`, `floor` or `second-bill` warning, a held `retry`, or a draft (`outbox:<id>`). Run timelines work the same way, with topics such as `row:<line>` and `release`. `note` skips one when the timeline's last line on that topic says the same and nothing has happened since, so checking an invoice again when nothing has changed adds nothing. A line with no topic records an event and is skipped only when it repeats the line before it.
- On an escalated invoice the decision line says when the policy would now replace or close and why it does not.
- Each timeline line has `prev_hash`, the hash of the invoice's line before it (64 zeros for the first), and `hash`, SHA-256 of `prev_hash` followed by `canonicalEvent`: the JSON `{at, invoice_id, kind, message, topic}` with the keys in that order. `meta.events_head` is the running hash, `sha256(events_head + hash)` for each line in id order, so lines removed from the end of a timeline, or a whole invoice's lines, are caught.
- `addEvent` reads the invoice's last hash, inserts the line and updates the running hash in one `BEGIN IMMEDIATE` transaction, because the CLI and the server write the same file and a step on one invoice writes on others' timelines. `note` runs its dedupe before calling it, outside the lock. The body is the private `appendEvent`. Ledger methods that write a line along with their change call it inside their own transaction: `openObligation`, `adoptPayout`, `releaseRun`, `createDraft`, `markDraft`, `recordRailFailure`, `holdForOutage` and `endOutage`.
- `Ledger.transaction(fn)` runs `fn` in one `BEGIN IMMEDIATE` and throws if a transaction is already open, since `node:sqlite` cannot nest them. Nothing that opens its own transaction (for example `addEvent`, `addRunEvent`, `requestApproval`, `requestRunApproval`, `signOff`, `releaseFor`, `useApproval`, `tryLock`, `adoptPayout`, `settle`, `reject`, `rejectAgain`), and no `note`, runs inside one. Timeline lines are written after the commit, except the ones those Ledger methods write with `appendEvent`. `openAttempt` and `addRunApproval` run only inside one.
- A timeline line is one line. `note` and `runNote` run the message through `oneLine` before the dedupe, the write and the console line, and `appendEvent` and `addRunEventRow` do it again for the lines written without them, so a line break in a typed name or note, an Airwallex name or a pay run cell becomes a space and cannot print as a line of its own on the page or in a terminal. Lines that older code stored keep their line breaks, and `pnpm payrun show` prints each run line as one line.
- `addEvent` hashes the line as it will read back: `storable` turns half of a surrogate pair, such as an emoji cut by `.slice`, into U+FFFD, as SQLite's UTF-8 would.
- The first open with the chain hashes the lines already there in id order and sets `meta.chain_started_at` and `meta.chain_backfilled_through`, the last line it hashed. A ledger whose chain has started (`chainStarted`: any of the three meta keys, the restart record, or a line with a hash) is never hashed again. A line with no hash, written by older code, is reported as written outside the chain, and the next line chains from the last line with a hash. There is no way to take such a line into the chain, because the same step would launder a forged one.
- `pnpm run audit` opens the file with `new Ledger(path, true)`, read-only, which skips the schema, the upgrade and the backfill. It refuses a missing file and a ledger whose chain has not started, a file from before the `meta` table included. An export in `json` is always written through `printableJson`. One in `csv` goes to a file or a pipe as it is, because whoever checks the hashes needs every message exactly, and through `printableLines` only when stdout is a terminal. `pnpm run audit run <RUN>` on a file from before pay runs, which has no `runs` table (`hasRunTable`), says the ledger has no pay runs.
- Pay run timelines are chained the same way, apart from the invoices': `run_events.prev_hash` and `hash` over `canonicalRunEvent`, the JSON `{at, run_id, kind, message, topic}` with `run_id` as a number, one chain per run, and a running hash of their own in `meta.run_events_head`. `addRunEvent` writes the line and the running hash in one transaction, and `Ledger.releaseRun` writes its release line inside its own. The first open with this code hashes the run lines already there and sets `meta.run_chain_started_at` and `meta.run_chain_backfilled_through`. `pnpm run audit` checks run chains after the invoices', `pnpm run audit run <RUN>` checks or exports one, and a ledger whose run chain has not started is reported, not hashed.
- Every chain sets its running hash when it starts, so a running hash that is missing when a line is written was removed. `chainHead` still writes the line, because a payment step must never fail for want of a hash. The running hash starts again from the genesis, and the first restart goes in `meta.events_head_restarted` or `meta.run_events_head_restarted` as `{at, id, of}`: the time, the line's id, and the invoice or `run N`. `restartOf` reads it, and from then on the ledger never reads as intact: `pnpm run audit`, the export's `ledger`, the incident and run audit lines, the MCP `audit` tool and the `audit:*` alerts (`runningHash` `started again`) all report it. Every invoice gets its first line in the transaction that writes it: `openObligation` writes "Incident opened by NAME", `adoptPayout` the found payout's line and `releaseRun` the run line. A run's upload line follows `createRun` with nothing awaited between them. So `unlinedInvoices` and `unlinedRuns`, which the snapshots and `runningHashCheck` read, list invoices and runs left with no line at all, which are reported the same way and counted in an alert's `withoutLine`.
- `auditSnapshot` reads what a check needs in one transaction. The check compares each line with the stored hash of the line before it and with its own content, so an edit shows up once. When the running hash does not match but every timeline verifies, it cannot say which invoice lost lines.
- `runningHashCheck`, which the incident detail's audit line uses, hashes only the lines added since its last check in this process. It reads the last line it hashed again each time, and ids are never reused, so removing the ledger's last lines is caught at once. Once a minute (`FULL_HEAD_CHECK_MS`) it hashes every line again, as the alert loop's audit check does, and only then does the running hash catch anything else: a line removed or rewritten with a new hash in the middle, a whole invoice's lines removed, or a timeline's last line removed when it is not the ledger's last. Those show on every incident's audit line within about a minute. The invoice's own chain, read in full each time, still shows a line edited, removed or inserted in its timeline at once. The audit export routes and `pnpm run audit` hash every line every time.
- The chain has no key. The audit catches a line edited, inserted or removed without new hashes, lines cut from the end of a timeline or of the ledger, every line removed together with the running hash (the restart record and the invoices, runs and breaks left with no line), and the chain's meta keys deleted as well, so that the next open starts the chain again (the invoices, runs and breaks with no line). It misses someone who can write `payonce.db` and either recomputes the hashes (lines rewritten with every hash after them and the running hash, or invoices, runs or breaks deleted with their lines and the running hash recomputed) or deletes every invoice, run, break and line along with the chain's meta keys and any restart record. `pnpm run audit` then reports the result intact.
- `meta` holds `started_at`, when the ledger was first opened. The sweep lists transfers from then, so payouts from an earlier ledger are not taken for outside ones. `meta.outages_since` is when the ledger was first opened by code that counts outages.
- `rail_failures` holds each rail-level failure once, keyed by transfer id: currency, method, code, payee, the bank's short reference, the invoice (or null), origin (`payonce` or `outside`), `created_at` as Airwallex wrote it, `seen_at` and `seen_by` (`look` or `sweep`), and `failed_at`, the time the window counts (see Rail outages). `outages` holds each outage: rail, `codes` (JSON), `state` `active` or `ended`, `declared_at`, the payees counted, the rule it was declared under (`threshold`, `window_minutes`), `counted` (JSON transfer ids), and `ended_at`, `ended_by` and `end_note`. `outage_holds` lists what each outage held, an invoice or a run, with `what` (`counted`, `original`, `replacement`, `approved` or `run`), one per outage per invoice or run (`one_hold_per_invoice`, `one_hold_per_run`). An invoice's `counted` hold becomes the hold of what the outage later holds of it (`insertHold`), and that hold's line is written then, so a counted invoice whose replacement the outage holds gets the `replacement` line. Event kind `outage` is chained like any other, on invoice and run timelines.
- `obligations.supplier_phone` is the phone number on the supplier record, set from the scenario. Only `usd-local-bank-change` has one, so only it offers a callback. Found payouts have none.
- `bank_changes` holds each callback: who called, the number, when, who they spoke to, what was confirmed, the old record and the typed fields, and `state` `pending`, `applied` or `failed`. The row is written before the Airwallex update.
- `obligations.state` is `open`, `escalated`, `settled` or `rejected` (closed without paying). The watcher, `dueLooks` and the server's start-up pick-up skip `settled` and `rejected` invoices.
- `obligations.duplicate_of` is a JSON list of the invoices a held invoice looked like, and `rejected_by` is who closed it without paying.
- `obligations.origin` is `payonce` or `outside`. `payout_reference` keeps a found payout's reference when it could not be the invoice number, and `obligationForReference` matches either.
- `obligations.invoice_floor_minor` is an invoice's own floor, 0 for none, in minor units of the wallet the invoice is paid from (`debitCurrency`, the source currency), because `floorFor` and the panel compare it with that wallet. `reserve_floor_minor` is the floor each invoice carried before `RESERVE_FLOORS`. The open that adds `invoice_floor_minor` copies every `reserve_floor_minor` that is not 0 into it, and only that open, so no invoice from before is held to a looser floor than it was. After that `reserve_floor_minor` is not read or written.
- `attempts.fee_minor` and `fee_currency` hold the fee as last read from the transfer. `record` keeps the stored fee when a read has none. `recordFee` writes only these columns, and only where `fee_minor` is null, so it can run outside an invoice's turn. `failedWithoutFee` lists failed transfers, PayOnce's and outside payouts, with no fee recorded, leaving out those tried too recently and putting the least recently tried first. `fee_tried_at` on both tables is when `feeTried` last marked a transfer before its fee was read. `latestFee` is the latest fee recorded in a currency by a transfer method, which the panel uses to estimate the fee of a payment not sent yet.
- `outside_payouts.amount_minor`, `currency`, `fee_minor` and `fee_currency` are written when a payout is tied and on every look that reads it. `attempts.amount_minor` and `currency` are written by `record` and `adoptPayout`. On both tables the amount and currency are what the transfer took from the wallet before the fee (`debitOf`): the source amount and currency when it was paid from another currency, and the transfer amount otherwise. A row from before has none. For PayOnce's own attempt from the invoice's own currency the panel then takes the invoice amount, which is exact, and for a cross-currency one the quote amount `lineAmount` gives. A found invoice's original or an outside payout from before gets the same amount marked estimated, until a look reads the transfer and stores what it took.
- `obligations.source_currency` is the wallet the invoice is paid from. Null means its own `currency`, and `toObligation` turns null into `currency`, so code never sees it. `NewObligation.sourceCurrency` is optional. The sweep sets it from a found payout's `source_currency`.
- `obligations.last_quote` is the latest quote `rateFor` took for the invoice, as `LastQuote` JSON with when it ends by PayOnce's clock.
- `obligations.due_date` is the invoice's due date as YYYY-MM-DD, null for none and for every invoice found in Airwallex. `run_rows.due_date` is a row's, and `run_rows.arrival` is the last check's estimate for a pay row as `ArrivalTerms` JSON, null on a skip row.
- `attempts.quote_id` and `quote_valid_to` hold the quote a cross-currency attempt is sent with. `approval_id` is the approval any attempt was opened on, null for one no approval released. `attempts.rate_mismatch` says why its transfer did not match that quote.
- Approvals need no FX column: the quote lives in `approvals.terms`, and `expires_at` carries the earlier expiry.
- After upgrading, restart every PayOnce process. An older process sharing the file builds terms without `fx` or `arrival` and would void the new requests, and would retry a pending cross-currency attempt without its quote.
- `adoptPayout` writes a found payout's invoice and attempt in one transaction. Its INSERT is plain, so an invoice written by another process in between makes it fail instead of gaining a second original.
- `outside_payouts` ties outside payouts to invoices, with the bank's short reference and the last state a look read. A person's close, `settle(invoiceId, true, "escalated", covered)`, also accepts an invoice whose attempts all failed and whose outside payout is paid and pays it (`paidOutside`, `payoutPays`), or one paid by a mismatched transfer (`paidMismatched`). Only `closeIncident` makes it.
- `outbox` holds message drafts: the invoice, template, audience (`supplier` or `bank`), the facts as JSON in the template's key order, subject, body, `text_hash` (SHA-256 of `JSON.stringify({template, subject, body})`), `state` (`draft`, `copied`, `sent`, `dismissed`), who created it and when, and who copied, sent or dismissed it, with a dismiss note. The partial unique index `one_open_draft_per_template` on `(invoice_id, template) WHERE state IN ('draft', 'copied')` allows one open draft per template per invoice, and a second is `DraftOpenError` with the open draft's id. `createDraft` inserts the draft and appends its timeline line with `appendEvent` in one transaction, so a draft never exists without the line that records its hash. `markDraft` moves a draft only from the states given (`copied` from `draft`; `sent` and `dismissed` from `draft` or `copied`) and writes its line in the same transaction, so a page and the CLI cannot both move it. `sent` and `dismissed` are final.
- `attempts.bank_created_at` and `bank_status` are the transfer's `created_at` and `status` as `record` last read them, kept with `COALESCE`. `attempts.arrival` is the route advisory's `ArrivalTerms` for a payment, written by `send` with `setArrival` right after it works the estimate out. Payments from before these columns have none. `attempts.opened_at` is when PayOnce opened the attempt, written by `insertAttempt`; attempts from before the column and a found payout's have none. `attempts.tried_at` is when `sendAttempt` last called Airwallex to create the transfer, written just before the call. `neverSentAt` also writes the current time for an attempt with neither `tried_at` nor `opened_at`. Opening a file from before the column gives every pending attempt with no transfer the time the column was added. `attempts.found_late_at` is when `recordLateTransfer` found a transfer for an attempt marked failed with none, written by `foundLate` before the transfer is recorded. `attempts.mismatched_transfer_id`, `mismatched_reference`, `mismatched_status`, `mismatched_amount_minor` and `mismatched_currency` keep a transfer under the attempt's request id that does not match the invoice, and `mismatched_cleared_at` is when a person closed the invoice after it was found.
- `alert_conditions` holds one row per condition that needed a person, keyed `invoice:<id>`, `payout:<transfer id>`, `run:<id>`, `audit:invoices`, `audit:runs`, `audit:recon`, `cash:<currency>`, `inbox`, `outage:<id>` or `recon`, with its fingerprint, episode, when it was last recorded as new, changed or back (`seen_at`) and when it cleared. `alerts` holds one row per message: the facts it is built from, fixed when queued, and `state` `queued`, `sending`, `sent`, `failed` or `skipped`, with tries, the next try, the claim and the last error. The unique index `one_alert_per_change` on `(alert_key, episode, fingerprint)` stops a key alerting twice for one fingerprint in one episode, so A, B, A flapping posts twice. `meta.alerts_started_at` is the first evaluation. The webhook address is never stored.
- Columns added after the first version are listed in `ADDED_COLUMNS` and added when the database is opened, under the write lock, so two processes opening an older file at once do not both add one.
- `obligations.escalated_at` is when the invoice first went to a person. `attempts.failed_at` and `paid_at` are when PayOnce first recorded the attempt failed, and paid; for a found payout's original taken on already failed or paid, that is when PayOnce took it on. Only the metrics read them. Only the five SQLite triggers in `TIME_TRIGGERS` write them: `obligation_escalated_at`, `attempt_failed_at` and `attempt_paid_at` run after an `UPDATE OF state` that moves the row into that state from another one while the column is null, and `attempt_failed_at_insert` and `attempt_paid_at_insert` run after an insert in that state, as `adoptPayout` makes. Each trigger sets only its own column, with `COALESCE` and `strftime('%Y-%m-%dT%H:%M:%fZ', 'now')`, on the same row by rowid. A trigger has no constraint, no RAISE and no SELECT, so it cannot fail the statement it runs in. `addColumns` creates them with `IF NOT EXISTS` in the write lock that adds the columns, on every writable open. `recursive_triggers` stays off, and no trigger changes a state, so none sets off another. They also fire for an older PayOnce sharing the file. A row already in that state when its column was added gets `''`, a time not known, which no trigger overwrites and the metrics count as not on file. Nothing in `decide`, the policy, approvals, terms, bindings, alerts, the board or the cash panel reads them.
- `attempts.refused_at` is when Airwallex refused to create the transfer, with or without a code. No trigger writes it, because only the caller knows why an attempt with no transfer failed: `sendAttempt` calls `failAttempt(requestId, code, true)` on a refusal, and `failNeverSent` passes false when Airwallex lists no transfer. Only the metrics read it. A refusal from before the column has none.
- Stored JSON is read strict. The row mappers (`duplicate_of`, attempt and run row `arrival`, run `columns`, run row `cells`, `reasons` and `held_for`, outage `codes` and `counted`, and an upload's `reply_to`, `attachments` and `notes`), the engine's `storedFindings` and the cash panel's line amount, which reads approval terms and a kept quote, all go through `storedStrings`, `storedList` and `storedObject`. Outside `readingSoft` those are plain `JSON.parse`. So the engine, the policy, approvals, terms, bindings, `committedMinor` and the run checks fail closed on a value they cannot read: the look throws, sends nothing and is tried again a minute later. The reads that span every invoice parse no column they do not use: `committedMinor` reads `Ledger.committedRead` (the open and escalated invoices and their attempts, without `duplicate_of` or `arrival`), and `likelyDuplicates`, `sameNumberForSupplier`, the run checks and the callback's check for another payment starting read `Ledger.scannedObligations`. So one spoiled row stops only its own invoice's looks. A held invoice whose `duplicate_of` does not parse stays held, and `pendingApproval` throws on it too, so nobody can approve paying it. Only views read soft, inside `readingSoft(fn)`: the board (`rankedBoard`, which covers `boardReport`, `boardGroups`, `outageHolding` and the supplier view's board entries), `outageView` and `outagesReport`, the incident, pay run and inbox lists (`GET /api/incidents`, `GET /api/runs`, `GET /api/inbox` and the MCP `incidents`), the cash panel as shown (`GET /api/cash`, `pnpm cash` and the MCP `cash`), and the supplier list and detail. In a view, a value that does not parse, or is not a list or an object as PayOnce writes it, reads as none, so one spoiled row cannot answer 500 for the whole view. The panel's line amount reads such terms or kept quote as no quote, the board tells a held request from a replacement by the invoice, and findings stand as not read. `readingSoft` takes synchronous reads only, so no look runs inside it. The server's start-up pick-up and the watcher read the invoices to wake inside it and wake them afterwards, so one spoiled row stops neither. The incident, run and upload details, alerts (the alerts' cash check included), `Ledger.emails`, the engine's reads of approval terms and `readNewEmails` read strict. An outage with no readable codes says "a rail-level code", as its alert does, and the page shows "None on file".
- `attempts_by_invoice`, `approvals_by_invoice`, `emails_by_invoice` and `outside_payouts_by_invoice` index those tables by invoice, beside `events_by_invoice`.
- `obligations.run_row_id` is the run row an invoice was released from (`Obligation.runRowId`). `attempts.misdirected` is 1 for a transfer `checkAccount` found went to other details than it was approved or decided for, or showed none, so it never counts as the account PayOnce last paid.
- A ledger from before `account_key` keeps a key only where `backfillAccountKeys` found an approval or a pay run row that named the account. A supplier PayOnce paid only through other payments (automatic replacements, single incidents' originals, approvals from before terms carried `accountKey`) counts as paid before with the account not confirmed: its next first payment is held with `UNCONFIRMED_ACCOUNT_REASON` and takes two approvers, until a checked payment to it is paid. `pnpm reset` starts an empty ledger, which has none of these.
- An invoice number is the primary key of `obligations`, and a second one fails with `errcode` 1555 (`SQLITE_CONSTRAINT_PRIMARYKEY`), not 2067.
- Pay runs are in tables of their own, created by `SCHEMA` on open. `runs` (state `waiting`, `released` or `cancelled`, the file's name, hash and header, the uploader, and the last check's cash as JSON), with the partial unique indexes `one_waiting_run` and `one_live_run_per_file`. `run_rows` (the cells as read, what the last check made of them, `action` `pay` or `skip`, `reasons`, `held_for`, `new_payee`, `bank_change_id`, `payee`, `pay_to`, `account_key`, and `state` `waiting`, `released` or `dropped` with a `note`). `run_approvals` and `run_signoffs` mirror `approvals` and `signoffs`, because those reference `obligations`, which a run has none of until it is released; the run methods are copies of the invoice ones, not generic over the tables. `run_events` is the run's timeline, hash-chained like `events`.
- `payRunRows` reads, as query predicates, the pay rows of a waiting run whose latest request is `approved` and not expired, and the released invoices still `open` with no attempt. A row drops out in the transaction that opens its attempt.
- `currency_locks` holds the lease per currency: `holder` and `expires_at`. `takeCurrencyLock`, under `BEGIN IMMEDIATE`, drops waiters that have not asked for 10 seconds, and takes the lock (inserting it, or taking it over once expired) only when no other waiter is first in line. Otherwise it adds the holder to `currency_lock_waiters` or refreshes its `seen_at`, keeping its place. `leaveCurrencyQueue` removes a holder that gave up. `withCurrencyLock` calls it whenever it stops waiting with an error: after 45 seconds, or when `takeCurrencyLock` throws on a busy ledger. A waiter that stopped then never holds up the queue for `WAITER_GONE_MS`. `renewCurrencyLock` and `releaseCurrencyLock` act only for the holder.

## Incident board

- `boardReport` lists every invoice that is not `settled` or `rejected`, and every pay row (`action` `pay`, `state` `waiting`) of the run waiting for approval, which has no invoices until it is released. It reads the ledger only and never calls Airwallex. It adds no action: rows link to the incident, or to `#run/N` for a row not released, where the existing cards act.
- Money at risk is the cash panel's lines and nothing else: `cashLines` without `fee-lost`, plus `payRunLines` and `waitingRunLines`, amount plus fee, summed per invoice and per currency of the wallet the money leaves. The waiting run has released nothing, so a line with its `runId` goes to its row, and any other run's line goes to the released invoice.
- Groups, in order. `person`: an invoice with a line of kind `awaiting-approval` or `awaiting-person`, a pay row of the waiting run while its request is not approved, an escalated invoice the bank reports paid that waits for a person to close it (`pendingClose` of a paid kind, reason `close`, as the incident page's close card offers it, ahead of the deadline and bank groups), or an invoice with any line at risk that a waiting upload offers first (`candidatesFor`'s `suggested`: the one invoice it names, not only among other digits, open or escalated). `deadline`: a payment with a transfer, pending or in flight, at or past `bank_created_at` plus `deadlineMinutes(obligation.transferMethod)`; with no creation time on file it counts only when the escalation reason starts with a deadline reason, as the outbox's trace request counts it. `bank`: any other payment with the bank, or a tied outside payout in flight or in an unknown status (the ledger keeps no creation time for those, so they never count as past the deadline). `open`: the rest, such as an invoice with a line of kind `approved` (an approval not expired or used, which the next look spends), a pay row of an approved run, which the server's watcher releases, a released run row waiting for its turn, a payment with no transfer yet, an escalated invoice with nothing at risk and no paid close, and an open invoice with nothing at risk. A waiting upload that offers an approved invoice first still puts it in `person`, as it does for a payment being sent. An active outage moves what it holds to `person` (see Outages on the board).
- Within a group: the largest per-currency amount at risk first (`rankMinor`), then the oldest `waitingSince`, then the invoice number. Amounts in different currencies are compared as plain numbers, because PayOnce has no exchange rates. The currency filter gives a strict order within one wallet.
- `why` and `also` are fixed strings in `incident-board.ts`, filled only with PayOnce's own figures: signoffs of the open request, the run id, how many uploads name the invoice, an outage's id and rail. Airwallex gives the rail's currency and method, so `railName` names a rail only when it is a currency code and a method (`RAIL_NAME`), and writes "a rail PayOnce cannot name" otherwise. Never the escalation reason, an email, a model's answer or an Airwallex message. `reason` is the code behind `why`. A `person` entry whose payment is past its deadline says so in `also`, and so does an entry that an upload offers first but that is in its group for another reason. An upload that names an invoice beside others, only nearly or among other digits never moves it; it adds "may be about this invoice" to `also`. The page and the CLI print them as text.
- `waitingSince` is the invoice's first timeline line (`Ledger.firstEvent`, which reads one row), or the run's `uploaded_at` for a run row. `deadlineAt` is the deadline of the live payment the entry is about, null when no creation time is on file.
- `totals` per currency, over the entries shown: `promisedMinor` (`FIRM_KINDS`), `waitingMinor` (`awaiting-approval` and `awaiting-person` with no run), `outageMinor` (`waiting-outage`), `runWaitingMinor` (`waitingRunLines`, which the cash panel does not count) and `withBankMinor` (`with-bank` and `outside`). With no filter, `promisedMinor`, `waitingMinor`, `outageMinor` and `withBankMinor` equal the panel's lines of the same kinds read at the same moment. With a currency filter only that currency is totalled. `invoices` is the number of invoices in the ledger, closed ones included.
- One report reads the whole invoice table three times (`obligations`, `cashLines` with `openOnly`, and one `invoiceIndex` shared by every waiting upload) and does the rest per open invoice. On seeded copies of the ledger it took 50 ms with 5,000 closed invoices and 51 waiting uploads, and 125 ms with 10,000 and 101.
- `GET /api/board` takes `group`, `currency` (the wallet, three capital letters) and `origin` (`payonce`, `outside`, or `pay-run`, which is any invoice with `run_row_id` and every waiting run row). An empty value is no filter, and anything else answers 400. `groups[].count` counts the entries that pass the currency and origin filters, whatever the group filter. `currencies` lists every wallet on the board. `outages` lists every active outage, whatever the filters.
- `pnpm board` takes the same filters as words in any order and prints the same ranking, after the active outages. A currency can be in any case, and must be a code `Intl.supportedValuesOf("currency")` lists or a wallet on the board (Node does not list CNH). Any other word, such as `pay`, prints the usage and exits 1. It prints names and invoice numbers with control characters and line breaks as spaces, and drops Unicode format characters (bidi controls, zero-width characters) and the tag block. With no invoices in the ledger it says how to start one.
- The page opens on the board when the address has no hash, and the "Incident board" button in the top bar brings it back. The incident list, pay runs and inbox stay in the sidebar. The board loads only while it is on screen, on the page's usual poll, and is redrawn only when its entries, totals, groups or filters change. The ages are set on their own nodes on every poll. Filters are kept in memory, not in the address or `localStorage`.
- Leaving the board, it stays on screen until the view picked, or that view's loading placeholder, is shown. The board held is dropped on the way back, because it is not polled while hidden. The view left then stays up to 250 ms while a fresh board loads, and the board shows "Loading" after that. If a refresh that skipped the board is still running, the board is fetched at once instead of after it.
- `#board-empty` shows "No incidents yet. Start one with the new incident form." while `invoices` is 0.
- `GET /api/incidents` gives each invoice on the board `board: { group, label }`, null for the rest, from one `boardGroups` per request. The sidebar keeps the state badge and adds the label as a tag when the group is not `open` and the label is not the badge's. An escalated payout past its deadline reads "Waiting on a person" and "Bank deadline passed", as the board lists it.

Checked on 2026-10-29 on a copy of the main ledger with the server on port 4337 (webhooks off, keyword reader): the sweep took on payouts made from other worktrees, and with a held `eur-from-usd` invoice, the sample pay run waiting for approval and an uploaded email naming an invoice in flight past its deadline, the board listed 15 entries across all four groups. Its `promisedMinor`, `waitingMinor` and `withBankMinor` equalled `GET /api/cash`'s lines in every currency (USD 0, 8,499.92 and 13,321.15), and the run's 81.00 USD and 50.00 EUR showed only in `runWaitingMinor`. The outside filter gave 9,321.15 USD, the panel's "Payouts sent outside PayOnce". Nothing was approved or sent.

Checked again on 2026-10-29 on a seeded copy, same settings: the sidebar's tags matched the board's group for all 14 open invoices, seven of them payouts sent outside PayOnce past their deadline. Moving between the board, an incident, a run and an email never left the main area blank, and with `/api/board` held back 800 ms the way back showed the incident for 280 ms, then "Loading", then the fresh board. An empty ledger showed the hint. Nothing was approved or sent.

### Outages on the board

- `boardReport` reads `ledger.activeOutage` on each invoice's rail and gives the entry `outage: { id, rail, touch }` when the outage touches it, from the entry's cash lines. `original`: a `waiting-outage` line, or a `pay-run` line of a released row, so a first payment not opened. `approved`: an `approved` line. `replacement`: an `awaiting-approval` or `awaiting-person` line on an invoice this outage holds whose `escalation_reason` starts with `OUTAGE_REASON`. Hold rows cannot tell this alone: a hold stays `replacement` after a person approves, and an invoice whose replacement waits on another reason keeps a `counted` hold. `approval`: any other `awaiting-approval` or `awaiting-person` line. Money with the bank is never touched. A run row is touched by the first active outage on any pay row's rail, `run` while the run is `approved` and `approval` otherwise, because the run is released whole.
- `original`, `approved` and `run` move the entry to `person` with reason `outage-original`, `outage-approved` or `outage-run`, since only a person ends an outage. A `replacement` waiting for approval gets `outage-replacement`. Any other `replacement`, and every `approval`, keeps its group and reason and gets a fixed `also` line saying a payment approved now waits for the outage to end. The escalation reason is only read to sort, as for deadlines, and never shown.
- `outages` in the report: each active outage, oldest first, with `outageView`'s `codes`, `payees`, `windowMinutes`, `declaredAt` and `text`, and what it holds now from the entries before any filter: `originals`, `replacements` and `approved` (invoice ids), `runs` (run ids), `atRisk`, the sum of those entries' cash lines, and `sends`, what ending it sends per currency: one payment per `original`, `approved` and `run` entry and the sum of their cash lines (`sendsOf`). A replacement it escalated is in `atRisk` and not in `sends`, because it still needs an approval. An `approval` entry is in neither, since nothing of it is held yet. `outageHolding` gives the same lists, as `OutageHolding`, to `GET /api/outages`, `pnpm outage` and the end of an outage, so the Outages card lists what the slot lists. Ending it, in one transaction, records a hold (the touch as `what`) for every invoice and run the slot listed, marks the outage ended, and then writes the end line on every invoice and run with a hold, `counted` ones included.

## Supplier view

- A supplier is one Airwallex beneficiary record: `obligations.beneficiary_id`, and `run_rows.beneficiary_id` for a pay row of the waiting run that no invoice holds yet. A skip row never makes a record, since its id may be one Airwallex does not have. The key in every route, link and command is the id, checked against `SUPPLIER_KEY_PATTERN` (`BENEFICIARY_ID_PATTERN` from `run-file.ts`). Every control keys on the record (`lastPaidTransfer`, `verifiedBankChange`, `payeeRule`, the run check), so the page shows what the next payment is checked against. Records are never merged. Records that share a name (`sameSupplier`, through `supplierNameKey`) or an account (an account key on file under both, or a `rail_failures.payee` both failed to) are linked, for display only. An empty name, and `UNNAMED_PAYEE`, the name the sweep gives a found payout with no account name, never link records. A stored id outside the pattern is listed with `key: null` and no link.
- `supplierList` and `supplierDetail` each read the ledger once, inside `Ledger.readSnapshot`. The list reads every record with `Ledger.supplierListRead`: only the columns its cautions, counts and names use from invoices (`SupplierObligation`), attempts (`SupplierAttempt`) and payouts sent outside PayOnce, no drafts or outage holds, and approvals with only the account their terms name, so each terms JSON is parsed once. It builds the links between records from that same read (`linksOf`). The detail reads its record with `Ledger.supplierRead(key)` (the invoices in full, what the page shows of each payment as `SupplierPayment`, with the route advisory's JSON parsed only for what paid a listed invoice, its drafts and holds) and the other records' names and accounts with `Ledger.supplierLinks(key)`, which leaves out that record's own approvals, read already. It reads an approval's account only inside `CASE WHEN json_valid(terms)`, as `metricsRead` reads `duplicate_of`, because SQLite promises no order for the two sides of an AND and `json_type` throws on text that is not JSON. Neither puts in its answer an email's or an upload's subject, body or display name, a draft's subject, body, facts or dismiss note, a callback's `spoke_to`, `confirmed` or `new_details`, a timeline line, an escalation reason or a skip reason. Both still read some of them. The list's read takes `escalation_reason` and the detail's takes whole invoice rows, and the reason is only tested with `startsWith` against exported constants. The detail's inbox and `boardEntriesFor` read waiting uploads in full, but only for `candidatesFor`. The board also reads each open invoice's first timeline line, only for its time, and the waiting run's rows in full. Both work on a read-only ledger. `Ledger.supplierNamed` says whether an invoice or a waiting pay row names a record, for `resolveSupplier`.
- Money and groups are the board's own, built by `boardEntriesFor` for the invoices that need them, each entry as the whole board has it: the list for every invoice that is not closed (`Ledger.openObligations`) and every pay row of the waiting run, summed per record, and the detail for its own invoices and pay rows, with their totals. Neither builds entries when its records have no open invoice and no waiting run row. The detail's waiting uploads and the board's use one invoice index.
- Accounts are named by where the money goes: each key `attempts.account_key`, approval terms and `run_rows.account_key` carry is read as its routeKey where the ledger keeps one (`Ledger.accountRoutes`, applied in the supplier reads), else as it is, and labelled A, B, C in the order first seen, so a bank name Airwallex rewrote makes no new account. Sources: decided for (`account_key`, `opened_at`), sent to (`sent_key`), asked to approve (the terms' `accountKey`), pay run (a pay row's `account_key`, `checked_at`), verified by a callback (the routeKey of `applied_key`), on the record before a callback (`routeKeyOf` the callback's `old_details`) and paid outside PayOnce (a payout's `sent_key`). The page and the CLI never print the key; the JSON carries it as `accountKey`. An ending comes only from `sent_ending` and the callback JSON, as 1 to 4 letters and digits. A payment's account is its `sent_key`, else its `account_key` when it has a transfer and is not misdirected. Its check is `checked`, `misdirected`, `not-kept` (no `account_key`), `not-sent` (no transfer) or `outside`.
- The account PayOnce last paid is `ledger.lastPaidTransfer`'s, never a copy of the rule. What PayOnce last stored is the newest key among decided, asked to approve, pay run and callback, and the header says the record is read again before every payment, naming the invoice it was stored on, or a pay run row as "row N of pay run M" (`runLine`), since the row's number may not be an invoice yet. The latest applied callback is the one `verifiedBankChange` reads, the newest applied whatever it kept. `verifiedBy` is that callback when its key is this account's. Each account reads only its own payments, payouts, callbacks and failures, grouped once per record. `barred` is `bankChangeRecorders` for each applied callback with this key, through `knownName`, as `barredFrom` reads it.
- Cautions are `{ code, level, text, invoices, accounts, keys, runs, since }`. `text` is fixed words that may hold account labels, counts, failure codes' words (`wordsFor`: only a code in `FAILURE_CODE`'s form that is the table's own entry, so `constructor` gets none) or a rail in its own form, and in `callback-verified` the account's ending (1 to 4 letters and digits) and when the callback was recorded, to the minute in UTC. Invoice numbers (25 at most), account labels and other record ids (`keys`) go in the arrays. No caution carries a name, a domain or a reference, and none fills `runs`. In order, cautions before infos:
  - `account-changed` follows the engine's tests. It shows, with that account's label, when `lastPaidTransfer` gives an account, the account PayOnce last stored is not that one, and the latest applied callback did not verify it (the `verifiedBankChange` test). It also shows, with those invoices and whatever the callbacks, whenever an open invoice's reason starts with `CHANGED_BANK_DETAILS_REASON`, `LAST_PAID_CHANGED_REASON`, `ACCOUNT_CHANGED_REASON` or `RUN_ACCOUNT_CHANGED_REASON` (a pay run row whose record changed after the run was approved). Its text has a part for each case. The first speaks only of first payments and pay run rows: PayOnce sends no first payment to those details, and skips a pay run row to them, before a callback. That rule does not hold a replacement whose original went to them, such as the replacement of a payout sent outside PayOnce.
  - `callback-verified`: the latest applied callback verified the account PayOnce last stored, and it is not the account `lastPaidTransfer` gives. It says when the callback was recorded and which account (label and ending), that paying a held invoice or a pay run row to it needs two approvers (`payeeRule`, `runRule`), and that nobody who recorded a callback for it may approve. It says nothing about automatic payments, and reads with `new-payee`, which says the same about two approvers.
  - Then `new-payee` (never paid, or paid only by itself and never on a person's approval), `unconfirmed-account`, `misdirected`, `shared-account`, `account-failure` (90701, 90101 or 90802 on the last paid or last stored account in the last 30 days), `domain-changed`, `asks-not-to-pay` and `asks-new-details` (open invoices only), `paid-twice` (`LATE_TRANSFER_REASON`), `no-phone` (escalated invoices with no phone on file, since a callback is recorded on the escalated invoice from its own phone), `recent-failures` (by `bank_created_at`, else `opened_at`; a failed attempt the bank still has live is not one), `non-receipt`, `flagged-senders`, `no-domain`, `outside-payout`, `held-duplicate` and `outage` (an active outage on an open invoice's rail).

## Outbox

- A draft is a message for a person to send to the supplier or to the bank. PayOnce never sends one, and marking one sent changes nothing else: no invoice state, no approval, no money. There is no recipient address on a draft, so nobody replies to a look-alike thread by mistake, and the page says to send it to the contact on file.
- Drafts are rendered from templates over facts PayOnce formats itself: the invoice number, the amount, the bank's short references (only if they match `^[A-Z0-9-]{1,30}$`), `in flight` or `paid`, Airwallex's status (only if it matches `^[A-Z_]{1,30}$`), dates written out, the method (only as `LOCAL` or `SWIFT`, and the line is left out otherwise), and the last four digits of `obligations.supplier_phone`. Never the supplier name, email text, the reader's findings text, model output, an escalation reason, approver names or account details. Two findings choose what is suggested: non-receipt and new bank details. The third, the ask to hold, cancel or not pay, stops every suggestion to the supplier. While it is on file, each supplier message that fits goes to `withheld` instead of the offers, and only the messages to the bank (the trace and refund trace requests) are still offered.
- Supplier drafts never show PayOnce's bank deadline, which is minutes in the sandbox. A payment still with the bank gives the route advisory's latest usual day from `attempts.arrival`, with a note that a public holiday can make it later, or "within the usual time for this route" when there is none. "Sent on" is the advisory's `from` day, or the day of `bank_created_at`. The trace request to the bank gives the transfer's creation time and status and no deadline.
- Templates: `payment-sent` fits when the original is with the bank or paid, suggested when the supplier reports non-receipt. `replacement-sent` fits when a replacement is with the bank or paid after a failed original, always suggested, and names the day of the callback in the approval the replacement was sent on, if any. `checking` fits an open or escalated invoice with emails on file, promises nothing, and is suggested on an escalated one unless `payment-sent` or `callback-notice` is. `callback-notice` fits an open or escalated invoice with a phone on file when the findings say the supplier asks for new bank details or the reason is a bank-details reason, always suggested. It says PayOnce calls the number on file before paying any other account and asks the supplier not to send bank details by email or in a reply. Without a phone it is listed in `notOffered` with why. `bank-trace` fits when a payment is in flight past `bank_created_at` plus the method's bank deadline, or, with no creation time on file, when the reason is a deadline reason. It is always suggested. `refund-trace` (audience `bank`) fits when reconciliation has an open `refund-missing` break on one of the invoice's own transfers, matched by `attempts.transfer_id` only (`ReconStore.refundBreaks`, ledger only; the latest such attempt wins), and is always suggested. It fits a settled or rejected invoice too, since a closed invoice can still be owed a refund. Its facts are `reference` (the attempt's, else the stored transfer's short reference, each only as `^[A-Z0-9-]{1,30}$`; with neither it does not fit), `debited` (the break's `expectedMinor` and `currency`, through `formatMoney`, only as a positive whole number and three capital letters), `status` (the stored transfer's, only as `^[A-Z_]{1,30}$`), `failedDay` (`failedBy` on the stored transfer, written out on this machine's calendar) and `method` (the invoice's, only as `LOCAL` or `SWIFT`). It never takes the invoice number, a name, a reason, the break's other facts or note, or anything else Airwallex wrote. Once the newest such break is `explained` it no longer fits because "a person explained the missing refund in reconciliation", and once it is `cleared` because "reconciliation no longer finds the refund missing". It does not say the refund landed, because a break also clears when only part of the money comes back (a `refund-differs` break then opens) or when the debit drops out of the balance history a check reads.
- Offers are a pure read: nothing is drafted until a person asks. A template with an open draft is not offered again. Nor is one whose last draft marked sent had the same facts JSON, so a message already sent is offered again only once its facts change.
- Each read hashes the stored text again (`intact`) and works the facts out again: `changed` lists each fact that differs, and `noLongerFits` says why the template no longer fits. The card and `pnpm outbox show` warn about each. A person can still mark a stale draft sent, and the sent line then says what had changed.
- Timeline lines are kind `outbox` with topic `outbox:<id>`, so they are standing lines that do not make the next look repeat its decision: `Draft N for the supplier created by NAME: "LABEL". Text SHA-256 HASH. PayOnce does not send it`, `Draft N copied by NAME`, `Draft N marked sent by NAME. PayOnce did not send it`, and `Draft N dismissed by NAME: NOTE`. The draft text itself is never on the timeline.
- The page's "Messages to send" card sits after the approval card. It lists suggested messages first with "Draft it", then the others, and each open draft in a read-only textarea filled through `.value`, with Copy (the clipboard, or the text selected when the browser refuses; a first copy is recorded), Mark sent and Dismiss with an optional note. The name field starts from the stored name. While the supplier asks not to pay, the card says "No message to the supplier is suggested, because they asked to hold, cancel or not pay this invoice" and lists the withheld messages with "Draft one anyway", which drafts through the same route. `pnpm outbox` lists them as held back, and its `draft` takes them. ## Alerts

- Off unless `ALERT_WEBHOOK_URL` or `ALERT_TEST_RECEIVER_URL` is set, and then only `pnpm ui` evaluates and posts. No CLI command imports the alert loop: the CLI writes the ledger, and the server's next check sees it. With alerts off there are no alert rows and no alert calls.
- `ALERT_WEBHOOK_URL` must be https on the default port with no user info, and either `hooks.slack.com` with a path under `/services/` (format `slack`) or `discord.com` or `discordapp.com` under `/api/webhooks/` (format `discord`). `ALERT_FORMAT` is `slack` (default) or `discord` and must match the host. Anything else turns alerts off with a start-up line that never repeats the value. `ALERT_TEST_RECEIVER_URL` is for a receiver on this machine only: http or https on 127.0.0.1, localhost or [::1], posted in the shape `ALERT_FORMAT` names. While it is set it wins over `ALERT_WEBHOOK_URL`, and the start-up line says alerts go to a test receiver.
- Alerts are built from ledger fields, never from timeline lines, which hold email subjects, senders, Airwallex error text and the supplier's phone number, and never from an upload's sender, display name, subject or text. The facts are invoice numbers, the supplier name, formatted amounts, the escalation reason, counts, dates and the bank's short references. An alert never names an approver, an account, a bank, an `accountKey`, a binding or a request id.
- `obligations.escalation_reason` must never hold email text, model output, a phone number or account details, because alerts send it. The reasons supplier emails add are fixed strings: `NOT_TO_PAY_REASON` and `PARTLY_UNREAD_REASON` (both `check`) and `EMAILS_BEFORE_PAYMENT_REASON` (`held`, or `approve-held` once a request is open). `NOT_TO_PAY_CLAUSE`, added to another reason, is a fixed string too, and so are `LATE_TRANSFER_REASON` (`twice`), `MISMATCHED_TRANSFER_REASON` (`check`, or `close` once the transfer is paid) and `MISMATCHED_FAILED_REASON` (`check`, or `held` when the invoice never sent a payment of its own or a person closed it before).
- Conditions: `invoice:<id>` for an escalated invoice, except while an approval is approved and not expired, or used with its payment still pending or with the bank, unless the reason is a deadline or `LATE_TRANSFER_REASON`. Its need is the first of: `approve-held` (a request to pay a held invoice), `approve`, `twice` (`LATE_TRANSFER_REASON`, posted as urgent with the title "INV may have been paid twice"), `close` (`pendingClose` of a paid one), `held` (a held invoice, or one a person closed before, with no request), `bank` (a deadline reason), `outside`, `callback` (a bank-details reason and a phone on file), `check`. Its fingerprint is the need, the reason without a floor clause (`baseReason`), and for an open request its action, amount, currency, `accountKey` and signoffs needed, so a request renewed on the same terms does not alert. The need is worked out from the reason without `NOT_TO_PAY_CLAUSE`, which stays in the fingerprint, so a held invoice alerts again when the ask arrives and its need stays the same. `payout:<transfer id>` for every outside payout tied to an invoice and every original of an `outside` invoice, once. `run:<id>` while `runStatus` is `waiting-approval`, by binding and signoffs needed. `audit:invoices`, `audit:runs` and `audit:recon` (reconciliation's record) when a chain breaks, a running hash is missing, does not match or has started again, or an invoice, run or opened break has no line, checked once a minute. Their facts give `runningHash` (`matches`, `missing`, `does not match` or `started again`) and `withoutLine`, and the message adds "With no line at all" only when that is above 0. `cash:<currency>` when the panel's `headroomMinor` is below 0. `inbox` while any upload waits for a person, with the count as its only fact. Its fingerprint is the newest upload's id in any state, so a new upload alerts again and a delivery or a dismissal does not. `outage:<id>` while an outage is active and for 24 hours after it ended, with its state as the fingerprint, so it posts "Outage declared on USD LOCAL" once and "Outage on USD LOCAL ended" once, then clears with nothing posted. Its facts are the rail, the codes (labels added in the message from `RAIL_FAILURE_CODES`), payees, window, up to five short references, the times and how many invoices and runs it held (its hold rows other than `counted`, as the Outages card lists them), never who ended it or the note. References outside `[A-Z0-9-]{1,30}` are left out one by one, and the Payouts field with them when none is left; the alert still posts. Airwallex short references such as `P261028-F9233YT` always pass. `recon` while any reconciliation break is open (see Reconciliation). The summary counts active outages. Before the first balance read, cash conditions are neither found nor cleared. The server's first check waits while that read is running (the cash callback answers `"reading"`), so a currency already below 0 when alerts are first turned on is counted in the summary. If the read fails, the check goes ahead without cash, and the currency gets an alert of its own once a read works.
- `Ledger.recordConditions` keeps the first condition found for each key, so a key found twice cannot fail the insert. It then reads the stored conditions, and when nothing is new, changed, back or gone it returns without writing. Otherwise it compares again in one `BEGIN IMMEDIATE` transaction and writes only the rows that changed, so a check that finds nothing never waits behind a CLI holding the write lock. `claimAlert` also reads for a due alert before its `UPDATE`. A new condition, a changed fingerprint, or a condition back more than 10 minutes after it cleared (a new episode) queues an alert with `INSERT OR IGNORE`. When that insert meets a `skipped` row for the same key, episode and fingerprint, the row is queued again with the facts as they are now, and its tries and last error are reset. A queued, sending, sent or failed row is left alone. So a condition that goes from A to B before A posts, and then back to A, posts B and then A. One back within 10 minutes as it was queues nothing new, but an alert skipped while it was gone is queued again the same way. On the first evaluation (both alert tables empty and no `meta.alerts_started_at`), every condition standing is recorded with no alert and `alerts_started_at` is set. One summary alert is queued, counting invoices waiting on a person, pay runs waiting for approval, emails waiting in the inbox, broken audit trails, currencies below 0 and open reconciliation breaks, but only when at least one condition stands. With nothing standing no summary is queued, and each later condition alerts on its own. Emptying both tables starts over only if `alerts_started_at` is deleted too.
- An alert is due 10 seconds after it is queued. `flush` posts up to four per 5 second check, 1.1 seconds apart. `claimAlert` takes the oldest due alert, or one whose claim ran out, in one `UPDATE ... RETURNING`, and the claim lasts 60 seconds. Before posting any alert but the summary, `skipStaleAlert` marks it `skipped` when its condition has cleared or no longer has the same episode and fingerprint. The check is inside that one `UPDATE`, and an alert it leaves alone is posted. So if another process records the condition back to the alert's fingerprint, either its write lands first and the alert posts, or it finds the alert skipped and queues it again. Only the claim holder can finish an alert.
- A post is one `fetch` with `Content-Type: application/json` and no other header PayOnce sets, `redirect: "manual"` and an 8 second timeout, never through the Airwallex client. Discord gets `wait=true`. 2xx is sent. 429 waits `Retry-After` or Discord's `retry_after`, between 1 second and 15 minutes. A 5xx, network error or timeout waits 30 seconds times 4 to the power of (tries made less one). Five tries in all, then `failed`. A 3xx, a 400 or any other 4xx fails at once. 401, 403, 404 and 410 also stop this process posting until a restart, and queued alerts wait. `last_error` keeps the status with Slack's lower-case code or Discord's numeric `code`, and nothing else from the answer, not even Discord's `message`, because a receiver could repeat part of the token there. For a network error or timeout it keeps Node's error text. Either way the address, its path and query are cut out.
- A message's title holds only PayOnce's words and identifiers that match `^[A-Za-z0-9-]{1,40}$`. Any other invoice id reads "an invoice" ("An invoice" at the start of a title), and its alert links to the page root. Text PayOnce did not write (an `AlertText` with `outside` true: the supplier name and the escalation reason, which can name other invoices or hold an Airwallex code) is rendered as an inline code span in both formats, after `defanged` drops every format character (Unicode `Cf`, which takes in bidi controls, zero-width characters, the soft hyphen, U+180E, U+206A to U+206F and tag characters) and the unassigned rest of the tag block U+E0000 to U+E007F, turns `://` into `[:]//`, a word-start `www.` into `www[.]` and a backtick into an apostrophe. Outside text with nothing left after that is shown as a placeholder in PayOnce's words, not as a span: "(no name)" for a supplier and "(no reason recorded)" for a reason. The parts of a message's line are joined with a space, so the span never follows a letter directly, which Slack would not read as code. On Slack the span also has `&`, `<` and `>` escaped; on Discord nothing inside a code span is read as markdown, a link or a mention. The only link is the one to the local page, built by PayOnce.
- Slack: `text` (the notification) is the title only, then a `header` block (plain text, at most 150 characters), a section with the line, a section of up to 10 fields, and a context block with the local link, with `unfurl_links` and `unfurl_media` false. Every `mrkdwn` text object has `verbatim: true`, so Slack does not turn a bare URL, domain or channel name into a link or parse a mention. The `<url|text>` link to the local page still works. Discord: `username`, `content` (the title, markdown escaped), one embed (title, description with the bare local link, colour, fields, footer, timestamp) and `allowed_mentions: { parse: [] }`, with no embed `url`. `capped` escapes first and then cuts between whole characters, so no escape or surrogate pair is split and the result never passes its cap: the supplier 200 characters, the reason 600, any other value 300, the title 150 on Slack and 256 on Discord, all inside Slack's 2,000 per field and Discord's 1,024 per field value and 6,000 per embed.
- The link is `http://127.0.0.1:<PORT>/#<invoice>`, `#run/<id>` for a run, `#recon` for reconciliation's alerts, and the page root otherwise (the inbox alert included), never the tunnel's address.
- While alerts are on, the server asks `BalanceCache` for a read when no read is 5 minutes old and it has not asked in 5 minutes, so the cash condition sees a falling balance with no page open. Like every good balance read, each one runs `recordMissingFees` after it, which can read up to five more transfers.

## Email reader

- `READER_API_KEY` in `.env` turns the model reader on. `READER_BASE_URL` defaults to Gemini's OpenAI-compatible endpoint. `READER_MODEL` is a comma-separated list tried in order and defaults to `gemini-3.5-flash,gemini-3.1-flash-lite`, both on Google's free tier.
- `pnpm dev` loads no env file, so it always uses the keyword placeholder.
- "Ask why" uses the same key, base URL, model list and timeout (see Ask why). One ask is at most one request per model, and the page's limits leave most of the free tier's calls a minute to the reader.
- The request is one chat completion per email with `reasoning_effort: "low"` and a `json_schema` response format. The model answers three booleans (`claimsNonReceipt`, `asksForNewBankDetails`, `asksNotToPay`) and no text. `toAnswers` checks the answer again, so a service that ignores the schema still cannot return anything else. The display name, Reply-To, the text found inside styles, attachment names and PayOnce's notes go in tags of their own, and the prompt says nothing in the sender's tags comes from PayOnce.
- `summarise` in `src/emails.ts` writes the summary from the findings for both readers, so no wording from an email or a model reaches the approval card or the approval binding.
- `ModelReader` also runs the keyword check and ORs the findings. Every finding only makes the policy more cautious, so a tricked model cannot remove a finding the keywords make. It can still hide one the keywords miss. The keyword check reads the display name, subject, body, style text and attachment names after `keywordText`: blank-looking letters become spaces, default-ignorable characters go, NFKC, straight apostrophes and one space for every whitespace run, so wrapped lines and curly apostrophes match.
- Each model gets one request with an 8 second timeout. If it fails, the next model is asked, and the console gets a `reader` line saying why. A refused key (401 or 403) stops at once. If every model fails, `read` throws, the engine marks the thread unread, and the policy escalates.
- Findings carry `readBy`, the model that answered, and the page shows it.
- The API key is cut out of any error text before it reaches the timeline, in every form `redactKey` cuts.
- Google may use free-tier content to improve its products. The fixtures are synthetic. The page's "Supplier email" card says so next to the upload, and names the reader.

## Ask why

- A person asks why PayOnce did what it did on an invoice, with the "Why this happened" card or `pnpm ask <INVOICE>`. The question is fixed, so nothing typed reaches the prompt. The answer is display-only: never stored in the ledger, the timeline, approval terms, alerts, drafts, `localStorage` or the console, and nothing PayOnce decides reads it. `engine.ts`, `decide.ts`, `approval.ts`, `alerts.ts`, `alert-payloads.ts` and `drafts.ts` never import `why-facts.ts` or `explainer.ts`.
- Every value in the facts is PayOnce's own words, a closed pattern (a bank reference `^[A-Z0-9-]{1,30}$`, a transfer id as a UUID, a status `^[A-Z_]{1,30}$`, a currency, an amount `formatMoney` wrote, a date, an ISO time, a rate `1 EUR = 1.1191 USD`, a count), a failure code in PayOnce's words (`FAILURE_WORDS`, with an Airwallex error code passed only from `KNOWN_CODES`, else "an error code PayOnce does not pass on"), or an alias. A wallet or transfer method that is not a currency code or `LOCAL` or `SWIFT`, as Airwallex can give for a payout found there, goes in PayOnce's words. The invoice explained is "this invoice", other invoices in the ledger are `[invoice N]`, and people are `[person N]` when the name is in `APPROVERS`, signed one of this invoice's approvals, started it, closed it without paying or recorded a callback on it. Any other name is "a person". The legend swaps aliases back only in the answer shown.
- The facts: the invoice (state, origin, run and row, amount, wallet, method, due date, who started it, booleans for a supplier domain and a phone on file, held before paying, the escalation reason, who closed it without paying, the latest decision and waiting lines, the invoices it looks like a second bill for), each payment (kind, reference, state, status, created, deadline and whether it passed, failure, whether a resend could fix it, what it took from the wallet, fee, the approval it was opened on, the approved rate, a rate mismatch as a boolean, found late, a transfer that does not match the invoice, and when it usually arrives), outside payouts, the emails (`emailEvidence` when its text is in the closed form, counts, the three findings, whether the reader failed, and `readBy`, only when it is one of `readerNamesFromEnv` and "the email reader" otherwise), the latest approval picked field by field, `pendingClose` with its reason, the cash (wallet, floor, where the floor comes from, committed money; the balance is not read), the policy as read now, outages (every active one, and every ended one that held this invoice: number, rail, state, times, codes, payees counted, window and what it held), the last 60 timeline lines and how many were left out or not passed on. Never `payTo`, `accountKey`, the beneficiary id, the quote id, the binding, the callback's number, contact or words, the stored findings' `unverifiedSenders`, an email or upload field, `payout_reference`, `supplier_phone`, a run's file name, who ended an outage or its note, or `policy.problem`.
- Reasons (the escalation reason, the reason in terms, the close card's reason and the body of each decision line) go through the grammar: one or more parts joined by ", and ", each matched whole at its position, with backtracking, so a part that holds ", and " is never split. Fixed parts come from the exported constants, and the parts with slots (a currency, an invoice or a list of them, a refusal code, a rate mismatch, a misdirected or late transfer) give only the safe slots. A reason that does not parse becomes "(a reason PayOnce does not pass on)", and the console gets `  why      N unrecognised reasons on <invoice>`, with no text. The arrival clause and the held suffix of a decision line are handled apart.
- Timeline lines pass only through `FIXED_LINES` and `LINE_RULES`, checked in order: a rule keeps a line whose slots are all closed patterns, or rewrites it in fixed words with only the safe slots (sender checks, payouts with their payee or reference, the email delivery line, bank lines with Airwallex's message, waiting lines with `payTo` or the phone, signoffs, callbacks, close notes, outage ends, drafts, a run's first line, the refusals of `send`). Each rule and fixed line names the sources it may come from, a kind and a topic such as `decision/decision`, `approval/waiting` or `error`, and passes no line from any other source. An error line holds whatever message the error had, and a callback line starts with a name someone typed, so neither can pass as a decision, a bank line or a closing line. An error line passes only as the fixed words of a rule for one of PayOnce's own errors (a lock wait, a refused or unfinished send, the reader failing, a refused bank change), or as the stand-in. Every line then passes `SAFE_LINE`. A line no rule knows, such as an Airwallex or network error, becomes "(a/an KIND line PayOnce does not pass on)" and is counted in `timelineLeftOut`. A template added later with outside text in it fails closed until it gets a rule.
- The request has the reader's shape (`Authorization: Bearer`, `reasoning_effort: "low"`, a strict `json_schema` of two strings, `explanation` and `notInFacts`, and the 8 second timeout), plus `max_tokens` 1,000. The user message is `<facts>` JSON `</facts>`, with `<` and `>` written as `\u003c` and `\u003e`. Each model gets one request, in `READER_MODEL`'s order. A failure (an error status, a timeout, a body that is not JSON, `finish_reason` other than `stop`, other fields than the two, an empty explanation) moves on to the next, and the console gets `  why      MODEL gave no answer after N ms: ...`. A 401 or 403 stops at once. `redactKey` cuts the key out of every error and out of both strings of an answer, since a service that echoes the key in an error could echo it in an answer too.
- `shownAnswer` runs `cleanText`, drops Unicode `Cf` and the tag block, collapses whitespace, caps the explanation at 1,000 characters and `notInFacts` at 300 (at the last sentence end, else the last space with an ellipsis, `cut` true), then swaps `[invoice N]` and `[person N]` back from the legend. `aliasesLeft` says the text still looks like it holds an alias, and only then do the page and the CLI show the legend.
- `POST /api/incidents/:id/why` takes `{}` and goes through `guard`, so another site cannot spend the quota. It does not take the invoice's turn: the facts are read in one snapshot, and the model is asked after it closes. 200 gives `{ explanation, notInFacts, cut, model, at, cached, asOf, legend, aliasesLeft }`. 404 for an invoice not in the ledger, 503 without `READER_API_KEY` (no facts are built), 500 when the facts cannot be built (nothing is sent), 409 while another ask runs, 429 with `retryAfterSeconds` and a `Retry-After` header, 502 when every model failed. `GET /api/options` carries `explainer: { on, models, host, googleFreeTier, perMinute, perDay }`. The server logs `  why      INV answered by MODEL in N s (N characters)`.
- `ExplainLimiter`, per server process and in memory only: one ask at a time; an answer remembered for 10 minutes by `factsKey` (SHA-256 of the invoice, the facts as sent and the model list), at most 50, oldest dropped, which costs no request and counts toward no limit; 2 asks started per rolling minute and 30 per UTC day; and a minute's pause after every model answered 429. The CLI is not limited.
- The card `#why` sits at the top of the incident's side column. It is redrawn only when its state changes, so the poll does not wipe an answer. Off without a key (button disabled, a hint); idle (the hint names the models and Google's free tier when the reader uses Google's endpoint, and the host for any other service); asking (the button disabled with the pulse); answered (the text in `<p>` text nodes, "Not in the records", the legend when aliases are left, the model and time, "Ask again"); cached (says nothing has changed since the time it was asked); stale (a caution when the timeline has a line past `asOf.lastEventId`, shown in place of the cached hint); error (`form-error`, "Try again"); limited (the button disabled until `retryAfterSeconds` has passed, for every invoice; the error that said when goes once the button comes back). Answers are kept per invoice for the page's session only. The page cleans the legend's names and the answer's text the way `pnpm ask` cleans them for the terminal: control characters and line breaks become spaces, and format characters and the rest of the tag block are dropped.
- `pnpm ask <INVOICE> facts` prints the system message, the user message exactly as sent, and the legend, and calls nothing, with or without a key. `pnpm ask <INVOICE>` prints the answer wrapped at 80 and the label. It strips control and format characters from names and invoice numbers after it swaps the labels back, as `pnpm board` does. It exits 1 for a missing argument, no ledger, a ledger an older PayOnce wrote, an invoice not in the ledger, no key (pointing to `facts`) and every model failing. After a request it sets the exit code instead of calling `process.exit`, because exiting while fetch's socket closes trips a libuv assertion on Windows.

## Web server

- It binds to loopback and has no login. `guard` checks the Host header and, for writes, the Origin header and a JSON content type. It refuses an `/api/` GET with 403 when `Sec-Fetch-Site` is present and is neither `same-origin` nor `none`, or when an `Origin` header names another origin (`crossSite`). Static files stay open. `X-Content-Type-Options: nosniff` is set once before routing, so every response has it, CSV downloads and errors included.

## MCP server

- `pnpm mcp` (or `node --import <tsx loader URL> src/mcp.ts`, as the client settings in the README start it) serves eleven tools over stdio, in this order: `board`, `incidents`, `incident`, `cash`, `runs`, `run`, `audit`, `outages`, `suppliers`, `supplier`, `metrics`. It only reads. No tool approves, closes, pays, sends, drafts, uploads, ends an outage or writes the ledger.
- Each call opens the ledger with `new Ledger(path, true)` and closes it in `finally`, so the process holds no connection between calls and `pnpm reset` can still rename the file. A missing file is refused in PayOnce's words and never created. The refusal gives the file's path from the PayOnce folder, or only its name when `PAYONCE_LEDGER` points somewhere else, because that path can hold the user's name. A file that `schemaGaps` finds lacking a table or column, written by an older PayOnce, is refused and never upgraded; `pnpm board` or a restart of `pnpm ui` upgrades it, but only the `payonce.db` in the folder they run in, so neither touches a `PAYONCE_LEDGER` file elsewhere, though the refusal still names them. SQLite would refuse a write on the read-only connection anyway. Reads are not wrapped in one transaction, as in the JSON API.
- It never imports `server.ts`, which builds an `AirwallexClient` and opens a writable ledger at import. It builds no Airwallex client and loads no credentials. From `<root>/.env` it keeps only the lines that set `RESERVE_FLOORS`, `BANK_DEADLINE_LOCAL_MINUTES`, `BANK_DEADLINE_SWIFT_MINUTES`, `OUTAGE_FAILURES`, `OUTAGE_WINDOW_MINUTES` or `PORT` (with or without `export`) and parses those alone, so the credentials and every other setting are never parsed into values. It copies only the settings not set already. `PAYONCE_LEDGER` comes from the client's settings, not `.env`. `console.log`, `info` and `debug` go to stderr, because stdout carries only MCP messages.
- Its one network call is `GET http://127.0.0.1:<PORT>/api/cash/cached`, with a 1.5 second timeout, no redirects and 4 MB at most. From the answer `cachedBalances` takes the balances and the floors as numbers, and Airwallex's error message as text, and `cashView` works the panel out again on the MCP's own ledger, so the headroom is the page's. A floors problem the server reports becomes "PayOnce's server could not read RESERVE_FLOORS", because its text cannot be vouched for. With no server, an older one that answers 404, or an answer that is not a cash panel, the floors come from `RESERVE_FLOORS`, there is no balance or headroom, and `balance.why` says why.
- `marked` walks each finished answer once. A sentence stays plain only at a full path in `PLAIN`, where a view builds it as the tool answers, from fixed wording and PayOnce's own figures, whatever the ledger holds: the board's `entries[].why`, `entries[].also[]` and labels, and an incident's `board.why` and `board.label` in `incidents`, the `supplier` tool's `cautions[].text`, `invoices[].board.(label|why|also[])` and `invoices[].emails.findings.summary`, the outage code labels (`RAIL_FAILURE_CODES`, or "rail failure"), `balance.why`, `emails.findings.summary` (from `summarise`), `approval.barred[].why`, `rows[].feeSeen` (only for a row whose currency is three capital letters and whose estimate `vouchedArrival` accepts), the `arrivalAdvice` sentences, `numberCalledLast4`, the audit wording (`audit.problem`, `breaks[].problem`, `runs.problem`), the outage rule's `rule.problem`, and the metrics' four label paths (`failures.rows[].label`, `outages.rows[].codes[].label`, `incidents.reasons[].label`, `recon.rows[].label`). A key of the same name anywhere else, such as inside stored approval terms, is not plain. A plain sentence still goes through `defanged` and `maskPhones`.
- After the plain paths, rules go by the string's path, first match wins. The email evidence (`approval.terms.evidence.emails` and `review.emails`) is wrapped as `quoted` unless it is exactly today's wording of `emailEvidence` and `summarise` (`EMAIL_EVIDENCE`). An older PayOnce put the sender's address there, as approvals 1 and 3 in the main ledger still show, and `review.emails` is built from the stored summary, which an older reader wrote itself. `approval.neededWhy` is wrapped as `quoted` unless it is empty, because it can name an invoice, a payee or a currency. `report.floors.problem` is wrapped as `quoted` unless it is `SERVER_FLOORS_UNREADABLE`, because this process's own problem quotes the `RESERVE_FLOORS` it could not read. An estimate's `country` (Airwallex's `bank_country_code`) stays plain only as two capital letters (`COUNTRY_CODE`), and its `route` only as one of `ROUTES`. The advice and the fee line are built from a stored estimate only when `vouchedArrival` accepts it: the method is LOCAL or SWIFT, the route is one of `ROUTES` or none, and the days and day counts are in PayOnce's own forms. A country that is not a code is left out of the advice. Any other estimate gets no advice, so text stored in an estimate never reaches a plain sentence. The terms still show the estimate, and whatever in it does not fit is wrapped. A reference, failure code, transfer status, rail, reader name (the keyword reader's name, or model ids joined by ", then ") or board reason code stays plain only when it fits its pattern.
- These are always wrapped: supplier names and domains (`supplier`, or `run-file` for a run's rows and domain checks), `payee`, `payTo`, `payoutReference` and an error message (`airwallex`), people's names and notes (`person`), and timeline lines, headlines, escalation, skip, close and rate-mismatch reasons, every other `problem` (a run's stored cash check included), a run's domain sentences and outage text (`quoted`). Any other string stays plain only as a token (an ISO time or day, a 64-character hash, a UUID, or 1 to 40 letters, digits, `_`, `:` and `-`) and is otherwise wrapped as `unknown`, so a field added to a view later is wrapped until a rule says otherwise. Wrapped text goes through `defanged`, `maskPhones` and `capped`: 200 characters for names, 600 for reasons, 2,000 for a timeline line and 300 otherwise. A token, or a code that fits its pattern, has only the phone numbers on file cut from it, so an invoice number of ten digits stays as it is.
- Phone numbers: `obligation.supplierPhone` becomes `phoneOnFile`, a callback's `numberCalled` in approval terms becomes `numberCalledLast4`, and in every wrapped string `maskPhones` cuts each phone number on file to its last four digits, however it is spaced and with or without its country code (matched by its last ten digits, since a callback may dial it that way), along with any `+` number of 7 digits or more and any other run of 10 digits or more that is not a date or an amount. A token or code shows the number on file, in either form, only as its last four digits.
- Left out: email bodies, subjects, senders, display names, Reply-To, style text and attachments (`incident` gives the counts and the findings, with the summary written again by `summarise`), the stored findings' `unverifiedSenders`, run file cells, the outbox, the inbox, alerts, the approver list (`outages` drops `enders`), and `busy` and `watching`, which only the server knows.
- An answer is `content[0]` `NOTICE`, `content[1]` the JSON and `structuredContent` the same object, with no `outputSchema`. A refusal is `isError: true` with PayOnce's words; anything unexpected goes to stderr and the answer names only the error's type, or the SQLite message for a ledger it cannot read, defanged and cut to 200 characters. A busy ledger (SQLite busy) gets "The ledger is busy with a write. Try again in a moment". A ledger with the journal of a write that never finished beside it (errcode 776, `SQLITE_READONLY_ROLLBACK`, which a read-only connection cannot roll back) gets PayOnce's words instead: a write was interrupted, and the next `pnpm ui` or `pnpm board` rolls it back. Those two roll back only the `payonce.db` in the folder they run in, so neither touches a `PAYONCE_LEDGER` file elsewhere. Input schemas are `z.strictObject`, so unknown keys are refused, and the SDK turns bad input into `isError` and an unknown tool into `-32602`. Every tool is annotated read-only, idempotent and closed-world. `listChanged` is false, and on 2026-07-28 connections `tools/list` and `server/discover` carry `ttlMs` 3,600,000 and `cacheScope` `public`.
- The SDK checks the revision on a connection's opening exchange and answers `-32022` with `supported` and `requested` for one it does not support. It then pins the connection, so a later request on it claiming another revision is served on the pinned one.
- The SDK is `@modelcontextprotocol/server` 2.3.1, published 2026-10-05 by the modelcontextprotocol/typescript-sdk release workflow with npm provenance, and `zod` 4.6.7. Both are pinned exactly. 2.4.0 was 10 days old when this was built, under the two-week rule, and its changes do not touch a stdio server with zod input schemas.

## Webhooks

- `pnpm ui` starts `WebhookReceiver` on `WEBHOOK_PORT` (4311, loopback). It answers `POST /airwallex/webhooks` and nothing else, so the tunnel exposes no other route. It answers 503 until it has the secret, so Airwallex retries.
- Without `WEBHOOK_URL`, `openTunnel` runs `cloudflared tunnel --no-autoupdate --url http://127.0.0.1:4311` (`CLOUDFLARED` sets the path) and takes the `trycloudflare.com` address from its output. The address changes on every start.
- `subscribe` finds PayOnce's subscription by the `request_id` prefix `payonce-transfers-` and moves it to the new address, or creates it with all nine `payout.transfer.*` events. The secret comes back from Airwallex and is held in memory only.
- `verifySignature`: HMAC-SHA256 hex of the `x-timestamp` header followed by the raw body, keyed with the secret, compared in constant time. A timestamp more than 5 minutes off is refused.
- The receiver takes the transfer from `data`, or from `data.object` when Airwallex nests it there.
- A paid, failed, cancelled or overdue event for a PayOnce transfer the ledger still has with the bank (`withBank`) puts a `bank` line on the timeline and wakes the agent. One for a payment the ledger already shows paid or failed changes nothing, and one for an attempt marked failed with no transfer asks for a sweep. Other events are only logged.
- The receiver prints refused requests (any answer but 200) at most once a minute: the first at once, and the rest counted and printed with the latest status when the minute is up (`RefusalLog`).
- With webhooks connected the watcher checks every 15 seconds. Without them it checks every 3, and the CLI every 2. `WEBHOOKS=off` skips the receiver, the tunnel and the subscription.
- `WEBHOOK_API_VERSION` defaults to `2025-06-30`. No response header says which version the account uses.

Found by running it on 2026-10-28:

- A webhook `request_id` is limited to 50 characters.
- The list call returns each subscription's secret. The update call moved PayOnce's subscription to a new tunnel address and kept its id.
- In three incidents, with about ten transfer status changes, Airwallex delivered no event within 12 minutes. The tunnel answered a request from outside, and the subscription listed the right address and events. The watcher caught every change. Delivery status per event is under Settings > Developer > Events in the web app, which needs the account owner's login.
- Checked in the web app later the same day: Airwallex creates an event for every status change (`scheduled`, `processing`, `sent`, `paid`, `failed`), with the transfer directly under `data` and `version` `2025-06-30`, addressed to the subscription's URL. Every event stayed `Queued` with no HTTP status, so none was ever attempted. With a fresh tunnel and the subscription moved to it, "Send test event" and "Re-trigger" in the web app delivered nothing either, while a POST from outside through the tunnel reached the receiver and got its 401. The sandbox records events but does not deliver them to this account.
- The scripted incidents with the watcher on: a replaced payment from start to close in 11 seconds through `pnpm recover`, and about 50 seconds for each escalation on the page while the watcher checked every 60 seconds.
- `winget install Cloudflare.cloudflared` waits on a UAC prompt. The standalone `cloudflared-windows-amd64.exe` from the GitHub release runs without admin rights.

## Sandbox behaviour found by running it

- Credentials are a scoped API key in `.env` (`AWX_CLIENT_ID`, `AWX_API_KEY`). Admin keys are deprecated.
- A new transfer starts `SCHEDULED` and moves to `PROCESSING` on its own within seconds. The simulator returns `500 operation_failed` for a transition requested while it is still `SCHEDULED`, so wait first.
- The simulator sometimes returns `500 operation_failed` after it has applied the transition. `simulateTransfer` reads the transfer after a server error and retries only if the target status was not reached.
- A transfer left in `SENT` was `PAID` about ten minutes later with no simulation call. This happened once.
- `PROCESSING` to `SENT`, `SENT` to `PAID` and `SENT` to `FAILED` (with `failure_type`) all work. A failed transfer reads `FAILED`, then `CANCELLED` a few seconds later. The `failure` object survives the change.
- `failure.details.type` is `INCORRECT_ROUTING` for every simulated failure. Read `failure.code` instead: 91401 system error, 91402 channel timeout, 90701 account closed, 90101 invalid account name or number, 90802 beneficiary bank returned, 91001 recall requested, 91301 duplication return, 99901 unable to apply, 99902 other.
- Creating a transfer takes the amount out of `available_amount` immediately. A failed transfer is refunded a few seconds later.
- A EUR SWIFT transfer of 4,000 carried a fee of 13.91 or 13.92 EUR. When it failed, the 4,000 came back and the fee did not.
- The beneficiary record and a transfer's `beneficiary.bank_details` hold the same object. The transfer keeps the details it was sent with: `POST /api/v1/beneficiaries/{id}/update` changes the record and not the transfer, and setting the old values back makes the two equal again.
- Reusing a `request_id` returns `400 duplicate_request_id` and names the original transfer.
- Run on 2026-10-28: `POST /api/v1/beneficiaries/{id}/update` with the GET record's `beneficiary` (without `fingerprint`), `nickname`, `payer_entity_type` and `transfer_methods` was accepted. Airwallex rewrote `bank_name` from the routing number ("Bank of America" became "Bank of America, NA"), so the read-back compares only the fields that say where money goes. The next transfer to the beneficiary went to the new account.
- The scenarios share one beneficiary per currency, so a bank change on one would reach the others. Each `usd-local-bank-change` run creates a beneficiary of its own, nicknamed `PayOnce demo supplier (bank change)` plus the invoice number.
- LOCAL USD transfers carry no fee in the sandbox.
- Run on 2026-10-28: `reserved_amount` and `pending_amount` in `GET /api/v1/balances/current` read 0 in USD while a 4,000 USD transfer was in `SENT`. Money in flight cannot be read from the balance, so the panel takes it from the ledger.
- The client sends no `x-api-version` header. The account default returns the newer status set (`FAILED` exists) with a nested `failure` object.
- Airwallex emails the account owner for every sent and cancelled transfer unless transfer notifications are turned off under Settings > User settings > Notifications. On 2026-10-28 the email for cancelled transfers was turned off there. Sent, overdue reminders and the daily summary of scheduled transfers were already off.
- `GET /api/v1/transfers` takes `from_created_at` as an ISO time with milliseconds and `Z`, and takes `status`. It lists newest first and pages with `page_size` and a `page` cursor taken from `page_after`.
- A transfer's `beneficiary` has `bank_details`, `address`, `entity_type` and `type`. `bank_details.account_name` is the only name on it.
- `created_at` reads like `2026-10-27T19:48:09+0000`, which `Date.parse` accepts.
- FX probe on 2026-10-28. `POST /api/v1/fx/quotes/create` takes `sell_currency`, `buy_currency`, `buy_amount` and `validity`, and the sandbox requires `validity`. Quotes are `MULTI_USE`, and `GET /fx/quotes/{id}` returns the same body after expiry and after use. A transfer with `source_currency` USD, `transfer_currency` EUR and a `quote_id` was accepted with the usual body. It carries `conversion: { currency_pair: "EURUSD", rate }` with `rate` equal to the quote's `client_rate`, `source_amount` equal to the quote's `sell_amount`, and a fee in the source currency (15.60 USD for SWIFT, `SHARED`, and 15.59 on a later run). USD `available_amount` fell by `amount_payer_pays` at creation, and EUR did not move.
- The quote's `currency_pair` is the market convention (EURUSD, USD per EUR) whichever way the money goes. Compare rates as Airwallex gives them and never invert one. `HR_1` cost about 0.12 percentage points more than `MIN_1` over mid-market.
- Reusing a request id after its quote expired returned `400 duplicate_request_id` naming the existing transfer: the duplicate check wins over the quote check.
- The simulator returns `500 operation_failed` for every transition of a transfer that converts (`SENT`, `PAID`, `FAILED`, `CANCELLED`), across 13 minutes. The probe's two transfers, `P261028-O6T855P` (`FX-PROBE-A`) and `P261028-937JTEB` (`FX-PROBE-B`), stayed in `PROCESSING`. From about 12:27 UTC the same day the simulator refused same-currency transitions too, until about 15:00 UTC, when they worked again. Nobody tried a converting transfer again after that. A failed converting payment and its replacement cannot be shown in this sandbox, and what a failure refunds was not observed. By Airwallex's docs, a converting transfer is refunded in the transfer currency by default, and the fee is not refunded.
- FX run on 2026-10-28 with `APPROVAL_TTL_MINUTES=2`: the `eur-from-usd` invoice was held, a request opened on an `HR_1` quote, and each 2 minute expiry opened a new request on a fresh quote. Sam, with a limit of 4,200, was refused on the 4,476.66 USD source amount. Alex's approval sent `P261028-71RA8Q0`: 4,476.40 USD at 1 EUR = 1.1191 USD plus a 15.60 USD fee, matching the approved quote. It stayed in `PROCESSING` and the invoice escalated at the 5 minute SWIFT deadline. The cash panel listed it under USD only.
- Runs on 2026-10-28. With the local deadline set to 1 minute, an original left in `SENT` escalated 63 seconds after it was sent. A failed payout made outside PayOnce was taken on within 30 seconds, and its approved replacement was paid and the incident closed 6 seconds after the approval. An outside payout made just before an approval was tied by the check before payment one second after the approval: the approval was voided and nothing was sent. When the bank paid that payout, the close card offered it.

Pay runs, checked on 2026-10-28 on a worktree ledger with hand-made invoices:

- `GET /api/v1/beneficiaries/{id}` answers 200 with an empty body for a well-formed id Airwallex does not have, and 400 `invalid_argument` for a malformed one. `findBeneficiary` treats a record whose `id` is not the one asked for as unknown. A record's `bank_details` carries `account_currency` and `account_name`.
- From about 12:27 to about 15:00 UTC the simulator answered `500 operation_failed` on every transition, so no paid or failed outcome could be seen for a run row in that time. A two-row run released at 13:33 waited 6 seconds for a USD lease another process held, then created P261028-NLOYLPE and P261028-OAM9OUA one after the other and held a third row as a likely duplicate. Both transfers stayed in `PROCESSING`, and both invoices escalated at their 3-minute deadline.
- By about 15:00 UTC same-currency transitions worked again: P261028-3JMKQFD moved to `PAID`. On the integration branch a pay run then paid one row (P261028-QO9B589) and failed another with `CHANNEL_TIMEOUT` (P261028-JY3VK1Q), and an automatic replacement (P261028-L968UVS) was paid. A converting transfer, P261028-C9NWDL7, went out on its approved quote and stayed in `PROCESSING`. The sandbox bank never asks the simulator to move a converting transfer, so nobody checked whether the simulator still refuses them.
- An automatic replacement that decided Replace, then waited for the lease while 1,000,000.00 USD was committed on another invoice, read the balance again under the lease and escalated with the floor reason, sending nothing.
- Merged build, checked on 2026-10-28 on a copy of the main ledger while the simulator was down. An `eur-from-usd` incident was held and a request opened on an `HR_1` quote at 4,476.44 USD, needing one approver. The cash panel listed it under USD, with the amount from the quote. ## Conventions

- The code uses explicit type annotations and few comments.
- TypeScript 7 needs `"types": ["node"]` in `tsconfig.json`.
- pnpm 12 blocks install scripts; `esbuild` is allowed in `pnpm-workspace.yaml`.
- The only direct runtime dependencies are `@modelcontextprotocol/server` and `zod`, pinned exactly and imported only by `src/mcp.ts`. The SDK brings `@modelcontextprotocol/core` 2.3.1. None of the three has install scripts.
