# PayOnce

Payment incident agent for the Airwallex Agentic Banking Hackathon 2026, built on starter kit 3. TypeScript, pnpm, Node 24. Sandbox only.

## Commands

```bash
pnpm install
pnpm typecheck                                      # tsc --noEmit
pnpm dev                                            # policy on seven sample incidents, no credentials
pnpm ui                                             # web page and JSON API at http://127.0.0.1:4310, webhook receiver on 4311
pnpm recover [OUTCOME] [INVOICE] [EMAILS] [SCENARIO] [NAME] # one incident against the sandbox, or continue an existing invoice (status checks, no webhooks)
pnpm approve <INVOICE> [REQUEST NAME]               # show the waiting approval (a replacement, or paying a held invoice), its request number and the policy; with both, record that person's approval of that request
pnpm close <INVOICE> [NAME] [NOTE]                  # show a paid incident or a held invoice waiting on a person; with NAME and NOTE, close it (a held invoice without paying)
pnpm run audit [INVOICE] [json|csv]                 # check every invoice and pay run timeline and both running hashes, or one invoice's; with a format, print its audit trail
pnpm run audit run <RUN> [json|csv]                 # the same for one pay run's timeline
pnpm cash                                           # read balances once and print each currency down to the headroom above its floor; exit 1 if Airwallex is unreadable, a floor is unreadable or a headroom is below 0
pnpm payrun upload <FILE> <NAME>                    # check a pay run CSV (Airwallex GETs only) and store it as a run waiting for approval; NAME is required
pnpm payrun show <RUN>                              # rows, cash, the waiting request, its number and who is barred
pnpm payrun approve <RUN> [REQUEST NAME]            # show the terms; with both, record that approval. pnpm ui releases the run
pnpm payrun check <RUN>                             # run every check again (GETs only) and open a new request if the old one expired or the terms changed
pnpm payrun cancel <RUN> <NAME> <NOTE>              # cancel a run that is waiting
pnpm reset                                          # move payonce.db aside so the next run starts an empty ledger
```

Defaults: OUTCOME `CHANNEL_TIMEOUT`, EMAILS `nothing-arrived`, SCENARIO `usd-local`, NAME the OS login name (who started the incident). OUTCOME is a simulator failure type, `PAID`, or `STAYS_IN_FLIGHT`, which leaves the original in `SENT`. `pnpm audit` is pnpm's own dependency audit, so the audit command needs `run`. There is no lint script and there are no tests.

## Structure

- `src/decide.ts`: pure decision policy (wait / replace / escalate / close). Rules stay in code; the model never decides amounts or moves money. `floorReason` is its cash check, which the engine also runs before it spends an approval.
- `src/incident.ts`: `Incident` and `Decision` types. Amounts are minor units.
- `src/engine.ts`: the agent, shared by the CLI and the server. `resumeIncident` looks at an invoice: it syncs the payments, reads new emails, decides and acts. `deliver` puts a fixture thread's emails on an invoice (uploads go through `src/intake.ts`), and `noteSenders` writes the sender and Reply-To check. `startPayment` sends a new invoice's original or holds the invoice for a person; given the account key a pay run approved, it also holds the row when the record changed or the floor would be breached (`CASH_HOLD_REASON`). `startFirst` sends an open invoice's first payment from a look: a pay run row's only when the look has the run's turn (`sendRunRow`), and any other invoice's after its first send failed. `replaceUnderLock` is the automatic replacement. `AccountChangedError` is what `requireAccount` throws. `approvePayment` records an approval of a replacement or of paying a held invoice, `closeIncident` records a person closing a paid incident or closing a held duplicate without paying, `payAgain` puts a person's second payment to the lock, `note` writes the timeline. `Bank` is the hook told about each payment sent. `linkOutsidePayout` ties a payout sent outside PayOnce to the invoice its reference names or nearly matches. `rateFor` takes a new exchange rate quote for a cross-currency payment or reuses one, and `checkRate` compares a transfer with the quote its approval named. The engine never simulates a bank outcome.
- `src/dispatcher.ts`: `Dispatcher` runs steps one invoice at a time. `wake` queues a look at an invoice, and a wake that arrives before a queued look has started is dropped. `wake(invoiceId, true)` gives the look the run's turn, so it may send a pay run row's first payment. A wake with the turn that finds a look already queued hands the turn to that look.
- `src/watcher.ts`: the fallback for webhooks. `Watcher` reads every transfer the ledger shows in flight, PayOnce's own and outside payouts tied to its invoices, and wakes the invoice when the bank has paid or failed one. It also wakes an invoice whose next look is due and one with an approval nobody has acted on. Given an interval, it runs the sweep. `lastCheckedAt` is when the last check that read every payment with the bank without an error started. A check with a failed read leaves it as it was, so the panel's "payment states checked" age grows while Airwallex cannot be reached. Given `release` (only `server.ts` passes it), it releases a waiting run whose request is approved, at most once a minute per run, and wakes a released row that has not sent, with the run's turn, one per run per check, only while the run's key is not busy. Without it, as in `pnpm recover`, it never touches an unsent run row.
- `src/deadlines.ts`: how long the bank has to pay or fail a transfer, by transfer method, counted from the transfer's `created_at`. `isOverdue` treats a time it cannot read as overdue.
- `src/sweep.ts`: `sweep` lists the transfers created since the ledger started and deals with the ones PayOnce did not send.
- `src/duplicates.ts`: `sameInvoiceNumber`, `sameNumberExactly` (the same number with no letters added), `likelyDuplicates` (the other invoices a new one may be a second bill for), `sameNumberForSupplier` (the other invoices to the same supplier whose number `sameInvoiceNumber` matches, for any amount or currency), `sameBillAndNumber` (the same test for two bills not in the ledger, such as two rows of a file), and `nearlyPays` and `invoiceForPayout` (the invoice a payout sent outside PayOnce is for).
- `src/sandbox-bank.ts`: `SandboxBank` plays the bank in the sandbox. It sends a new transfer to `SENT`, pays or fails it when the scenario says so, and pays every replacement. The scripted run sends its original inside `scripting`, and the bank leaves that one to the script. Any other original gets the outcome `expectOriginal` recorded in this process, else what `outcomeOf` reads from the ledger (a pay run row's `sandbox_outcome`), else is paid. It reads each sent transfer first, and tries again up to four times on a server error or a lost connection, as the simulation calls do. A transfer that converts is left alone, because the simulator refuses to move it. Before its deadline the bank reports it once: one error line on the timeline, and the error with its stack trace on the console, as `noteError` prints every error. `PAID_OUTCOME`, `STAYS_IN_FLIGHT` and `SANDBOX_OUTCOMES` (the page's bank outcomes and a run file's `sandbox_outcome` values) live here.
- `src/scenario.ts`: the demo payments (`SCENARIOS`), `openScenario`, `runScenario` (the scripted incident) and `untilAtRest`. A held invoice stops the script before anything is sent, and no supplier emails arrive for it. When the script's first send fails, it records the scenario's outcome with `expectOriginal`, so the bank gives it to the original that the next look sends. `eur-from-usd` is the one scenario with a `sourceCurrency`.
- `src/webhooks.ts`: `WebhookReceiver` and `verifySignature`.
- `src/tunnel.ts`: `openTunnel` starts a cloudflared quick tunnel and reads its address from cloudflared's output.
- `src/assess.ts`: maps an Airwallex transfer to `originalState` and `resendCanFix`, compares bank details, and reads the fee the payer paid (`feeOf`) and what a transfer took from the wallet before the fee (`debitOf`). `record`, the sweep, `payoutMoney`, `rateMismatch` and `conversionText` all read the debit through `debitOf`.
- `src/ledger.ts`: SQLite tables for obligations, attempts, approvals, emails, findings and events. `isExpired` and `expiryOf` say when an approval request stops covering a payment.
- `src/payments.ts`: idempotent send and status sync between Airwallex and the ledger. `recordMissingFees` reads the fee of up to five failed transfers the ledger has none for, those never tried or tried longest ago first. A transfer whose fee it could not record is read again only after 10 minutes.
- `src/reserve.ts`: the reserve floors. `reserveFromEnv` reads `RESERVE_FLOORS` (currency:amount pairs, major units), `currencyFloor` gives one currency's floor and where it comes from, `floorFor` gives the floor one invoice's replacement is held to, and `describeFloors` is the start-up line. `debitCurrency` is the wallet a payment leaves: `obligation.sourceCurrency`.
- `src/cash-position.ts`: the cash panel. `cashLines` lists every amount the ledger knows about by kind, `committedMinor(ledger, currency, { invoiceId?, runId? })` adds up the promised ones the policy, the run checks and the panel all take off, leaving out the invoice or run being paid, `payRunLines` gives one `pay-run` line per row of an approved waiting run and per released row not sent yet (from `Ledger.payRunRows`), and `cashReport` works each currency down to its headroom. `lineAmount` is what a line takes from its wallet.
- `src/run-file.ts`: the pay run file. `parseRunFile` reads the CSV (RFC 4180 quotes, CRLF or LF, a BOM, blank lines skipped), refuses a file it cannot read with `FileProblem`s, and reads each row with `rowFromCells`, which a check also uses on the cells the ledger stored. `RUN_COLUMNS`, `MAX_RUN_ROWS` (50) and `MAX_RUN_FILE_CHARS` (40,000) live here.
- `src/runs.ts`: pay runs. `checkRows` (GETs only), `uploadRun`, `recheckRun`, `settleRunRequest` (keeps or opens the run's request inside the transaction that wrote the check), `approveRun`, `releaseRun`, `cancelRun`, `pendingRunApproval`, `runRule`, `runBarred`, `largestTotal`, `runNote` (the run's timeline) and `runKey` (the Dispatcher key `run:N`).
- `src/currency-lock.ts`: `withCurrencyLock` holds a lease on a currency in `currency_locks` around a payment and hands the step its `Lease`. `withCurrencyLocks` takes several in code order. Waiters queue in `currency_lock_waiters` and get the lock in the order they asked. `CurrencyBusyError` means 45 seconds passed behind the payments ahead.
- `src/fx.ts`: `quoteValidity` reads `FX_QUOTE_VALIDITY` when a quote is taken, as the bank deadlines are read, and throws on a value it does not take. `describeQuotes` is the start-up line.
- `src/approval.ts`: `ApprovalTerms` is `ReplacementTerms` (action `replace`, built by `termsFor`) or `HeldPaymentTerms` (action `pay`, built by `heldTermsFor`). `RunTerms` (action `run`, built by `runTermsFor`) is a run's. `bindingOf` is SHA-256 of the terms JSON. `payTo` is the pay-to line. `FxTerms` is the quote in the terms of a payment from another currency's wallet, built by `fxTermsOf` (and `withFeeEstimate`) in one key order. `paymentAmount` and `runAmount` are the only ways to make the `PaymentAmount` the approval policy takes. `describeRate`, `markupOf`, `paidWith` and `conversionText` write rates for people, and `rateMismatch` compares a transfer with its approved quote.
- `src/bank-change.ts`: `bankChangeForm` says what a person needs to record a callback about new bank details, or why one cannot be recorded now. `recordBankChange` checks the callback, writes a `bank_changes` row, updates the beneficiary in Airwallex and reads it back. It compares with the latest original that became a transfer.
- `src/approvers.ts`: the approval policy. `policyFromEnv` reads `APPROVERS` (name:limit pairs), `TWO_APPROVERS_ABOVE` and `APPROVAL_TTL_MINUTES`. `signoffsNeeded` says how many approvers a payment needs and why, `eligibleApprovers` who could approve it, `checkSigner` says why a person may not approve one, and `signoffProblem` checks an approval, an invoice's or a run's, against the policy as it is now. All four take a `PaymentAmount`, never a bare number.
- `src/emails.ts`: `EmailReader` interface (a `name` shown on the page, and `read`), `EmailFindings` (three findings), `summarise`, `unverifiedSenders` (From and Reply-To, ASCII only), `emailEvidence` (the email part of approval terms) and the fixture loader.
- `src/eml.ts`: `parseEmail` reads an uploaded raw email (bytes) into sender, Reply-To, subject, body, `styleText`, attachments (name, type, size), `notes` (fixed codes, `NOTE_TEXT`) and `partial`, or refuses it with PayOnce's own words. `cleanText`, `cleanLine`, `validAddress`, `validDomain`, `noteTexts`.
- `src/html-text.ts`: `htmlToText`, the one-pass HTML scanner, returning the text, `styleText` and whether styles or markup could draw characters PayOnce cannot read.
- `src/css-text.ts`: `scanCss`, the CSS tokenizer that takes out every string and any text that is not CSS, and applies the fail-closed rule.
- `src/intake.ts`: `storeUpload`, `candidatesFor` (the invoices an upload names), `deliverUpload` and the timeline lines for a delivery.
- `src/model-reader.ts`: `ModelReader` reads the emails it is given with one chat completion over plain `fetch`, with no SDK. The engine gives it one email at a time.
- `src/reader.ts`: `readerFromEnv` picks `ModelReader` when `READER_API_KEY` is set and the keyword placeholder otherwise.
- `src/keyword-reader.ts`: the fallback reader. It matches a handful of phrases.
- `src/server.ts`: `node:http` server for `web/` and the JSON API. It runs scenarios in the background, starts the watcher and connects webhooks.
- `src/audit-trail.ts`: how a timeline line is hashed (`canonicalEvent`, `eventHash`, `nextLedgerHead`), `chainBreaks` and `ledgerReport` to check them, and `auditExport` and `auditCsv` for the export. `canonicalRunEvent`, `runEventHash`, `runChainReport`, `runChainReports`, `runLedgerReport` and `runAuditExport` do the same for pay run timelines.
- `src/recover.ts`, `src/approve.ts`, `src/close.ts`, `src/audit.ts`, `src/cash.ts`, `src/payrun.ts`, `src/reset.ts`, `src/index.ts`: the CLI commands. `pnpm recover` refuses an invoice from a pay run that has not sent its original.
- `docs/demo.md`: the recording script for the four demo incidents, with sandbox times measured on 2026-10-06, before the agent waited for webhooks and status checks.
- `src/airwallex/`: `client.ts` (login, token refresh, 30 s timeout, refuses non-sandbox hosts), `transfers.ts` (`createTransfer` sends `source_currency`, and `quote_id` only when one is given), `fx.ts` (`createQuote`, `QuoteValidity`), `beneficiaries.ts` (`getBeneficiary`, `findBeneficiary`, which gives undefined for an id Airwallex does not have, `updateBankDetails`), `balances.ts` (`getBalances` and `getAvailableMinor` on the cash account only, and `BalanceCache` for the panel), `webhooks.ts` (`subscribe`), `simulation.ts` (every sandbox-only call).
- `web/`: static page (`index.html`, `styles.css`, `app.js`) with no build step and no external requests.
- `fixtures/emails/`: sample supplier threads. `{{invoice}}` is replaced with the invoice number. `new-account.json` uses a look-alike sender domain on purpose. `moved-banks.json` comes from the right domain, says the supplier changed banks and gives no account numbers.
- `fixtures/pay-run-example.csv`: a sample pay run file, with this sandbox account's demo beneficiary ids.

## Rules the engine keeps

- The agent learns what the bank did only by reading Airwallex. A webhook or the watcher wakes it, and it reads the transfer itself. Nothing in a webhook's body feeds a decision.
- Every step on an invoice goes through the `Dispatcher`, including a person's approve and close, so two steps never run on one invoice at once.
- The engine writes an attempt row, with its `request_id`, before the Airwallex call. A 4xx marks the attempt failed, except a 429. Any other error, a 429 included, leaves it pending, because the transfer may exist, and a later look retries it under the same `request_id`. This holds for every payment, not only pay run rows.
- Once an invoice is escalated, only a matching approval releases a payment, even if the policy would now replace.
- After sending a replacement the agent waits for the bank. It closes the incident on the look that reads the replacement as paid. A replacement already out is never approved a second time.
- Waiting on the bank has a deadline: the transfer's `created_at` plus `BANK_DEADLINE_LOCAL_MINUTES` (default 3) or `BANK_DEADLINE_SWIFT_MINUTES` (default 5). The look saves it in `obligations.look_at`, and the watcher wakes the invoice when it comes. `startPayment` saves it too, as soon as a new invoice's original is sent, so the look at the deadline comes even when no look runs before it, as when the sandbox bank's script fails. If the send's outcome is unknown, `startPayment` moves the next look a minute on, as a failed look does. An original still in flight then escalates. A replacement still in flight escalates too, with nothing more sent, and the incident still closes if the bank pays it.
- A look that throws leaves the next look as it was. If that time has passed or was never set, it moves a minute on, so a failing look is retried once a minute and not on every check. The watcher wakes an invoice for an approved or expired approval only when no later look is planned. A request that becomes approved makes the invoice's next look due at once, so a watcher in another process uses it on its next check.
- If a replacement has failed, the policy escalates instead of sending a third payment.
- Approvals follow the policy in `src/approvers.ts`, on the page and in `pnpm approve` alike. A name must be in `APPROVERS` and within its limit, compared with what the payment takes from the wallet it leaves, in that wallet's currency (`paymentAmount`). The person who started the incident (`obligations.started_by`) cannot approve. Two different approvers are needed above `TWO_APPROVERS_ABOVE`, for a payment to an account the original did not go to, and when `started_by` is null. Without `APPROVERS` every approval is refused.
- An approval request expires `APPROVAL_TTL_MINUTES` after it was opened. `escalate` returns the expiry as the next look, and that look opens a new request. `signOff` refuses an expired request inside its transaction, and a request it completes gets at least `APPROVED_USE_WITHIN_MS` (10 minutes) to be used. An approved request that expired before use is voided. A request recorded before expiry existed counts as expired, and the watcher wakes its invoice.
- `escalate` opens no request when `APPROVERS` is unusable or fewer approvers could sign than the payment needs (`eligibleApprovers`). It withdraws any open one and says so on the timeline.
- When one request replaces another that already had signoffs, the timeline says those approvals no longer count.
- An approval is spent with `useApproval` (or `releaseFor` for a held invoice), which only moves an `approved` row that has not expired to `used`, so one another process voided meanwhile, or one that expired during the look, is not spent. `useApproval` also spends nothing unless the invoice is still escalated and has no live outside payout, checked inside its transaction as `releaseFor` does. Each opens the payment's attempt in the same transaction, after the check that the record still holds the approved account, so the money counts as approved or as being sent at every moment and a failed check leaves the approval unspent. The attempt records the approval it was opened on (`approval_id`). `openAttempt` copies the quote from that approval's own terms, so a cross-currency attempt carries the quote that was approved and no other. The outside payouts are read again after the last list of transfers.
- The policy escalates a replacement above `TWO_APPROVERS_ABOVE` instead of sending it unprompted. Once the original has failed, `assess` asks `paidDuplicate` for a paid invoice among those `likelyDuplicates` finds, and keeps it on the assessment. Where the policy would replace, it escalates with "it looks like a second bill for X, which is paid", on every look. Where the policy escalates for another reason, `namingPaidDuplicate` adds ", and it looks like a second bill for X, which is paid" to the reason in the approval terms, after the floor clause, in `withFloorReason` and in the terms `requestedDecision` rebuilds. So every replacement request names the paid match whatever sent the invoice to a person, and an approval of terms that did not name it is void. `replaceUnderLock` looks again under the lease and builds its reason the same way, so the next look keeps its request. With no paid match nothing is added to the terms. `continueEscalated` checks again under the lease too. `useApproval` runs a check inside its transaction and spends nothing when `paidDuplicate` gives a different answer from the one `assess` got, as happens when another process records the match paid during the look. The next look is due at once: it voids the approval and opens a request naming the match. When the policy escalates for another reason, `escalate` also writes a standing `second-bill` warning, "Also, it looks like a second bill for X, which is paid", because the decision line gives only the policy's reason.
- `ApprovalTerms.accountKey` is a hash of the full bank details the payment goes to, because `payTo` shows only the last four digits.
- New bank details never come from an email or the reader. A person records a callback with `recordBankChange`: the number they called must match `obligations.supplier_phone` by its digits, with or without the country code, and it is only accepted once the invoice is escalated and every payment for it has failed. The details they type are merged into the beneficiary record, sent with `updateBankDetails`, and read back. The change is `applied` only if the record then holds them, with `applied_key` set to the record's `bankDetailsKey`.
- When the record's bank details differ from the original's, `escalate` requests an approval only if `verifiedBankChange` finds an applied change for that beneficiary whose `applied_key` equals the record now. Otherwise it opens nothing, withdraws any open request and waits for a callback. The terms carry the callback in `evidence.bankChange`, the request needs two approvers, and the person who recorded the callback is barred.
- Recording a callback withdraws the open request for the old account. It is refused while another open invoice to the same beneficiary has a pending attempt or an unspent approval, or a pay run row to it is approved or released and not sent (`payRunRows`), because the change would move that payment's account outside its turn. The fields not on the form must equal the original transfer's, and the call must come after the original was sent. Only the latest applied callback for a beneficiary counts, and everyone who recorded a callback for an account is barred from approving payments to it.
- Every replacement re-reads the beneficiary before it is sent and refuses if `accountKeyOf` the record differs from the approved terms' `accountKey`, or from the details the automatic decision was made on. After sending, a transfer whose details differ escalates with a warning. A pending replacement is first looked up by `request_id`, and is only sent again if the record still holds the approved account.
- Before an approval is used, `approvalProblem` checks it against the policy as it is then: every signoff has the request's binding, there are enough of them, and each signer still passes `checkSigner`.
- A payout PayOnce did not send, whose reference names an invoice in the ledger, is tied to that invoice. So is one that `nearlyPays` an invoice: same supplier, amount and currency, with a reference `sameInvoiceNumber` matches. The sweep ties a near match to an invoice not yet closed first, then to the oldest. A failed payout that only nearly matches a closed invoice is not tied: it becomes an incident of its own, with a warning naming the closed invoice. The check before a payment ties a near match to the invoice being paid, unless the reference names another invoice exactly. While one is in flight, paid or in an unknown status, the policy escalates before any other check, an open approval is withdrawn and nothing is sent. A settled or rejected invoice that gains one is reopened as escalated.
- Before any payment, an original or a replacement, automatic or approved, the agent lists the transfers again and ties any new payout for the invoice. If it finds one, it sends nothing, leaves the approval unspent and looks again at once.
- Any other payout PayOnce did not send becomes an invoice with origin `outside` once it has failed or is in flight past its deadline. The policy escalates where it would replace, so a person approves the replacement.
- No approval is requested for an invoice the ledger shows as paid once.
- Before a new invoice's original is sent, `startPayment` ties any unseen payout for it sent outside PayOnce. It then holds the invoice for a person if `likelyDuplicates` finds another invoice, not `rejected`, to the same supplier (same beneficiary or same name) for the same amount and currency, with a number `sameInvoiceNumber` matches; if `sameNumberForSupplier` finds such an invoice for any amount or currency, because PayOnce pays an invoice number once; or if an outside payout for it is live. These checks run in the transaction that opens the attempt. A held invoice is `escalated` with no attempt and `obligations.duplicate_of` listing the matches. Nothing is sent.
- `sameInvoiceNumber` ignores case, spaces, dashes and other marks, and leading zeros. It also matches a number to the same number with up to four letters added after the last digit, but not two numbers with different letters (`INV-42A` and `INV-42B`, `RENT-2026-OCT` and `RENT-2026-NOV`).
- `heldBeforePaying` is an escalated invoice that has sent nothing: every attempt, if any, failed without a transfer. Airwallex refusing every original (a 4xx on create) escalates the invoice, at once on the first send and otherwise on the next look, so it is held the same way.
- A held invoice pays only on an approval of `HeldPaymentTerms` under the same policy. Each look adds any invoice that `likelyDuplicates` now finds to `duplicate_of`, so one started later, or one that came first while this one was held for another reason, is listed too. The terms list each matched invoice with its state, the payment that paid it, and whether that payment, or one still with the bank, went to the same account. A change in any of them voids the approval. When the payment that paid a matched invoice, or else one still with the bank, went to another account than the one on file (`sameAccount` false), the request needs two approvers and the timeline warns. A match that was paid to the same account does not by itself need a second approver.
- On a matching approval, `continueHeld` ties unseen payouts and checks the record still holds the approved account. `Ledger.releaseFor` then spends the approval, moves the invoice back to `open` and opens the original's attempt in one transaction, which changes nothing if the approval is no longer approved, the invoice has been closed or has sent something, or an outside payout for it is live. It also changes nothing when `duplicatesOnFile` (each matched invoice's state and its payments that have a transfer) differs from what it was when `continueHeld` built the terms, or when `likelyDuplicates` finds an invoice the terms do not list. The next look adds that invoice to `duplicate_of` and to the terms. The invoice then carries on like any other. A pending original paid on such an approval is retried only if the record still holds the approved account.
- A person closes a held invoice without paying through `closeIncident`, which calls `Ledger.reject`: state `rejected`, with `rejected_by` set. `pendingClose` offers it as kind `duplicate` when `duplicate_of` lists matches and `unpaid` otherwise. It is refused while an outside payout for the invoice is live. The invoices it matched get a line on their timelines. A rejected invoice that gains a live outside payout is reopened, and when that payout fails, `continueHeld` closes it again without asking anyone to pay it.
- `releaseFor` and `reject` only change an escalated invoice that has sent nothing and has no live outside payout, so a release and a close from different processes cannot both succeed.
- Pay again never reaches Airwallex. `Ledger.tryLock` inserts a replacement attempt inside a transaction and always rolls it back, so the lock either refuses it or nothing is left behind. When the lock does not refuse, the timeline says why nothing was sent.
- A look writes a `bank` line when it finds a payment the ledger had in flight now paid or failed.
- Approval terms take the pay-to account from the beneficiary record as it is now, and the policy escalates if that differs from the account on the original transfer. The timeline carries a warning whenever they differ, whatever reason the policy escalates for.
- A reader failure marks the thread unread, which escalates. The next look reads from the email that failed, and keeps the count of those read before it.

## Uploaded emails

- A person uploads an `.eml` file or pastes raw source on the page. There is no CLI for it. `parseEmail` works on bytes with no dependency, never throws on input and refuses with PayOnce's own words: over 2 MiB, an Outlook `.msg`, text that is not raw source (the first line must be a header field), no blank line within 64 KiB of headers, more than 300 fields, 100 MIME parts, multipart nesting deeper than 8, a bad or colliding boundary. Every scan moves forward, no regex can backtrack on a long run, and the 2 MiB worst cases parse in under 200 ms.
- Headers: unfolded, raw UTF-8 decoded, RFC 2047 words decoded in the subject, display names and file names only. From and Reply-To use a strict ASCII grammar: two From fields, several mailboxes, groups, a quoted local part, an address literal or anything outside ASCII give `SENDER_UNREADABLE` or `REPLY_TO_UNREADABLE`, which the sender check flags. The display name is never compared.
- Every text part is read, plain and HTML; a part is dropped only when it is identical to one already read after whitespace and case are collapsed, and a `multipart/alternative` that kept two gets `versions-differ`. Charsets go through `TextDecoder` under WHATWG labels, with four aliases; `utf-7`, `x-user-defined` and labels it refuses mark the part undecodable. Base64 decodes across early padding. Pasted source is UTF-8 for unencoded parts. `multipart/signed` reads its second part as the signature only for pgp and pkcs7 signature types.
- HTML: script and style content is left out of the text, except inside `<svg>` and `<math>`, where it is read as text too. Comments end at `-->` or `--!>` or the end of input, nothing in them opens or closes an element, and their text is kept. Every string in a style block or `style=""` attribute (CSS escapes decoded), style text that is not CSS PayOnce can parse, and every script's text go to `styleText`, "text found inside styles", which the reader reads and the page shows. Font names cost nothing there.
- One fail-closed rule for CSS: anything CSS could make a client show that is not a string PayOnce took out makes the email partial. That is a `content` value with anything but strings, comments, `none`, `normal` or `!important`; `counter()`, `counters()` or `attr()` anywhere; an `@font-face` with `src` (Outlook's blocks with only `font-family` and `panose-1` are fine); `@counter-style`; `unicode-bidi` other than `normal` and `<bdo>`; `@import`, a linked style sheet, or a URL in `url()`, `src()`, `image()` or `image-set()` outside the email (not `cid:`, `data:` or a fragment); and CSS left open. No special case is added beyond this rule.
- PayOnce does not reproduce a mail client's layout. Reordering (flex `order`, bidi in SVG, positioning) and list numbering can make what a person sees differ in order from what the reader gets. That is accepted because no protection depends on rendering: bank details change only through a callback to the number on file, the sender check works on addresses, approvals bind the account read from Airwallex, and findings only add caution.
- `partial` is set by any note in `PARTIAL_NOTES`: text past 32,000 characters, style text past 8,000, a text part sent as an attachment (or `text/calendar` and the like), a forwarded `message/rfc822`, encrypted or opaque-signed mail, more than 16 text parts, an undecodable part, a skipped header line, a line among the email's own headers that is not a field (`header-text`: that line and the lines after it, up to the blank line, are read as text, and those that are fields are read as fields too), a repeated Content-Type, Content-Transfer-Encoding, boundary or charset, an encoded header in a refused charset, a signed section with more than two parts, and the CSS rule above. Notes are codes kept outside the body, so a sender cannot forge one.
- Attachments are listed by name, type and size from the encoded length, and never decoded, stored or opened. Links are never followed and images never loaded.
- Matching (`candidatesFor`) reads the subject, the body and attachment names, never the sender, amount or supplier. Tokens with a digit (up to 5,000, each at most 128 characters), the same without a file extension, and a word followed by a number ("inv #5001") are looked up by `numberOf` keys, so exact is `sameNumberExactly` and near is `sameInvoiceNumber`. Exactly one live candidate is offered first, unless it is an all-digit number next to other digits. Nothing is delivered by itself: a person picks the invoice, or types another, and confirms. The page keeps that pick, the typed number and the name across polls that rebuild the card, drops a pick that is no longer offered instead of moving it to the suggestion, and names the invoice on the button ("Deliver to INV-...").
- `deliverUpload` runs in the invoice's turn. `Ledger.deliverUpload` moves the upload from waiting to delivered, adds the email and makes an open or escalated invoice's next look due, in one transaction. The timeline then says who uploaded and delivered it, the sender and Reply-To check, text nobody read, another invoice it names, an upload with the same Message-ID, and for a closed invoice that the email is on file and does not reopen it. PayOnce's words come first and the subject last.
- Each new email is read on its own and ORed with the stored findings, so findings only ever add caution. The timeline line says what the emails read in that look found ("Read 1 new email: ...") and, when that differs, the invoice's findings so far. The reader has a third finding, `asksNotToPay` (hold, cancel or not pay, sent in error, paid another way), which escalates. An email with `partial` escalates with "part of a supplier email could not be read".
- An invoice with no supplier domain on file (a pay run row without `supplier_domain`, a found payout) flags every sender.
- An invoice with any email on file before its first payment is held for a person (`EMAILS_BEFORE_PAYMENT_REASON`), pay run rows waiting their turn included. A held invoice reads its emails in `continueHeld`, opens no request until they are read (and looks again a minute later), and its `HeldPaymentTerms.evidence.emails` carries the evidence, added only when it has emails, so other held invoices keep their binding.
- `emailEvidence` in approval terms is the findings' summary, the number of emails on file, how many have text PayOnce could not read and how many senders the check flags. It names no address. Every new email changes it, so it voids an open approval. A replacement request opened before the count existed is replaced once, with a timeline line. The approval card and `pnpm approve` show it for a held invoice as for a replacement, and `pendingClose` gives it as `CloseReview.emails`, which the close card and `pnpm close` show.
- `useApproval`, `releaseFor` and the automatic replacement's transaction spend nothing when the invoice's email count differs from the one the look assessed.
- A non-finite amount throws in `toMinor`, and the policy escalates if the cash position is not a number. `readMinor` gives null instead, for amounts that are only recorded or shown.
- The reserve floor is per currency, from `RESERVE_FLOORS`. In a currency not listed every automatic replacement escalates ("no reserve floor is set for this currency"). That check comes last, just before the policy would replace, and with no floor set the cash is not checked, so it never takes the place of a more specific reason. A payment sent outside PayOnce is checked before the cash, so the policy's reason for it does not move with the balance or the floor. `CUR:0` means no floor on purpose. A setting that cannot be parsed makes every floor unreadable (`floorFor` returns NaN), so every automatic replacement escalates as "the cash position could not be read". `obligations.invoice_floor_minor` lets an invoice be stricter than its currency, never looser. Of new invoices only `eur-swift-low-reserve` sets one, and invoices from before `RESERVE_FLOORS` keep the floor they carried. An invoice floor above 0 counts as set when the currency is not listed.
- Before an automatic replacement the policy takes off `committedMinor`: money promised to other invoices in the same wallet that has not left `available` yet. That is attempts being sent with no transfer yet, `approved` approvals not used or expired on invoices that could still pay, and pay-run rows of an approved waiting run or released and not sent. Money with the bank is already out of `available`, and requests waiting on a person are not counted, so one held invoice cannot block replacements elsewhere. `assess` adds it up before it reads the balance, so a payment that gets its transfer in between is counted twice, never missed. The checks made under the currency lock (`replaceUnderLock`, a run row's floor check in `startPayment`, and a run's `cashCheck`) add it up before the read and again after it, and `committedAcross` takes each invoice at the larger of the two, so a payment promised in between is not missed either. The panel's headroom takes off the same lines. For a cross-currency invoice the wallet is the source wallet and a line's amount comes from `lineAmount`. A pay run's USD cash check therefore counts a EUR invoice paid from USD at its quote's USD amount.
- Every replacement request names the floor when it applies, the first one included. `act`, `continueEscalated` and `replaceUnderLock` (when its decision under the lease escalates) all run `withFloorReason`, which calls `floorReason`, the check `decide` makes, on the same `floorFor` and `committedMinor` figures, so the two cannot disagree. When the original failed, no outside payout is live and the policy escalated for another reason first (sent outside PayOnce, two approvers, and the like), a floor reason that also applies (below the floor, unreadable or not set) is added to the reason in the approval terms as "<reason>, and <floor reason>". With no floor set the added part is `NO_FLOOR_CLAUSE`, "no reserve floor is set for this currency", because the other reason already says why a person approves. The decision line keeps the policy's order. `escalate` then writes a standing `floor` warning. It says the approval request names the floor only when a request bound to these terms is open, which is not the case after `awaitApproval` withdrew a request on an old quote. A look that finds the floor no longer applies after such a warning writes a line saying so. That line adds that an approval of a request naming the floor still counts only when such a request or approval is open.
- An approved replacement is checked against the floor again before it is spent. Once the floor applies, an approval of terms without the floor reason is void because the binding changed, and the new request names both. While the floor does not apply, `asRequested` rebuilds the terms with only the floor changed (below it, unreadable, not set). A request or approval that has not expired and whose binding matches one of them still counts, so a refund that lifts cash above the floor neither voids an approval nor reopens a partly signed request. A request opened because the approval was void for another reason, or because the payment now needs more approvers, gives the terms as they are now, without the floor. An approval of a request that named the floor is spent however far below the floor cash has fallen since, as in `eur-swift-low-reserve`. The terms carry no shortfall figure, because one would void approvals on every balance move. For a cross-currency invoice the rebuilt terms keep the open request's quote, because `rateFor` offers that quote while the request is open, and the binding can still match. The floor figures are in the source wallet at the quote's amount.
- The cost line on the timeline appears when the replacement pays a fee or something is committed elsewhere, and names the committed amount. The policy's floor reason is unchanged, so no approval is voided by wording.
- A single incident's original, and an original released after a hold, are not checked against the floor. A pay run's rows are, at the check, under the lock at release, and under the lock when each is sent.
- Every payment PayOnce creates holds the lease of the wallet it leaves (`withCurrencyLock` on `debitCurrency`, the source currency for a cross-currency invoice) from its last Airwallex read through creating and recording the transfer: an original from `startPayment`, an automatic replacement (`replaceUnderLock`), an approved replacement (`continueEscalated`, which takes it before it spends the approval), a held invoice's original paid on an approval, and a retry of a pending attempt, the last try of a lapsed quote included. `openAttempt` refuses a lease in any other currency. The lease is a `currency_locks` row taken by a conditional upsert under `BEGIN IMMEDIATE`, so the CLI and the server take turns. It lasts 60 seconds, is renewed every 20 while held, and runs out by itself after a crash. Waiters get it in the order they asked (`currency_lock_waiters`), so a run sending its rows back to back cannot starve a payment that started waiting meanwhile. A payment waits up to 45 seconds behind the payments ahead of it, then fails with `CurrencyBusyError` having sent and spent nothing, and the next look comes a minute later (`resumeIncident` plans it, or `startPayment` itself when the scripted run called it). It is not re-entrant. `openAttempt`, `useApproval`, `releaseFor` and `Ledger.releaseRun` check inside their transaction that the lease row still names the holder and has not expired, and throw `LeaseLostError` if not, so a holder whose lease ran out opens nothing. Payouts sent outside PayOnce take no lease, so one created in the window between a balance read and the attempt is the one case the lock cannot see.
- An automatic replacement takes the lease, ties unseen payouts, checks the record still holds the account, reads the balance again, and runs `decide` again, with the fresh balance and the committed money as it is now, in the transaction that opens the attempt. Anything but replace escalates with that reason.
- Fees are stored on attempts and outside payouts from the transfer's `fee_amount` and `fee_currency`, and are 0 when `fee_paid_by` is `BENEFICIARY`. Decisions still read the fee from the transfer they just fetched, never from the ledger. The panel books a transfer to the wallet it took money from, which for a payout paid from another currency is its `source_currency` with its `source_amount`, and a fee to its own `fee_currency`. No figure adds two currencies together.
- The cash panel caches balances for 30 seconds. The policy never uses that cache: `assess` reads the balance fresh on every look.
- An invoice with a `sourceCurrency` other than its `currency` (`crossCurrency`) is paid by one transfer per attempt that converts on a quote: `source_currency`, `transfer_currency` and `quote_id`. The quote buys exactly the invoice amount. There is no separate conversion.
- Every cross-currency payment goes out on a quote a person approved. `startPayment` holds the original before paying (reason "it is paid from USD, so a person approves the exchange rate before PayOnce pays it", after the duplicate and outside-payout reasons). `decide` escalates a replacement after the cash, outside-origin and two-approver checks and before the no-floor check. `openAttempt` refuses a cross-currency attempt unless the approval it is opened on carries a quote, and `sendAttempt` refuses an attempt with no `quoteId` before calling Airwallex.
- The quote is `terms.fx` and is in the binding. It is added only on a cross-currency payment, by a conditional spread right after `accountKey`, so every other payment's terms, and every existing binding, are unchanged. `changedFields` names a change as "exchange rate".
- One quote rule: a new approval request never opens on a quote an earlier request showed. While a request is `requested` or `approved` and not expired, `rateFor` builds the terms on its quote, so the binding holds still across looks. Otherwise it offers the invoice's last quote (`obligations.last_quote`) when the latest request did not show it and it still has more than 22 minutes left (`2 * APPROVED_USE_WITHIN_MS + QUOTE_MARGIN_MS`), so a request opened on it stays open at least 10 minutes. Only when it cannot does it take a fresh quote, which becomes the last quote. A look that opens no request, for example because nobody on the list can approve the payment, takes no new quote while the last one holds. When a new request is needed and the terms carry an open request's quote (other evidence changed), `awaitApproval` withdraws the open one and returns now, and the next look takes a fresh quote. A rate line (kind `payment`) is written only when a request opens on a quote, with the last request's rate when it differs. The waiting line for a payment nobody can approve names no rate, only roughly what the payment takes from the wallet.
- A cross-currency request expires at `min(opened + APPROVAL_TTL_MINUTES, quote end - APPROVED_USE_WITHIN_MS - QUOTE_MARGIN_MS)`, with a 2 minute margin. The quote end is the earlier of `valid_to_at` and arrival plus the quote's validity, so a clock that differs from Airwallex's cannot stretch it. With the approved use window this ends any approval at least 2 minutes before its quote. A short TTL, such as 2 minutes for the demo, still opens a request. `FX_QUOTE_VALIDITY` takes `MIN_30` or longer, and a quote that holds less than 12 minutes is refused.
- Approval limits, `TWO_APPROVERS_ABOVE`, `eligibleApprovers`, `signoffsNeeded` (in `continueHeld` too) and `signoffProblem` use `paymentAmount(terms)`: the quote's sell amount in the sell currency for a cross-currency payment, the invoice amount otherwise. `decide` uses `incident.sourceAmountMinor` for the cash check and the two-approver check. The fee stays out of the limit.
- The attempt keeps `quote_id`, `quote_valid_to` and the approval it was opened on (`approval_id`), all written before the Airwallex call by `openAttempt`, inside `useApproval` or `releaseFor`, from the approval's own terms. Every attempt opened on an approval keeps its `approval_id`, including a same-currency one. A retry sends the same request id and quote, never a new one, under the source wallet's lease. Until `quote_valid_to` plus the transfer method's bank deadline, a 4xx on a retry (`sendAttempt(..., "retry")`) never fails a cross-currency attempt: it stays pending and holds the lock, and the look runs again a minute later. The first send's 4xx still fails it as before. After that time the look makes one last try under the same request id (`"lapsed"`). `duplicate_request_id` records the transfer it names. A quote refusal (`quote_expired` or `quote_id_invalid`, the codes Airwallex documents; the sandbox has not shown its own) fails the attempt if `findTransferByRequestId` also comes back empty, because Airwallex checks the request id before the quote, and the timeline says why. Any other error on the last try, a 429 or 401 included, or a listing that throws, leaves the attempt pending: the look takes the refused path only when the ledger shows the attempt failed, and otherwise throws and is retried a minute later. `failAttempt` changes only an attempt that is still pending with no transfer. A held original then goes back to a person through the refused-original path, and a replacement through the policy, each for a new approval on a new quote.
- `checkRate` compares the transfer with the `fx` of the approval the attempt was opened on (`Ledger.approvalOf`: by `attempts.approval_id`, or the latest approval for an attempt without one), through `rateMismatch`: `currency_pair`, `rate`, and the source amount and currency `debitOf` reads, never inverted, and a transfer with no `conversion` counts as a mismatch. The retry's account check and the panel's `lineAmount` read the approval the same way. It runs wherever an attempt first gains a transfer: in `send`, after a retry, and when found by `request_id`. A mismatch is recorded on the attempt (`rate_mismatch`) and escalates with a warning. The look reads the obligation again after syncing its attempts, so an invoice escalated that way takes the escalated path in the same look. Only a person then closes the invoice, whether the attempt was the original or a replacement: `settle` refuses unless `closeIncident` calls it, and `pendingClose` gives the mismatch as the close card's reason. An attempt with a mismatch that then failed does not block the automatic close once another payment is paid.
- The cash check reads the source wallet. `assess` takes a quote for a cross-currency invoice only once its original has failed, and uses the original's fee if `fee_currency` is the source currency, else NaN, so the policy reads the cash as unreadable. The cost line is in the source currency.
- `debitCurrency` is the source currency, so the reserve floor, `committedMinor` and the cash panel use the source wallet. `lineAmount` gives a line's amount: what `debitOf` read from the transfer (`attempts.amount_minor`), else for a cross-currency payment the sell amount of the quote the attempt was sent with or the open request is on, else the last quote's (`obligations.last_quote`), estimated, else 0, estimated. A line whose amount comes from a quote has `fromQuote`, and the page notes it.
- A failed cross-currency original is replaced from the same source wallet on a fresh quote. Paying from the currency Airwallex refunds a failed converting transfer in is not built.
- Pay runs do not use FX: each row pays in its own currency from that currency's wallet. A file with a `source_currency`, `paid_from`, `pay_from` or `sell_currency` column is refused, `Ledger.releaseRun` writes `source_currency` as null, and `startPayment` refuses a run row whose invoice would convert. A run's approval limits go through `runAmount(terms)`, the largest currency total taken from the run's terms, so `checkSigner`, `eligibleApprovers` and `signoffProblem` get the same branded `PaymentAmount` for a run as for an invoice.
- On resume, a paid replacement closes the incident unless an outside payout for the invoice is live or the payment that paid it went out at an unapproved rate. A paid original goes to the policy, which closes it only if no supplier email reports the payment missing.
- An escalated invoice is closed by a person through `closeIncident`, never by a resume, once the bank reports it paid once: by PayOnce's original or replacement, or by an outside payout after every payment PayOnce sent failed. `pendingClose` says when that applies. Closing sends nothing and is not bound to terms.
- A settled invoice that is still paid once is left alone on resume.

## Pay runs

- A run file names each row's beneficiary by id, with the supplier, the amount (major units, a dot, at most two decimals, parsed as a string so nothing is rounded), a two-decimal currency, and optionally the method, `sandbox_outcome` and `supplier_domain` (a plain ASCII domain, only A to Z lowercased; anything else is a row problem). Nothing else is read from a file: no bank details and no phone number. An unknown or repeated column, a missing required column, an unclosed quote, no rows, more than 50 rows or more than 40,000 characters refuses the file and stores nothing. A problem in the header names the header's line, and an unclosed quote names the line it opened on. A problem with the file as a whole (no name, empty, no rows, too many rows or characters) has no line.
- `checkRows` skips a row, with every reason found, for a cell problem; an invoice number in the ledger exactly (`alreadyInLedger`), or by `sameNumberExactly` for the same supplier whatever the amount; a number on an earlier row (exactly, or by `sameNumberExactly` for the same beneficiary); an earlier row `sameBillAndNumber` matches; a beneficiary Airwallex does not have or with no bank details; a supplier cell that is not the record's `account_name` once case, spacing and punctuation are dropped; a currency other than the record's `account_currency`; a method the record does not take, or none when it takes both; or bank details other than the ones `lastPaidTransfer` went to with no `verifiedBankChange` for the record. The skip message for a changed account says to check with the supplier, pay outside PayOnce, or restore the old details, because no callback can be recorded outside an incident.
- `lastPaidTransfer` is the latest paid attempt on an `origin = 'payonce'` invoice to the beneficiary that is not `misdirected`. A row to a beneficiary with none is a new payee. A row whose account a callback verified carries `bankChange`.
- A row that `likelyDuplicates` matches against the ledger is a pay row with `heldFor` listing the matches. It counts in the totals, is released with the run, and `startPayment` holds it when it comes to send it. `likelyDuplicates` itself is unchanged.
- The cash check runs per currency over the pay rows: one `getBalances` read, less `committedMinor(currency, { runId })`, less the rows and their fees (`latestFee` by method, 0 and "not known" when none is recorded). When that leaves less than the floor, every row in the currency is skipped with the shortfall in the reason. A skipped row goes through `skipRow`, which clears `heldFor`, `newPayee` and `bankChangeId`, because those only matter on a row that pays. A currency with no floor set does not block, and the terms carry `reserveFloorMinor: null`. An unreadable `RESERVE_FLOORS`, or no balance in the currency, skips the currency's rows.
- Only one run waits at a time (`one_waiting_run`), and a file whose run is not cancelled cannot be uploaded again (`one_live_run_per_file`). Both are checked before Airwallex is read and again inside `createRun`'s transaction, which also skips a row whose number reached the ledger meanwhile. `POST /api/incidents` refuses a number on the waiting run's pay rows.
- `RunTerms` hold every pay row in file order (line, invoice, amount, currency, beneficiary, method, `payTo`, `accountKey`, `heldFor`, `bankChange`, and `supplierDomain` on a row that gives one) and a total per currency with its floor. Skipped rows, new-payee flags, sandbox outcomes and how many approvers are needed are not in the terms.
- `runRule`: two approvers when a row pays a new payee, when a row pays a callback-verified account, when a row's `supplier_domain` has a caution, or when any currency's total is above `TWO_APPROVERS_ABOVE`. `domainChecks` gives a caution when the domain differs from the latest invoice to the beneficiary with one, when the run gives the same beneficiary another domain, or when it is the first domain for a beneficiary PayOnce has paid once. A first domain for a beneficiary never paid gets a note only. The approval card and `pnpm payrun show` and `approve` show each row's domain with its caution or note. Limits are checked against the largest currency total (`runAmount`, which `largestTotal` shows), because limits are bare numbers. `runBarred`: the uploader, and the callback recorders of every `bankChange` row. Approving follows `approvePayment`: the request on screen, `checkSigner`, `signOffRun`, the binding.
- A run request expires after `APPROVAL_TTL_MINUTES` and is not renewed by itself. `recheckRun` ("Check again", `pnpm payrun check`) runs every check, then in one transaction (`setRunRows` running `settleRunRequest`) rewrites the rows and keeps a request, requested or approved, with the same binding that has not expired. Otherwise it opens a new one, saying when signoffs no longer count. With nothing left to pay, or too few eligible approvers, it opens none and says why. It is refused while the run's latest request is approved and has not expired, because the release pays those rows.
- `releaseRun` runs in the run's turn (`runKey`). It checks every row again. If the approval expired, the binding differs, or `signoffProblem` finds a problem, the approval is voided and the rows rewritten in one transaction, which changes nothing if another process has released the run or opened a newer request since, and the run waits for a person to check it again; no request opens by itself. Otherwise it takes the lease of every currency the run pays, in code order, and runs the cash check again on a fresh balance. A shortfall voids the approval and the run waits for a person. Else `Ledger.releaseRun` spends the approval and marks the run released, writes each pay row as an `open` invoice (supplier = the record's account name, `started_by` = the uploader, `run_row_id`, `look_at` now, the approved `supplierDomain` or none, no phone) with its first chained line naming the run, row, file hash, approvers, request and binding, and sets each released row's `account_key` and `pay_to` from the approved terms, all in one transaction that first checks every lease. A check that rewrote the rows meanwhile cannot change the account a row pays. A plain INSERT that fails on a taken number rolls back to a savepoint and drops that row. Timeline lines on the run come after the commit, except the release line, written in the transaction.
- After the commit the release wakes each released invoice in file order with the run's turn (`wake(invoiceId, true)`) and waits for it before the next, so a run never sends a burst. The approve route and the watcher start a release without awaiting it. `pnpm payrun approve` only signs, and the server's watcher releases the run on its next check; a run approved while no server runs waits, and is void once its use window has passed.
- A released row's first look with the run's turn calls `startFirst`, which sends the original through `startPayment` with the row's `accountKey`. Under the lease it reads the balance, ties unseen payouts and reads the record last. Then, in one transaction, it checks that the invoice is still open with no attempt, the record's account (a missing beneficiary or other details holds the row), `likelyDuplicates`, `sameNumberForSupplier`, a live outside payout and the floor (the committed money without this invoice, so the run's other unsent rows count), and opens the attempt. A row that fails any of these is held, with `CASH_HOLD_REASON` for the floor.
- Only the release, or the server's watcher once the run's key is not busy, sends a run row, because only they wake it with the run's turn. Any other look at an unsent row (the resume and bank-change routes, a webhook, the sweep, `pnpm recover`'s watcher) notes that it waits for its turn and makes its next look due, so the server's watcher gives it one. `pnpm recover` refuses a run invoice that has not sent.
- A retry of a pending original on a run invoice checks the account of a used `pay` approval first, then the row's `accountKey`.
- `continueHeld` on a run invoice: a missing beneficiary, or a record that no longer holds the row's account and has no verified callback, withdraws any request and waits for a person to close it. Otherwise two approvers are needed when PayOnce has never paid the beneficiary or last paid it another account (`payeeRule`), as for the run itself.
- `cancelRun` works only on a waiting run. It voids the open request and drops the pay rows, so their numbers are free again. Anyone with a name and a note may cancel.
- The sandbox bank reads a run row's `sandbox_outcome` from the ledger through `runRowOf`, so it survives a restart. The engine never reads it, and it is not in the terms.

## Ledger

- `src/ledger.ts` uses `node:sqlite`, which ships with Node 24, so there is no database dependency or server.
- The file is `payonce.db` in the working directory and is git-ignored. `pnpm reset` renames it with a timestamp, which is also ignored, so the next run starts empty. The rename fails with `EBUSY` while `pnpm ui` has the file open. Transfers already sent in the sandbox stay there.
- The duplicate lock is the partial unique index `one_live_attempt_per_invoice` on `attempts(invoice_id) WHERE state <> 'failed'`. A violation has `errcode` 2067 and is rethrown as `DuplicatePaymentError`.
- `paidOnce` is true when one attempt is paid and every other attempt has failed. `settle` closes an obligation only then, and not while an attempt that has not failed has a `rate_mismatch`, unless a person closes it. It also voids any approval still open.
- `obligations.escalation_reason` holds the policy's last reason for sending the invoice to a person.
- Approvals live in the `approvals` table with states `requested`, `approved`, `used` and `void`. Each approver's approval is a row in `signoffs` with the binding they approved. `signOff` adds one and marks the request approved once it has `needed` of them, in one transaction, so the server and the CLI cannot both count the last one. `approvals.approver` joins the names for display. The binding is the hash of the terms JSON, so build terms only through `termsFor` to keep the key order stable.
- A new request voids any earlier request or approval for the invoice that is still open. An approval is marked `used` before the payment is tried, so it covers one attempt.
- An approval request is created only when the original has failed, or for a held invoice. `requestApproval` opens one only while the invoice is escalated, in one transaction, so it cannot land on an invoice another process has just closed. `pendingApproval` shows none on an invoice that is not escalated. The duplicate lock still applies to an approved payment.
- Supplier emails and the reader's findings are stored per invoice in `emails` and `email_findings`. The findings record how many emails they cover (`emailsRead`). Only new emails are read, one at a time, and the findings are ORed and reused, so a reader that words its summary differently on a second call cannot void an approval. An uploaded email's row also has `inbox_id`, `reply_to`, `style_text`, `attachments`, `notes` (codes) and `partial`; a fixture email's are empty.
- `inbox` holds uploads: who and when, `source` (`file` or `paste`), the file name, `raw_sha256`, `raw_bytes`, `content_hash` (SHA-256 of the bytes with CRLF as LF), Message-ID, sender, display name, From as written, Reply-To, date as written, subject, body, style text, attachments, notes and `partial`. The raw bytes are not kept. `state` is `waiting`, `delivered` (with `invoice_id`, `delivered_by`, `delivered_at`) or `dismissed` (with `dismissed_by`, `dismiss_note`), which is final. Each change is a conditional update on `state = 'waiting'`. The unique index `one_upload_per_email` on `content_hash` refuses a second upload of the same email (`DuplicateUploadError`), and `sameMessageId` lists uploads that share a Message-ID and say something different.
- `webhook_events` holds the id of every webhook event taken, so a redelivered event is ignored. `attemptOf` finds the attempt a transfer belongs to by `request_id` or transfer id.
- Approval evidence includes the email summary, so new emails that change the findings void an approval.
- `events` holds the timeline. A line with a `topic` says how things stand: the decision, what the invoice is waiting on, an approval, the cost of a replacement, or a bank-details mismatch. `note` skips one when the timeline's last line on that topic says the same and nothing has happened since, so checking an invoice again when nothing has changed adds nothing. A line with no topic records an event and is skipped only when it repeats the line before it.
- On an escalated invoice the decision line says when the policy would now replace or close and why it does not.
- Each timeline line has `prev_hash`, the hash of the invoice's line before it (64 zeros for the first), and `hash`, SHA-256 of `prev_hash` followed by `canonicalEvent`: the JSON `{at, invoice_id, kind, message, topic}` with the keys in that order. `meta.events_head` is the running hash, `sha256(events_head + hash)` for each line in id order, so lines removed from the end of a timeline, or a whole invoice's lines, are caught.
- `addEvent` reads the invoice's last hash, inserts the line and updates the running hash in one `BEGIN IMMEDIATE` transaction, because the CLI and the server write the same file and a step on one invoice writes on others' timelines. `note` runs its dedupe before calling it, outside the lock. The body is the private `appendEvent`, which `releaseRun` also calls inside its own transaction.
- `Ledger.transaction(fn)` runs `fn` in one `BEGIN IMMEDIATE` and throws if a transaction is already open, since `node:sqlite` cannot nest them. Nothing that opens its own transaction (`addEvent`, `addRunEvent`, `requestApproval`, `requestRunApproval`, `signOff`, `releaseFor`, `useApproval`, `tryLock`, `adoptPayout`), and no `note`, runs inside one: timeline lines are written after the commit. `openAttempt` and `addRunApproval` run only inside one.
- `addEvent` hashes the line as it will read back: `storable` turns half of a surrogate pair, such as an emoji cut by `.slice`, into U+FFFD, as SQLite's UTF-8 would.
- The first open with the chain hashes the lines already there in id order and sets `meta.chain_started_at` and `meta.chain_backfilled_through`, the last line it hashed. A ledger whose chain has started (`chainStarted`: any of the three meta keys, or a line with a hash) is never hashed again. A line with no hash, written by older code, is reported as written outside the chain, and the next line chains from the last line with a hash. There is no way to take such a line into the chain, because the same step would launder a forged one.
- `pnpm run audit` opens the file with `new Ledger(path, true)`, read-only, which skips the schema, the upgrade and the backfill. It refuses a missing file and a ledger whose chain has not started. `pnpm run audit run <RUN>` on a file from before pay runs, which has no `runs` table (`hasRunTable`), says the ledger has no pay runs.
- Pay run timelines are chained the same way, apart from the invoices': `run_events.prev_hash` and `hash` over `canonicalRunEvent`, the JSON `{at, run_id, kind, message, topic}` with `run_id` as a number, one chain per run, and a running hash of their own in `meta.run_events_head`. `addRunEvent` writes the line and the running hash in one transaction, and `Ledger.releaseRun` writes its release line inside its own. The first open with this code hashes the run lines already there and sets `meta.run_chain_started_at` and `meta.run_chain_backfilled_through`. `pnpm run audit` checks run chains after the invoices', `pnpm run audit run <RUN>` checks or exports one, and a ledger whose run chain has not started is reported, not hashed.
- `auditSnapshot` reads what a check needs in one transaction. The check compares each line with the stored hash of the line before it and with its own content, so an edit shows up once. When the running hash does not match but every timeline verifies, it cannot say which invoice lost lines.
- `meta` holds `started_at`, when the ledger was first opened. The sweep lists transfers from then, so payouts from an earlier ledger are not taken for outside ones.
- `obligations.supplier_phone` is the phone number on the supplier record, set from the scenario. Only `usd-local-bank-change` has one, so only it offers a callback. Found payouts have none.
- `bank_changes` holds each callback: who called, the number, when, who they spoke to, what was confirmed, the old record and the typed fields, and `state` `pending`, `applied` or `failed`. The row is written before the Airwallex update.
- `obligations.state` is `open`, `escalated`, `settled` or `rejected` (closed without paying). The watcher, `dueLooks` and the server's start-up pick-up skip `settled` and `rejected` invoices.
- `obligations.duplicate_of` is a JSON list of the invoices a held invoice looked like, and `rejected_by` is who closed it without paying.
- `obligations.origin` is `payonce` or `outside`. `payout_reference` keeps a found payout's reference when it could not be the invoice number, and `obligationForReference` matches either.
- `obligations.invoice_floor_minor` is an invoice's own floor, 0 for none, in minor units of the wallet the invoice is paid from (`debitCurrency`, the source currency), because `floorFor` and the panel compare it with that wallet. `reserve_floor_minor` is the floor each invoice carried before `RESERVE_FLOORS`. The open that adds `invoice_floor_minor` copies every `reserve_floor_minor` that is not 0 into it, and only that open, so no invoice from before is held to a looser floor than it was. After that `reserve_floor_minor` is not read or written.
- `attempts.fee_minor` and `fee_currency` hold the fee as last read from the transfer. `record` keeps the stored fee when a read has none. `recordFee` writes only these columns, and only where `fee_minor` is null, so it can run outside an invoice's turn. `failedWithoutFee` lists failed transfers, PayOnce's and outside payouts, with no fee recorded, leaving out those tried too recently and putting the least recently tried first. `fee_tried_at` on both tables is when `feeTried` last marked a transfer before its fee was read. `latestFee` is the latest fee recorded in a currency by a transfer method, which the panel uses to estimate the fee of a payment not sent yet.
- `outside_payouts.amount_minor`, `currency`, `fee_minor` and `fee_currency` are written when a payout is tied and on every look that reads it. `attempts.amount_minor` and `currency` are written by `record` and `adoptPayout`. On both tables the amount and currency are what the transfer took from the wallet before the fee (`debitOf`): the source amount and currency when it was paid from another currency, and the transfer amount otherwise. A row from before has none. For PayOnce's own attempt from the invoice's own currency the panel then takes the invoice amount, which is exact, and for a cross-currency one the quote amount `lineAmount` gives. A found invoice's original or an outside payout from before gets the same amount marked estimated, until a look reads the transfer and stores what it took.
- `obligations.source_currency` is the wallet the invoice is paid from. Null means its own `currency`, and `toObligation` turns null into `currency`, so code never sees it. `NewObligation.sourceCurrency` is optional. The sweep sets it from a found payout's `source_currency`.
- `obligations.last_quote` is the latest quote `rateFor` took for the invoice, as `LastQuote` JSON with when it ends by PayOnce's clock.
- `attempts.quote_id` and `quote_valid_to` hold the quote a cross-currency attempt is sent with. `approval_id` is the approval any attempt was opened on, null for one no approval released. `attempts.rate_mismatch` says why its transfer did not match that quote.
- Approvals need no FX column: the quote lives in `approvals.terms`, and `expires_at` carries the earlier expiry.
- After upgrading, restart every PayOnce process. An older process sharing the file builds terms without `fx` and would void the new requests, and would retry a pending cross-currency attempt without its quote.
- `adoptPayout` writes a found payout's invoice and attempt in one transaction. Its INSERT is plain, so an invoice written by another process in between makes it fail instead of gaining a second original.
- `outside_payouts` ties outside payouts to invoices, with the bank's short reference and the last state a look read. `settle(invoiceId, true)` also accepts an invoice whose attempts all failed and whose outside payout is paid. Only `closeIncident` passes it.
- Columns added after the first version are listed in `ADDED_COLUMNS` and added when the database is opened, under the write lock, so two processes opening an older file at once do not both add one.
- `obligations.run_row_id` is the run row an invoice was released from (`Obligation.runRowId`). `attempts.misdirected` is 1 for a transfer `send` found went to other details than it was approved or decided for, so it never counts as the account PayOnce last paid.
- An invoice number is the primary key of `obligations`, and a second one fails with `errcode` 1555 (`SQLITE_CONSTRAINT_PRIMARYKEY`), not 2067.
- Pay runs are in tables of their own, created by `SCHEMA` on open. `runs` (state `waiting`, `released` or `cancelled`, the file's name, hash and header, the uploader, and the last check's cash as JSON), with the partial unique indexes `one_waiting_run` and `one_live_run_per_file`. `run_rows` (the cells as read, what the last check made of them, `action` `pay` or `skip`, `reasons`, `held_for`, `new_payee`, `bank_change_id`, `payee`, `pay_to`, `account_key`, and `state` `waiting`, `released` or `dropped` with a `note`). `run_approvals` and `run_signoffs` mirror `approvals` and `signoffs`, because those reference `obligations`, which a run has none of until it is released; the run methods are copies of the invoice ones, not generic over the tables. `run_events` is the run's timeline, hash-chained like `events`.
- `payRunRows` reads, as query predicates, the pay rows of a waiting run whose latest request is `approved` and not expired, and the released invoices still `open` with no attempt. A row drops out in the transaction that opens its attempt.
- `currency_locks` holds the lease per currency: `holder` and `expires_at`. `takeCurrencyLock`, under `BEGIN IMMEDIATE`, drops waiters that have not asked for 10 seconds, and takes the lock (inserting it, or taking it over once expired) only when no other waiter is first in line. Otherwise it adds the holder to `currency_lock_waiters` or refreshes its `seen_at`, keeping its place. `leaveCurrencyQueue` removes a holder that gave up. `withCurrencyLock` calls it whenever it stops waiting with an error: after 45 seconds, or when `takeCurrencyLock` throws on a busy ledger. A waiter that stopped then never holds up the queue for `WAITER_GONE_MS`. `renewCurrencyLock` and `releaseCurrencyLock` act only for the holder.

## Email reader

- `READER_API_KEY` in `.env` turns the model reader on. `READER_BASE_URL` defaults to Gemini's OpenAI-compatible endpoint. `READER_MODEL` is a comma-separated list tried in order and defaults to `gemini-3.5-flash,gemini-3.1-flash-lite`, both on Google's free tier.
- `pnpm dev` loads no env file, so it always uses the keyword placeholder.
- The request is one chat completion per email with `reasoning_effort: "low"` and a `json_schema` response format. The model answers three booleans (`claimsNonReceipt`, `asksForNewBankDetails`, `asksNotToPay`) and no text. `toAnswers` checks the answer again, so a service that ignores the schema still cannot return anything else. Reply-To, the text found inside styles, attachment names and PayOnce's notes go in tags of their own, and the prompt says nothing in the sender's tags comes from PayOnce.
- `summarise` in `src/emails.ts` writes the summary from the findings for both readers, so no wording from an email or a model reaches the approval card or the approval binding.
- `ModelReader` also runs the keyword check and ORs the findings. Every finding only makes the policy more cautious, so a tricked model cannot remove a finding the keywords make. It can still hide one the keywords miss. The keyword check reads the subject, body, style text and attachment names after `keywordText`: blank-looking letters become spaces, default-ignorable characters go, NFKC, straight apostrophes and one space for every whitespace run, so wrapped lines and curly apostrophes match.
- Each model gets one request with an 8 second timeout. If it fails, the next model is asked, and the console gets a `reader` line saying why. A refused key (401 or 403) stops at once. If every model fails, `read` throws, the engine marks the thread unread, and the policy escalates.
- Findings carry `readBy`, the model that answered, and the page shows it.
- The API key is cut out of any error text before it reaches the timeline.
- Google may use free-tier content to improve its products. The fixtures are synthetic. The page's "Supplier email" card says so next to the upload, and names the reader.

Found by running it on 2026-10-06:

- The key goes in `Authorization: Bearer`. A strict `json_schema` response format and `reasoning_effort: "low"` are accepted, and a good answer has `finish_reason` `stop`.
- `gemini-3.8-flash`, the model in Google's examples, answered 503 "high demand" on 5 of 8 calls. In about 35 reader calls, `gemini-3.5-flash` and `gemini-3.1-flash-lite` between them always returned an answer, usually in 1.6 to 5.8 seconds. `gemini-3.5-flash-lite` took 8 to 18 seconds. The 2.5 models return 404 for new users.
- `gemini-3.5-flash` returns 429 after about six calls in a minute and answers again a minute later. The second model answered each time. Daily limits are shown only in AI Studio.
- Both default models gave the expected findings on the two fixtures, a reworded email the keywords miss, a thank-you email and an email with an injected instruction to answer false. The one difference: `gemini-3.5-flash` once read the injection email as a non-receipt claim.
- One "new account" incident on the page took 21 seconds, against 8 with the keyword reader. Its first read took 12 seconds, before the timeout was cut from 15 seconds to 8.

## Web server

- It binds to loopback and has no login. `guard` checks the Host header and, for writes, the Origin header and a JSON content type.
- Routes: `GET /api/options`, `GET /api/cash`, `GET /api/incidents`, `GET /api/incidents/:id`, `GET /api/incidents/:id/audit` (JSON, or CSV with `?format=csv`), `POST /api/incidents` (takes `bankOutcome`, `emails`, `scenario`, `startedBy` and an optional `invoiceId`, refused with 409 when it is already in the ledger), `POST /api/incidents/:id/approve` (needs `approver` and `approvalId`), `POST /api/incidents/:id/close` (needs `closedBy` and `finding`), `POST /api/incidents/:id/resume`, `POST /api/incidents/:id/pay-again`, `GET /api/incidents/:id/bank-details`, `POST /api/incidents/:id/bank-change` (takes `calledBy`, `numberCalled`, `calledAt`, `spokeTo`, `confirmed` and `details`), `GET /api/runs`, `POST /api/runs` (takes `fileName`, `csv` and `uploadedBy`; 201 `{ runId }`, 400 with `problems` for a file it cannot read, 409 with `runId` while a run waits or for the same file, 422 with `rows` when every row is skipped, 502 when Airwallex could not be read), `GET /api/runs/:id`, `GET /api/runs/:id/audit` (JSON, or CSV with `?format=csv`), `POST /api/runs/:id/approve` (needs `approver` and `approvalId`), `POST /api/runs/:id/check` and `POST /api/runs/:id/cancel` (needs `cancelledBy` and `note`). `HttpError` takes an `extra` object merged into the error JSON.
- Inbox routes: `POST /api/inbox` (takes `uploadedBy`, `source` `file` or `paste`, `fileName` and `eml`, the bytes in strict base64; `readJson` is given a 3 MB limit for this route only; 201 `{ id, candidates, suggested }`, 400 an email PayOnce cannot read, 413 over 2 MB, 409 `{ id, state, invoiceId }` for one already uploaded), `GET /api/inbox` (waiting uploads, then the latest 50 others, with no matching), `GET /api/inbox/:id` (the upload, notes in words, candidates, `sameMessageId`), `POST /api/inbox/:id/deliver` (`invoiceId`, `deliveredBy`; in the invoice's turn, then a wake for an open or escalated invoice) and `POST /api/inbox/:id/dismiss` (`dismissedBy`, `note`). An incident's emails carry `uploadId`, `uploadedBy`, `replyTo`, `styleText`, `attachments`, `notes` in words and `partial`. `GET /api/options` adds `maxEmailBytes`, `reader` and `readerIsModel`. Static files are served with a Content-Security-Policy and every response with `nosniff`.
- The page has a "Supplier email" card (file or paste, a name, the free-tier notice), an "Inbox" list and `#inbox/N`, which shows the upload, a match card (candidates, another invoice, a name) and a dismiss card. Email text only ever reaches text nodes.
- The CSV travels as a string inside JSON, so the guard covers an upload and nothing parses multipart. The upload waits for the checks, a few Airwallex GETs. A run's id is `^[1-9][0-9]{0,9}$`. Every step on a run (approve, check, cancel, release) runs in `runKey(id)`'s turn. An approval that completes the request starts the release in that key's turn without awaiting it.
- A run's detail has the run, `status` (`waiting-approval`, `approved`, `expired`, `needs-check`, `released`, `cancelled`), `counts`, the rows with each released row's invoice (state, attempts, `busy`, `watching`), the last check's cash, the approval in an incident's shape plus `largest`, the events, `busy` (the run's key or any of its invoices) and `watching`. An incident's detail has `run: { id, line }` or null, and the list carries `runId`. `GET /api/options` adds `runColumns`, `sandboxOutcomes`, `maxRunRows` and `maxRunFileChars`.
- The page routes `#run/7` to a run. The sidebar has a "Pay run" form (file input, read with `file.text()`, and the stored name, kept in step with the incident form's name) and a "Pay runs" list. The run view has a rows card, the run's timeline with its audit line and downloads, the approval card (the approver picker checks limits against the largest total), the cash card from the last check, a cancel card while it waits and "Check again" in the header. An incident from a run links back to it. The "New payee" and callback tags show only on a row that pays.
- An incident's detail carries `audit`: the number of lines, and `problem`, the first break in the chain or a running hash that is missing or does not match, null when there is none. The page shows it under the timeline with links to the export. It carries `review` when a person can close it, and the page shows the close card from that. `busy` is true while the agent or the sandbox bank is working on it, and `watching` while a payment is with the bank, including an outside payout tied to it. The page polls every 1.5 seconds while either is true.
- Approve and close wait for any step already running on the invoice, then run. Resume queues a look.
- `GET /api/cash` answers at once from `BalanceCache` and the ledger. It starts one balance read when the last try, good or failed, is 30 seconds old, so a page that stays open reads the balance at most twice a minute and a closed one reads nothing. The server reads once at start. After each good read it runs `recordMissingFees`, so while failed transfers have no fee one refresh makes up to six reads: the balance and five transfers. Because it answers before the read it starts, the first answer after nobody asked for a while carries a read older than 30 seconds, with `refreshing` true. `refreshing` covers only the balance read, not the `recordMissingFees` run after it, though no new read starts before that run ends. The page says it is reading the balances again and polls every 1.5 seconds until the balance read lands. A failed read keeps the last good one, and the answer carries the error, the read's age and `statesCheckedAt` from the watcher. Headroom is null when the balance was never read, Airwallex has no balance in that currency, or `RESERVE_FLOORS` is unreadable. `payRuns` is `{ built: true }`, and a `pay-run` line carries its `runId`; the page links a row not released yet to its run.
- A currency is listed when it has a floor set, a line in the ledger, an invoice floor or a balance that is not zero. The page shows the cash panel above the incident, one row per currency. A currency is open by default when money in it is promised or waiting on a person, or a headroom is below 0. A person's click is kept in `localStorage` under `payonce.cashOpen`. The panel is redrawn only when the figures change, and the ages are set on their own nodes on every poll.
- The page scrolls to keep the newest timeline line on screen when that line was already visible, and for 15 seconds after an action.
- On start it wakes every invoice that still has a pending or in-flight attempt, and the sandbox bank goes back to paying any replacement still in flight, and an original in flight that was paid on an approval after a hold. It reads that from the approval the attempt was opened on (`approvalOf`), not from the invoice's latest request.
- The watcher sweeps every 30 seconds. A paid, failed, cancelled or overdue webhook for a transfer the ledger does not know asks for a sweep on the next check. One for an outside payout already tied to an invoice wakes that invoice.
- `GET /api/options` lists the default email thread first, so the form opens on the incident that is replaced without a person. It also lists the approvers and the approval policy, and an incident's approval carries its signoffs, `needed`, `expiresAt` and who is barred, so the page can offer only the names that may approve.
- When `terms.fx` is set, the approval card adds what the payment takes from the source wallet, an "Exchange rate" row (the rate as Airwallex quotes the pair, the markup over mid-market, the quote id and when it runs out) and a "Transfer fee" row, and the page compares limits with `fx.sellAmountMinor`. The header says "Paid from USD" when `obligation.sourceCurrency` differs from `currency`.

## Webhooks

- `pnpm ui` starts `WebhookReceiver` on `WEBHOOK_PORT` (4311, loopback). It answers `POST /airwallex/webhooks` and nothing else, so the tunnel exposes no other route. It answers 503 until it has the secret, so Airwallex retries.
- Without `WEBHOOK_URL`, `openTunnel` runs `cloudflared tunnel --no-autoupdate --url http://127.0.0.1:4311` (`CLOUDFLARED` sets the path) and takes the `trycloudflare.com` address from its output. The address changes on every start.
- `subscribe` finds PayOnce's subscription by the `request_id` prefix `payonce-transfers-` and moves it to the new address, or creates it with all nine `payout.transfer.*` events. The secret comes back from Airwallex and is held in memory only.
- `verifySignature`: HMAC-SHA256 hex of the `x-timestamp` header followed by the raw body, keyed with the secret, compared in constant time. A timestamp more than 5 minutes off is refused.
- The receiver takes the transfer from `data`, or from `data.object` when Airwallex nests it there.
- Paid, failed, cancelled and overdue events for PayOnce's own transfers wake the agent. They put a `bank` line on the timeline unless the ledger already shows the payment paid or failed. Other events are only logged.
- With webhooks connected the watcher checks every 15 seconds. Without them it checks every 3, and the CLI every 2. `WEBHOOKS=off` skips the receiver, the tunnel and the subscription.
- `WEBHOOK_API_VERSION` defaults to `2025-06-30`. No response header says which version the account uses.

Found by running it on 2026-10-28:

- A webhook `request_id` is limited to 50 characters.
- The list call returns each subscription's secret. The update call moved PayOnce's subscription to a new tunnel address and kept its id.
- In three incidents, with about ten transfer status changes, Airwallex delivered no event within 12 minutes. The tunnel answered a request from outside, and the subscription listed the right address and events. The watcher caught every change. Delivery status per event is under Settings > Developer > Events in the web app, which needs the account owner's login.
- Checked in the web app later the same day: Airwallex creates an event for every status change (`scheduled`, `processing`, `sent`, `paid`, `failed`), with the transfer directly under `data` and `version` `2025-06-30`, addressed to the subscription's URL. Every event stayed `Queued` with no HTTP status, so none was ever attempted. With a fresh tunnel and the subscription moved to it, "Send test event" and "Re-trigger" in the web app delivered nothing either, while a POST from outside through the tunnel reached the receiver and got its 401. The sandbox records events but does not deliver them to this account.
- The scripted incidents with the watcher on: a replaced payment from start to close in 11 seconds through `pnpm recover`, and about 50 seconds for each escalation on the page while the watcher checked every 60 seconds.
- `winget install Cloudflare.cloudflared` waits on a UAC prompt. The standalone `cloudflared-windows-amd64.exe` from the GitHub release runs without admin rights.

## Sandbox behaviour found by running it

- Credentials are a scoped API key in `.env` (`AWX_CLIENT_ID`, `AWX_API_KEY`). Admin keys are deprecated.
- A new transfer starts `SCHEDULED` and moves to `PROCESSING` on its own within seconds. The simulator returns `500 operation_failed` for a transition requested while it is still `SCHEDULED`, so wait first.
- The simulator sometimes returns `500 operation_failed` after it has applied the transition. `simulateTransfer` reads the transfer after a server error and retries only if the target status was not reached.
- A transfer left in `SENT` was `PAID` about ten minutes later with no simulation call. This happened once.
- `PROCESSING` to `SENT`, `SENT` to `PAID` and `SENT` to `FAILED` (with `failure_type`) all work. A failed transfer reads `FAILED`, then `CANCELLED` a few seconds later. The `failure` object survives the change.
- `failure.details.type` is `INCORRECT_ROUTING` for every simulated failure. Read `failure.code` instead: 91401 system error, 91402 channel timeout, 90701 account closed, 90101 invalid account name or number, 90802 beneficiary bank returned, 91001 recall requested, 91301 duplication return, 99901 unable to apply, 99902 other.
- Creating a transfer takes the amount out of `available_amount` immediately. A failed transfer is refunded a few seconds later.
- A EUR SWIFT transfer of 4,000 carried a fee of 13.91 or 13.92 EUR. When it failed, the 4,000 came back and the fee did not.
- The beneficiary record and a transfer's `beneficiary.bank_details` hold the same object. The transfer keeps the details it was sent with: `POST /api/v1/beneficiaries/{id}/update` changes the record and not the transfer, and setting the old values back makes the two equal again.
- Reusing a `request_id` returns `400 duplicate_request_id` and names the original transfer.
- Run on 2026-10-28: `POST /api/v1/beneficiaries/{id}/update` with the GET record's `beneficiary` (without `fingerprint`), `nickname`, `payer_entity_type` and `transfer_methods` was accepted. Airwallex rewrote `bank_name` from the routing number ("Bank of America" became "Bank of America, NA"), so the read-back compares only the fields that say where money goes. The next transfer to the beneficiary went to the new account.
- The scenarios share one beneficiary per currency, so a bank change on one would reach the others. Each `usd-local-bank-change` run creates a beneficiary of its own, nicknamed `PayOnce demo supplier (bank change)` plus the invoice number.
- LOCAL USD transfers carry no fee in the sandbox.
- Run on 2026-10-28: `reserved_amount` and `pending_amount` in `GET /api/v1/balances/current` read 0 in USD while a 4,000 USD transfer was in `SENT`. Money in flight cannot be read from the balance, so the panel takes it from the ledger.
- The client sends no `x-api-version` header. The account default returns the newer status set (`FAILED` exists) with a nested `failure` object.
